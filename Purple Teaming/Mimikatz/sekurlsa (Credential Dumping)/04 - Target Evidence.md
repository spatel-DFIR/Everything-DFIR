# Mimikatz — sekurlsa — Target Evidence

Evidence left on the **target** host — the box whose `lsass.exe` gets read. This is a different evidentiary shape than a typical lateral-movement tool: sekurlsa doesn't drop files, create services, or touch the registry to do its core job — it opens a handle and reads memory. **Filesystem and registry sections here are genuinely thin, not under-researched** — say so rather than padding them. The evidentiary weight of this note sits almost entirely in the access event itself (Sysmon Event ID 10) and its `GrantedAccess` value, exactly as flagged in `01 - Overview.md`'s red-flag callout.

## Filesystem

**Thin by design.** A live `sekurlsa::logonpasswords`/`wdigest`/`msv`/etc. read against the running `lsass.exe` process writes **nothing to disk on the target** — no dropped file, no temp artifact, nothing. What *does* show up filesystem-wise depends entirely on which loading method (`00 - Mimikatz Overview.md`'s table) or which sekurlsa sub-command was used:

| Scenario | Filesystem artifact |
|---|---|
| Dropped `mimikatz.exe`/`.dll` run directly | The binary itself, wherever staged — standard execution-evidence trail (Prefetch, Amcache, ShimCache) applies exactly as it would for any executable; see `Windows/06 - Evidence of Program Execution/` for the general artifacts, not re-derived here |
| Reflective load (`Invoke-Mimikatz`, Beacon `execute-assembly`, Meterpreter `kiwi`) | **None** — the mimikatz DLL is mapped directly into an already-running process's memory and never exists as a file (`00 - Mimikatz Overview.md`) |
| `sekurlsa::minidump` workflow (the "quiet-target" variant from `02 - Hands-On Use Cases.md`) | The `.dmp` file itself is the one substantial filesystem artifact this module's ecosystem produces — see below |
| `sekurlsa::tickets /export`, `sekurlsa::backupkeys /export` | `.kirbi` ticket files / exported key material written wherever mimikatz's working directory was at the time — small files, easy to miss in a generic file-listing sweep |

**The minidump file itself** deserves its own line: when the operator uses `comsvcs.dll`'s `MiniDump` export, `procdump.exe -ma`, or Task Manager's "Create dump file" to produce the `.dmp` that `sekurlsa::minidump` later parses *offline*, that dump file is large (typically tens to a few hundred MB for a full-type LSASS dump, scaling with how many logon sessions are cached) and carries a standard `MZ`-prefixed Minidump file header. A large, recently-created file sitting in `C:\Windows\Temp\`, `C:\ProgramData\`, or a similarly writable path — with no obvious legitimate reason to exist — is a meaningful anomaly on its own, independent of any process-access telemetry.

## Registry

Also thin — sekurlsa doesn't write registry keys as part of its core operation. What's relevant here is **pre-existing configuration state** that determines whether/how much sekurlsa can extract, not evidence *generated by* running it. Worth checking during an investigation, but don't mistake it for execution evidence:

| Key | Relevance |
|---|---|
| `HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders\WDigest\UseLogonCredential` | If set to `1` on a build where the secure default is `0` (Windows 8.1/Server 2012 R2+, or any earlier build with KB2871997 applied), `sekurlsa::wdigest` can recover cleartext passwords for sessions established after the flip. The key's own `LastWriteTime` can date when (or if) it was deliberately re-enabled — see `02 - Hands-On Use Cases.md`'s WDigest walkthrough |
| `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\RunAsPPL` | LSA Protection (Protected Process Light) state. `1` (or `2`, which additionally requires a UEFI-lock removal to disable) blocks an unsigned `OpenProcess` against `lsass.exe` outright — the presence/absence of this key is why a `sekurlsa::logonpasswords` attempt on one host succeeds and an identical attempt on another fails cleanly (`01 - Overview.md`) |
| `HKLM\SYSTEM\CurrentControlSet\Control\LSA\LsaCfgFlags` (or Device Guard/Credential Guard policy equivalents) | Credential Guard enablement state. When active, NTLM/TGT secret material is isolated inside the `LsaIso.exe` VBS enclave and is architecturally unreachable to sekurlsa regardless of privilege level — again, environmental context for interpreting a partial/failed extraction, not something sekurlsa itself writes |

## Windows Security Event Log

The uncomfortable finding for this module: **the Security log, by default, essentially never records the LSASS memory read itself.** The events below establish surrounding context (who logged on, what process ran) — none of them are a first-class, default-on record of "process X opened process Y with read access," which is exactly why Sysmon (below) carries the real weight in this file.

| Event ID | Signal | Caveat |
|---|---|---|
| 4672 | Special privileges assigned to a new logon (e.g. `SeDebugPrivilege` present in the token) | Confirms the logon that eventually ran `privilege::debug` had admin-equivalent rights — doesn't confirm sekurlsa specifically ran |
| 4688 | Process creation for `mimikatz.exe`, `powershell.exe` (reflective loader), `rundll32.exe` (comsvcs MiniDump), or `procdump.exe` | Only shows the full command line (including any `/ntlm:`/`/aes256:` material typed inline) if command-line process-creation auditing is separately enabled — off by default |
| 4689 | Process termination for the same | Tail end of the activity window |
| **4656** | "A handle to an object was requested" — `Object Type: Process`, `Object Name` resolving to `lsass.exe`, `Accesses` matching the requested rights | **Generates only if `lsass.exe`'s own process object has a SACL configured with the matching audit ACE.** This is not part of any default Windows audit policy and is uncommon even in hardened environments — verified against Microsoft's own event documentation: per-object SACL is a hard requirement, not an artifact of "Audit Process Access" being enabled globally |
| **4663** | "An attempt was made to access an object" — companion to 4656, generated when the previously-requested access is actually exercised | Same SACL requirement as 4656 — if you don't see 4656 for `lsass.exe`, you won't see 4663 either |

If an environment has gone to the trouble of placing an audit SACL directly on the `lsass.exe` process object, 4656/4663 become a genuinely strong, Security-log-native signal. Absent that (the overwhelming majority of environments), this log tier alone cannot show the read — that job falls to Sysmon.

## Sysmon (if deployed)

| Event ID | Signal |
|---|---|
| **10 (Process Access)** | **The headline event for this entire module.** `TargetImage = C:\Windows\System32\lsass.exe`, `SourceImage` = whatever opened it, `GrantedAccess` = the specific rights granted at the kernel level. See the dedicated breakdown below |
| 1 (Process Create) | The dropped `mimikatz.exe`, the `powershell.exe` hosting a reflective load, or `rundll32.exe`/`procdump.exe` for the minidump path — parent/child chain shows exactly how the process got there |
| 11 (File Create) | The `.dmp` file write for the minidump path, or a dropped binary write for a disk-based run — **absent entirely** for a reflective load or a live `logonpasswords` read, since neither touches disk |
| 3 (Network Connect) / 22 (DNS Query) | Only relevant if a reflective loader was pulled via `IEX (New-Object Net.WebClient).DownloadString(...)` from operator infrastructure (`02 - Hands-On Use Cases.md`'s PowerShell scenario) — shows the target reaching out to the staging server, a target-side mirror of the operator-side web log covered in `03 - Source Evidence.md` |
| 7 (Image/DLL Loaded) | Lower-signal, but worth checking for legitimate credential-dumping tools (ProcDump) loading `dbghelp.dll`/`dbgcore.dll` to actually write the minidump — a reflectively-loaded mimikatz DLL performing the equivalent memory read has no comparable, cleanly-resolving module load to show |

## The `GrantedAccess` Signature — Deep Dive

Building on `01 - Overview.md`'s red-flag callout: the exact rights requested in the `OpenProcess()` call are visible in Sysmon 10's `GrantedAccess` field, and — because this is generated by the kernel at handle-open time — **it cannot be spoofed, suppressed, or altered by anything the operator controls inside mimikatz itself.** The values below are the ones worth building detections around:

| `GrantedAccess` | Flags (hex arithmetic) | Typical source |
|---|---|---|
| **`0x1010`** | `PROCESS_VM_READ` (`0x0010`) \| `PROCESS_QUERY_LIMITED_INFORMATION` (`0x1000`) | A default `sekurlsa::logonpasswords`-style live read — verified directly against `kuhl_m_sekurlsa_acquireLSA()`'s call, matches `01 - Overview.md` exactly |
| **`0x1410`** | Adds `PROCESS_QUERY_INFORMATION` (`0x0400`) on top of the `0x1010` base | Community threat-hunting research (SysmonCommunityGuide, multiple published LSASS-hunting writeups) consistently associates this broader mask with ProcDump/Task Manager-class tools rather than mimikatz's default request — treat as a strong *enrichment* signal, not a mimikatz-specific guarantee, since the exact mask any given tool requests is a function of that tool's own code and can shift across versions |
| **`0x1038`** (computed) | `0x1010` base **+** `PROCESS_VM_OPERATION` (`0x0008`) **+** `PROCESS_VM_WRITE` (`0x0020`) | `sekurlsa::pth`'s reopened LSASS handle (`01 - Overview.md`) — **this is a value derived by combining the documented named flags, not a literal hex constant cited in the source itself** (Delpy's code ORs named constants together, not hex literals), but the arithmetic is exact and this combination is categorically different from every other sekurlsa sub-command: it's the only one requesting *write* access to LSASS |
| Broad/near-full masks (e.g. `0x1FFFFF`, `PROCESS_ALL_ACCESS`) | Varies | Some minidump-producing tools request far more than they strictly need — don't assume every wide-mask hit is benign, and don't assume every narrow-mask hit is mimikatz; correlate with `SourceImage` and the process tree |

**No other legitimate process needs read access to `lsass.exe`'s memory as a matter of routine operation** — the small allow-list is the OS itself, the specific security/EDR agent(s) actually deployed on that host, and (occasionally) approved diagnostic tooling run deliberately by an admin. Any `SourceImage` outside that known-small set requesting any of the masks above against `lsass.exe` warrants investigation regardless of the exact numeric value.

**`CallTrace` as a secondary enrichment field:** Sysmon's Event 10 also records a call stack (`CallTrace`) for the accessing thread. A legitimate on-disk tool like ProcDump resolves cleanly through named, signed modules (`dbghelp.dll`, `dbgcore.dll`) in that stack. A reflectively-loaded mimikatz DLL — mapped directly into memory rather than loaded via the normal loader — frequently shows an `UNKNOWN(...)` or unbacked-memory-region entry in the call stack instead, because the calling code isn't backed by a file the OS can resolve a module name for. This is real signal but requires inspecting the raw event (not always surfaced in default log-viewer summaries) and isn't a substitute for the `GrantedAccess` mask as the primary detection.

## Network-Layer Evidence

| Scenario | What's visible |
|---|---|
| Live `sekurlsa::*` read (any sub-command) | **None.** `OpenProcess()` against a local process is entirely local — no network protocol involved (`01 - Overview.md`'s Techniques table) |
| Reflective loader fetched via HTTP(S) | Outbound connection from the target to operator infrastructure — Sysmon 3/22 as noted above; the operator-side mirror (web server access logs) is covered in `03 - Source Evidence.md` |
| Minidump exfiltration | A large, single outbound file transfer off the target — over SMB, HTTP, or whatever channel the operator's C2/relay uses — distinctive by size and destination even without deep-packet content inspection |
| Chained after remote code execution | If sekurlsa followed a lateral-movement technique (`Impacket/psexec/`, WinRM, etc.), that technique's own target-evidence file documents the delivery leg — not re-derived here |

## Endpoint Security Product Signatures

- **Static signature on the dropped binary:** the stock `mimikatz.exe`/`.dll` carries near-universal AV/EDR static detection (`00 - Mimikatz Overview.md`) — expect an independent, product-specific alert on any host running a current endpoint agent if the binary was dropped and executed in anything resembling its default form.
- **Attack Surface Reduction rule — "Block credential stealing from the Windows local security authority subsystem (lsass.exe)"** (Microsoft Defender, ASR rule GUID `9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2`): purpose-built specifically to stop this exact technique by preventing untrusted processes from opening `lsass.exe` with credential-theft-relevant access, independent of any static file signature. In **Block** mode, the underlying `OpenProcess()` call fails outright regardless of which `GrantedAccess` mask was requested — sekurlsa's live-read path fails cleanly with no credential material recovered. In **Audit** mode, the read is allowed to proceed but the attempt is still logged. Both modes generate an event in the `Microsoft-Windows-Windows Defender/Operational` log: **Event ID 1121** for a Block-mode action, **Event ID 1122** for an Audit-mode detection — verified against Microsoft's own ASR event documentation. Because this rule is specifically about LSASS credential access, hosts running it in Block mode may also need explicit exclusions for legitimate diagnostic tools (ProcDump, Task Manager dumps) that would otherwise be caught by the same rule.
- **Generic EDR hooking:** most modern EDR agents independently hook `OpenProcess`/`NtOpenProcess` (via kernel callbacks or usermode instrumentation) specifically watching for `PROCESS_VM_READ`-class access to `lsass.exe` from non-allow-listed processes — this operates whether or not ASR is configured, and is a large part of why the reflective-loading evasion in `02 - Hands-On Use Cases.md` only defeats *file-based* detection, not this behavioral layer.
- **LSA Protection / Credential Guard:** not an EDR product, but functionally the same effect — see `01 - Overview.md`'s Prerequisites table and the Registry section above. When active, they block or neuter the technique at the kernel/hypervisor level before any endpoint-product logic even runs.
- **On LSA Protection specifically blocking the call:** when `RunAsPPL` denies the `OpenProcess`, mimikatz's own console shows an access-denied error and the kernel simply refuses the handle. Whether this denial reliably produces its own distinct target-side log entry (beyond a possible failed-access Sysmon 10 record, if Sysmon's telemetry captures denied as well as granted access attempts) is **not something verifiable with confidence here** — don't assume a dedicated "PPL blocked an access attempt" event exists without confirming it against the specific Sysmon/EDR version deployed.

## Memory Forensics

- **Reflectively-loaded instances on the target itself:** if the operator ran `Invoke-Mimikatz` or an equivalent loader interactively on the target (rather than remotely via a lateral-movement chain), the loaded DLL exists only in the memory of whichever process hosted it (`powershell.exe`, a C2 agent) — same dynamic as the operator-side case in `03 - Source Evidence.md`, mirrored here on the target. A live memory capture of that process, not a disk image, is the only way to recover it. See `Windows/17 - Memory Forensics/Memory Analysis (Processes, Injection, Rootkits).md` for general technique.
- **`lsass.exe`'s own memory, for a read-only sekurlsa command:** unaltered. Every sekurlsa sub-command except `pth` only *reads* LSASS memory — there's no content change inside `lsass.exe` itself to recover forensically from a plain `logonpasswords`/`wdigest`/`msv` pull, only the access-event trail documented above.
- **`lsass.exe`'s own memory, for `sekurlsa::pth`:** the one exception. Per `01 - Overview.md`'s verified mechanics, `pth` **writes** patched session-key/NTLM material into a logon-session structure inside LSASS's own memory (for the newly-created suspended process's session), not merely into the new process. This is the only sekurlsa operation that leaves content-level residue inside LSASS itself — a targeted memory capture taken shortly after a `pth` run could, in principle, show injected credential material sitting in a session structure that doesn't match what a legitimately-derived session key would look like, though extracting and confirming that requires the same reverse-engineered structure knowledge mimikatz itself uses.

## Building a Timeline

Because sekurlsa's evidence shape differs sharply by loading method, build the timeline around whichever variant applies rather than a single universal sequence:

**Live direct read** (dropped binary or reflective, any `sekurlsa::*` sub-command):
`Sysmon 1 (mimikatz.exe or hosting process launch) → [Security 4688, if command-line auditing enabled] → Sysmon 10 (GrantedAccess against lsass.exe) → [console output or C2 exfil of results — no further target-side artifact] → process exit (Sysmon 5 / Security 4689)`. This entire sequence typically spans seconds.

**Offline minidump ("quiet-target") path:**
`Sysmon 1 (rundll32.exe comsvcs.dll or procdump.exe launch) → Sysmon 10 (GrantedAccess for the dumping tool, often a broader mask than 0x1010) → Sysmon 11 (File Create — the .dmp, often very large) → [file transferred off-box, see Network-Layer Evidence above] → nothing further on this host.` Critically, **the actual sekurlsa parsing never happens on this host at all** — it happens later, on the operator's own analysis machine, entirely outside any timeline this target's logs can construct. Cross-reference `02 - Hands-On Use Cases.md`'s "Offline Analysis of a Dumped LSASS Minidump" and `03 - Source Evidence.md`'s framing of that split.

## Distinguishing `sekurlsa::pth` from a Read-Only Extraction

> 🔴 **Escalate differently.** Every sekurlsa sub-command except `pth` is read-only against LSASS — a `GrantedAccess` of `0x1010`/`0x1410` and nothing more. `sekurlsa::pth` is categorically more invasive: it requests write access (`GrantedAccess` `0x1038`, computed above), spawns a new suspended process under the target's logon context, and generates a **Security 4624 with Logon Type 9 (NewCredentials)** — the same logon type produced by `runas /netonly` and `CreateProcessWithLogonW`'s `LOGON_NETCREDENTIALS_ONLY` flag, both well-documented Windows logon-type mappings. A `4624`/Type 9 landing within moments of a `0x1038`-masked Sysmon 10 against `lsass.exe` is a strong, specific pass-the-hash signature — treat it as a materially worse event than a routine `logonpasswords` read, since it means a new authenticated identity was actively minted and used, not just read.
