# Mimikatz — sekurlsa — Overview

> 🔴 **Red Flag Principle:** Any process **other than the small, known set that legitimately touches `lsass.exe`** (other system processes, EDR agents) opening a handle to `lsass.exe` with **memory-read access** is the single strongest signal this module leaves behind — logged as **Sysmon Event ID 10 (ProcessAccess)** with `GrantedAccess` **`0x1010`** or **`0x1410`** for a default `sekurlsa::logonpasswords`-style read. This survives binary renaming, reflective loading, and every other cosmetic evasion available to the operator, because it's generated by the kernel at the moment of the `OpenProcess` call, not by anything mimikatz itself controls.

## History

`sekurlsa` is mimikatz's original and flagship module — the one that made the tool famous. The name is widely read as a portmanteau of **"security"** and **LSA/LSASS** (the module's own source header simply describes it as "SekurLSA module... Some commands to enumerate credentials..."), reflecting its purpose: reading credential material directly out of the **Local Security Authority Subsystem Service** process, `lsass.exe`. It's authored and maintained by Benjamin Delpy (`@gentilkiwi`) as part of the core [`gentilkiwi/mimikatz`](https://github.com/gentilkiwi/mimikatz) repository, under the project's CC BY 4.0 license — see `00 - Mimikatz Overview.md` for the tool-level history, including the WDigest-cleartext origin story that this module's `wdigest` sub-command is a direct descendant of.

The module's source (`mimikatz/modules/sekurlsa/`) is organized as one file per credential "package" it knows how to parse — `kuhl_m_sekurlsa_msv1_0.c`, `kuhl_m_sekurlsa_wdigest.c`, `kuhl_m_sekurlsa_kerberos.c`, `kuhl_m_sekurlsa_tspkg.c`, `kuhl_m_sekurlsa_livessp.c`, `kuhl_m_sekurlsa_ssp.c`, `kuhl_m_sekurlsa_credman.c`, `kuhl_m_sekurlsa_dpapi.c`, `kuhl_m_sekurlsa_cloudap.c` — each of which understands the exact in-memory layout LSASS uses for that specific authentication provider on a specific Windows build. This per-provider, per-build structure is the module's defining engineering fact and directly explains why sekurlsa needs frequent updates: its source carries **build-specific byte-pattern signatures going up to Windows 11 24H2** as of this writing, because Microsoft doesn't publish or guarantee these internal structures, and every new Windows build risks silently changing them.

## How It Works

```
Operator (mimikatz.exe / reflectively-loaded DLL)              lsass.exe (target process, live or via .dmp file)
───────────────────────────────────────────────                ─────────────────────────────────────────────────
1. privilege::debug ─────────────────────────────▶  Enables SeDebugPrivilege in the caller's token
                                                       (required before step 2 can succeed against a
                                                       protected system process)

2. sekurlsa::logonpasswords (or any sekurlsa cmd)
   kuhl_m_sekurlsa_acquireLSA():
     ├─ Locate PID for "lsass.exe"
     └─ OpenProcess(                              ──▶  Kernel logs the handle-open — Sysmon Event ID 10,
          PROCESS_VM_READ |                             GrantedAccess = 0x1010
          PROCESS_QUERY_LIMITED_INFORMATION,             (VM_READ 0x0010 | QUERY_LIMITED_INFO 0x1000)
          FALSE, lsassPid)

3. Locate the provider DLLs already loaded          Reads lsass.exe's loaded-module list (msv1_0.dll,
   inside lsass.exe (getVeryBasicModuleInformations)  wdigest.dll, kerberos.dll, etc.) to know where to look

4. Pattern-scan the relevant DLL's in-memory code   Build-specific byte signatures locate the *undocumented*
   for a known byte sequence (per-Windows-build)      internal `LogonSessionList` structure inside LSASS —
   ──────────────────────────────────────────────▶    there is no public API that enumerates this

5. Walk LogonSessionList via further memory reads   Each entry = one logon session: LUID, username, domain,
   ──────────────────────────────────────────────▶    SID, logon time, and a pointer chain into each loaded
                                                        provider's own per-session credential structure

6. Decrypt in-memory credential material            Windows encrypts session-key/credential material at
   using build-specific LSA crypto keys              rest in LSASS memory using an internal (also
   ──────────────────────────────────────────────▶    undocumented) key — mimikatz locates and uses this
                                                        key (nt5/nt6 "local helper" in the source) to decrypt
                                                        it locally, entirely within the reading process

7. Print/return decrypted credential material       Plaintext (if a provider caches it), NTLM hash, SHA1,
                                                       Kerberos keys/tickets — depending on which providers
                                                       are present and which sekurlsa sub-command was run
```

Step-by-step, in plain terms:

1. **Privilege setup** — `privilege::debug` enables `SeDebugPrivilege`, which is what actually lets an administrator-context process open a handle to a protected system process like `lsass.exe` at all.
2. **Open LSASS** — sekurlsa's default live-memory path calls `OpenProcess()` with exactly **`PROCESS_VM_READ | PROCESS_QUERY_LIMITED_INFORMATION`** (verified directly against `kuhl_m_sekurlsa_acquireLSA()` in the official source) — **read-only**, no write/execute rights requested. This is a deliberately minimal ask: mimikatz doesn't need to write into LSASS or inject code to read credentials, it only needs to read raw memory. **There is no default driver involved** — `mimidrv.sys` exists in the project but is used for separate operations (like stripping LSA Protection, see below), not for sekurlsa's core memory read.
3. **Find the provider modules** — walks `lsass.exe`'s loaded-module list to find `msv1_0.dll`, `wdigest.dll`, `kerberos.dll`, `tspkg.dll`, `livessp.dll`, and others — sekurlsa only extracts from providers actually loaded in the target's LSASS.
4. **Locate the undocumented session list** — Microsoft doesn't expose an API for "list all logon sessions and their credential material." Instead, mimikatz **pattern-scans** the loaded DLL's executable code for a short byte sequence known (from Delpy's own reverse-engineering, encoded per-Windows-build in the source) to sit near the reference to LSASS's internal `LogonSessionList`. This is the single most fragile part of the tool — a Windows build with no matching signature yet shipped will cause sekurlsa to fail cleanly rather than silently return wrong data, which is why version currency (using a mimikatz build that has a signature for the target OS build) matters operationally.
5. **Walk the structure and decrypt** — once the list is found, mimikatz walks each logon-session entry, reads each provider's per-session credential structure, and decrypts session-key-protected material using build-specific LSA crypto key material it also locates by pattern/offset (the `nt5`/`nt6` "local helper" split in the source reflects genuine cryptographic differences between older and newer Windows builds).
6. **Present results** — decrypted material is printed to the console (or returned over whatever C2 channel is relaying the session, if loaded in-memory via `kiwi`/Beacon).

**Offline variant (`sekurlsa::minidump`):** instead of a live `OpenProcess`, mimikatz opens a `.dmp` file (produced by `procdump.exe -ma lsass.exe`, the `comsvcs.dll` MiniDump technique, or Task Manager's "Create dump file") via `CreateFile`, validates the dump's recorded processor architecture against mimikatz's own build (source explicitly checks `ProcessorArchitecture != PROCESSOR_ARCHITECTURE_AMD64`/`_INTEL` and errors if they don't match), and reads the Windows build number out of the dump's `SystemInfoStream` to select the correct build-specific pattern/offset table — then everything from step 3 onward proceeds identically against the dump file's contents instead of live process memory. This decouples the memory *read* (which happened whenever/wherever the `.dmp` was produced) from the credential *parsing* (which can happen later, offline, on a completely different machine) — see `02 - Hands-On Use Cases.md` for why this matters operationally.

**`sekurlsa::pth` reopens LSASS with more than read access.** Verified directly against the source: pass-the-hash first creates a new, suspended process under the target's logon context (`LOGON_NETCREDENTIALS_ONLY`, so it authenticates outbound as the target without ever needing their password), then **reopens the existing LSASS handle with `PROCESS_VM_OPERATION | PROCESS_VM_WRITE` added** to patch the new process's in-memory session key/NTLM hash directly inside LSASS before resuming it. This is a materially different, more invasive LSASS access pattern than every other sekurlsa sub-command — see the `GrantedAccess` distinction called out in `04 - Target Evidence.md` and `05 - Detection and Hunting.md`.

## Techniques / Protocols Used

| Layer | Detail |
|---|---|
| Process access | Local `OpenProcess()` against `lsass.exe` — no network protocol involved for the live-read path |
| Privilege model | Windows privilege model — `SeDebugPrivilege` (`privilege::debug`), optionally a SYSTEM token (`token::elevate`) for some operations |
| Memory technique | Direct process-memory reads (`ReadProcessMemory`-equivalent) plus offline Minidump-format file parsing — **not** DLL injection, code execution inside LSASS, or a kernel driver by default |
| Credential material recovered | LM/NTLM hashes, SHA1, Kerberos keys/tickets, WDigest/TsPkg/CredSSP/LiveSSP/CloudAP plaintext or key material (provider-dependent — see command reference below) |
| Remote delivery (when chained) | Whatever got the operator execution in the first place — SMB/SVCCTL (`Impacket/psexec/`), WinRM, a C2 agent's reflective-load channel (`Metasploit/Meterpreter/`) — sekurlsa itself has no network component |

## Command Reference — sekurlsa Sub-Commands

Verified directly against `kuhl_m_sekurlsa.c` in the official [gentilkiwi/mimikatz](https://github.com/gentilkiwi/mimikatz) repository — every command below is registered exactly as listed there.

| Command | Plain-English meaning |
|---|---|
| `sekurlsa::logonpasswords` | The all-in-one dump — runs every loaded credential provider in one pass and prints everything found per logon session. The command most people mean when they say "run mimikatz" |
| `sekurlsa::msv` | LM & NTLM hashes only, from the MSV1_0 authentication package |
| `sekurlsa::wdigest` | WDigest provider credentials — **cleartext passwords**, but only for sessions established while `UseLogonCredential=1` was set (see `03/04 - Evidence` files) |
| `sekurlsa::kerberos` | Kerberos-package credentials — cached passwords and, on some builds, smartcard PINs |
| `sekurlsa::tspkg` | CredSSP/Terminal Services package credentials (RDP-related caching) |
| `sekurlsa::livessp` | LiveSSP provider credentials (Microsoft-account-linked auth, Windows 8+; not built for ARM64) |
| `sekurlsa::cloudap` | Cloud Authentication Provider (Azure AD/Entra-joined device) cached material, Windows 10 1909+ |
| `sekurlsa::ssp` | Generic SSP-cached credentials |
| `sekurlsa::credman` | Windows Credential Manager entries currently cached in a logon session |
| `sekurlsa::dpapi` | Cached DPAPI master keys visible in LSASS memory |
| `sekurlsa::process` | Switch (or reset) the module's memory source back to the **live `lsass.exe` process** — the default context |
| `sekurlsa::minidump <file.dmp>` | Switch the module's memory source to an **offline minidump file** instead of the live process — every other sekurlsa command then operates against the dump. Architecture (x86/x64) recorded in the dump must match the running mimikatz build |
| `sekurlsa::pth /user:<u> /domain:<d> /ntlm:<hash> [/run:<cmd>] [/impersonate]` | **Pass-the-hash.** Spawns a new process under the target identity and patches its in-memory NTLM/session-key material directly inside LSASS — accepts `/ntlm:`, `/aes128:`, or `/aes256:` key material |
| `sekurlsa::tickets [/export]` | Lists (and optionally exports to `.kirbi` files) Kerberos tickets found in LSASS memory across sessions — broader than the `kerberos` module's own `kerberos::list`, since it reads other users' sessions too, not just the caller's |
| `sekurlsa::ekeys` | Lists Kerberos encryption keys (RC4, AES128/256, etc.) derived from cached credentials |
| `sekurlsa::krbtgt` | Locates/dumps `krbtgt`-related key material directly from LSASS (not built for ARM64) |
| `sekurlsa::backupkeys [/export]` | Extracts DPAPI domain "preferred backup key" material (x64/ARM64 builds only) |
| `sekurlsa::dpapisystem` | Extracts the machine's `DPAPI_SYSTEM` LSA secret from memory |
| `sekurlsa::trust` | Extracts inter-domain trust key material (x64/ARM64 builds only) |
| `sekurlsa::bootkey` | Sets the SecureKernel boot key candidate, used to attempt decryption of Credential-Guard-isolated material when a suitable key has been separately obtained |

## Quick Use-Case List

- Live SYSTEM-context dump of every credential in memory (`sekurlsa::logonpasswords`)
- Offline analysis of a previously-dumped LSASS minidump (`sekurlsa::minidump`) — no live LSASS touch on the analysis machine at all
- WDigest cleartext-password extraction, when the provider has been (re-)enabled
- Isolated single-provider extraction (`msv`, `kerberos`, `tspkg`, `credman`, etc.) rather than the full `logonpasswords` sweep, for a narrower/quieter pull
- Kerberos ticket harvesting across every session on the box (`sekurlsa::tickets /export`), feeding a pass-the-ticket workflow
- Pass-the-hash to spawn a process authenticating as another user (`sekurlsa::pth`), without ever needing that user's plaintext password
- Pass-the-hash with AES key material instead of NTLM, avoiding RC4/NTLM authentication traffic entirely
- In-memory/reflective execution via `Invoke-Mimikatz` or a similar PowerShell loader, specifically to avoid the disk-based AV signature on the stock binary
- Remote execution chained immediately after a lateral-movement foothold — e.g. `Impacket/psexec/` or `wmiexec.py` drops the operator into a SYSTEM shell, which then runs sekurlsa in-process
- Extraction from an already-established C2 session's in-memory credential module — Meterpreter's `kiwi` extension (`load kiwi` → `creds_all`), see `Metasploit/Meterpreter/02 - Hands-On Use Cases.md`
- DPAPI master-key / backup-key extraction feeding a later offline DPAPI-blob decryption (e.g. browser-saved credentials, saved RDP passwords)
- CloudAP/Entra-joined-device credential material extraction on hybrid-joined endpoints

Full walkthroughs with commands and MITRE ATT&CK mapping for every item above live in `02 - Hands-On Use Cases.md`.

## Prerequisites

| Requirement | Notes |
|---|---|
| Local administrator | Required to enable `SeDebugPrivilege` and successfully `OpenProcess` against `lsass.exe` |
| `privilege::debug` run first | Without it, the `OpenProcess` call in step 2 above fails outright regardless of admin rights |
| Architecture match | mimikatz build (x86/x64) must match the target `lsass.exe`'s bitness — applies to both the live-process path and `sekurlsa::minidump` |
| Provider must be loaded/enabled | `wdigest` only returns cleartext if `UseLogonCredential=1` and the session was established/re-established after that setting took effect (see `03 - Source Evidence.md`/`04 - Target Evidence.md`) |
| LSA Protection / Credential Guard state | If `RunAsPPL` (LSA Protection) is enabled, an unsigned `OpenProcess` from mimikatz is blocked outright by the kernel — bypassing this needs `mimidrv.sys` (a signed kernel driver) to strip the protection flag, a materially noisier and more privileged operation than the default read. If Credential Guard is active, NTLM/TGT secret material lives inside an isolated VBS enclave (`LsaIso.exe`) that sekurlsa cannot reach at all, regardless of privilege level. Both are covered in `04 - Target Evidence.md` |
| For `sekurlsa::minidump` specifically | A `.dmp` file of `lsass.exe` already produced by some other means (ProcDump, `comsvcs.dll`, Task Manager) — no live LSASS access needed on the analysis machine itself |
