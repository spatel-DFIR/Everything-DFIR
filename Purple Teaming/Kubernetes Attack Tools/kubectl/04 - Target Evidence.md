# kubectl — Target Evidence

> **Target Evidence Note:** kubectl is a **remote API client** — it sends HTTP requests to the Kubernetes API server, which logs every API call if audit logging is enabled. This page documents what forensic analysts find in the cluster's logs when an attacker uses kubectl against it.

## Kubernetes API audit logs

The **primary and most reliable signal** for kubectl usage is the **Kubernetes API Audit Log**, generated by the `kube-apiserver` component. When enabled (often via a cluster-wide audit policy), every API request is logged with:
- Request timestamp and unique request ID.
- Requestor identity (user, ServiceAccount, group).
- HTTP verb (GET, POST, PATCH, DELETE, etc.).
- API resource and namespace.
- Request/response payloads (optional, often redacted for Secrets).
- Response status (e.g., 200 OK, 403 Forbidden).

### Audit log location and format

Audit logs are typically written to:
- **Local file:** `/var/log/kube-audit.log` (or configured path on the API server node)
- **Webhook backend:** Sent to an external logging service (e.g., Splunk, CloudWatch, Datadog)

**Format:** JSON, one object per line.

### Example audit log entry

```json
{
  "level": "RequestResponse",
  "auditID": "12345678-1234-1234-1234-123456789012",
  "stage": "ResponseComplete",
  "requestObject": {
    "apiVersion": "v1",
    "kind": "Pod",
    "metadata": {
      "name": "new-pod",
      "namespace": "default"
    }
  },
  "responseStatus": {
    "code": 201,
    "reason": "Created"
  },
  "requestReceivedTimestamp": "2024-08-01T10:30:00.000Z",
  "stageTimestamp": "2024-08-01T10:30:00.100Z",
  "verb": "create",
  "apiVersion": "v1",
  "objectRef": {
    "resource": "pods",
    "namespace": "default",
    "name": "new-pod"
  },
  "sourceIPAddress": "192.168.1.100",
  "userAgent": "kubectl/v1.30.0",
  "user": {
    "username": "system:serviceaccount:default:my-sa",
    "uid": "12345678-abcd-1234-abcd-1234567890ab",
    "groups": ["system:serviceaccounts", "system:serviceaccounts:default", "system:authenticated"],
    "extra": {}
  }
}
```

**Key fields for detecting kubectl usage:**

| Field | Interpretation |
|-------|---|
| `verb` | HTTP verb: `get`, `list`, `watch`, `create`, `patch`, `delete`, `deletecollection` |
| `apiVersion` | API group version: `v1` (core), `apps/v1` (Deployments), `batch/v1` (Jobs), etc. |
| `objectRef.resource` | Resource type: `pods`, `secrets`, `configmaps`, `nodes`, etc. |
| `objectRef.namespace` | Namespace targeted (empty for cluster-scoped resources like nodes) |
| `sourceIPAddress` | IP of the source making the API call (attacker's machine if external, Pod IP if internal) |
| `userAgent` | Tool: `kubectl/v1.30.0`, `kube-client/v1.x.x`, custom clients may spoof this |
| `user.username` | Identity: e.g., `system:serviceaccount:default:my-sa` (ServiceAccount token) or certificate CN |
| `requestReceivedTimestamp` | Timestamp of the API call |

### Audit log patterns for common kubectl operations

**Reconnaissance (list/get operations):**
```
verb: list, resource: pods, objectRef.namespace: default
verb: list, resource: clusterroles
verb: get, resource: secrets, objectRef.name: admin-secret
```

**Pod creation (for lateral movement/persistence):**
```
verb: create, resource: pods, objectRef.namespace: default
verb: create, resource: deployments, objectRef.namespace: default
verb: create, resource: cronjobs, objectRef.namespace: default
```

**Pod execution (exec into container):**
```
verb: create, resource: pods/exec, objectRef.namespace: default, objectRef.name: target-pod
```

**Credential extraction:**
```
verb: get, resource: secrets, objectRef.namespace: kube-system
verb: list, resource: secrets, objectRef.namespace: kube-system
```

**RBAC modification (if cluster-admin):**
```
verb: create, resource: clusterrolebindings
verb: patch, resource: clusterroles
```

## Kubelet logs

The **kubelet** is the node-level component that manages Pods. If a Pod is created or executed via kubectl, the kubelet logs the action:

### Kubelet log locations

- **systemd journal:** `journalctl -u kubelet` (most common)
- **File log:** `/var/log/kubelet.log` (if not using systemd)

### Kubelet log patterns

When kubectl creates a Pod, the kubelet logs:
```
1. Pod creation event: "Pod <namespace>/<pod-name> created"
2. Container image pull: "Pulling image '<image>:<tag>'"
3. Container startup: "Container <container-name> started"
```

When kubectl execs into a Pod:
```
"Opening exec stream for pod <namespace>/<pod-name>, container <container-name>"
```

**Forensic value:** Timestamps and Pod names, useful for correlating with audit log entries.

## Control plane component logs

The **kube-controller-manager** and **kube-scheduler** log when kubectl objects are processed:

### Controller-manager logs

- **Deployment creation:** Controller creates a ReplicaSet in response to the Deployment
- **Pod template conflicts:** Errors if a Pod spec is invalid

### Scheduler logs

- **Pod scheduling:** "Pod <namespace>/<pod-name> assigned to node <node-name>"

These log activity **triggered by** kubectl operations, not the operations themselves — useful for post-facto correlation but less direct than audit logs.

## Container runtime logs

The **container runtime** (Docker, containerd, CRI-O) logs image pulls and container lifecycle events:

### containerd logs

```
time="2024-08-01T10:30:00Z" level=info msg="Pulling image..."
time="2024-08-01T10:30:00Z" level=info msg="Container started: <container-id>"
```

### Docker logs

```
docker logs <container-id>  # Standard output of the container
docker inspect <container-id>  # Metadata, including image used, entrypoint, mounts
```

## ETCD artifacts

If ETCD (the cluster's state database) audit logging is enabled, every change to cluster state is logged:

- **ETCD logs:** Typically found on the control plane node, often at `/var/lib/etcd/`
- **Format:** Binary protocol buffer format (not human-readable)

**Forensic value:** If ETCD logs are captured and parsed, they show the exact sequence and timing of all state changes.

## Event objects (Kubernetes Events)

When Pods are created, scheduled, or fail, Kubernetes generates **Event objects** that are stored in ETCD and visible via:

```bash
kubectl get events -A
kubectl get events -n <NAMESPACE> --sort-by='.lastTimestamp'
```

Events are retained for 1-2 hours by default, then deleted. **Forensic value:** Events visible at investigation time show recent Pod activity.

## Pod logs

If a malicious Pod created by kubectl is still running, its logs (stdout/stderr) are available:

```bash
kubectl logs <POD_NAME> -n <NAMESPACE>
```

If the Pod has executed commands, the attacker's output will be in the Pod's logs.

## Network connections and traffic

If the cluster has network traffic logging enabled:

- **CNI plugin logs:** Calico, Flannel, Weave, etc. log Pod-to-Pod network flows
- **Network policies:** If NetworkPolicies are in place, denied connections are logged
- **API server logs:** HTTPS connections from external IPs (the attacker's machine)

**Pattern:** Unexpected connections to the API server (port 6443) from external IPs are suspicious.

## ServiceAccount token usage patterns

If an attacker uses a ServiceAccount token to authenticate, the audit log shows:

```json
{
  "user": {
    "username": "system:serviceaccount:default:my-sa",
    "groups": ["system:serviceaccounts", "system:serviceaccounts:default"]
  }
}
```

Token usage frequency (e.g., hundreds of API calls per second) is anomalous and suggests automated tooling.

## File system evidence on nodes

If kubectl creates Pods that mount host volumes or run with `privileged: true`, the attacker may leave files on the node's filesystem:

- **Mounted volumes:** Any files written to a `hostPath` mount survive the Pod deletion
- **Container file system:** Ephemeral; deleted when the Pod is deleted (unless using persistent volumes)

## Strongest Target Evidence Signal

**The Kubernetes API audit log entry itself** is the single most reliable signal:

1. **Timestamp:** Exact moment of the kubectl operation.
2. **Requestor:** Username/ServiceAccount (correlates to the attacker's credential).
3. **Action:** Verb (create, delete, patch, etc.) and resource (pods, secrets, etc.).
4. **Object:** Exact namespace, name, and object modified.
5. **Source IP:** Where the request came from (external attacker or from within the cluster).

**Example detection scenario:**
```
A Deployment was created in the kube-system namespace by the "admin" user.
Audit log shows: verb=create, resource=deployments, namespace=kube-system, user=admin
Deployment spec runs a reverse shell to 192.168.1.100:4444
Deployment creates a Pod that mounts /host volume
Kubelet logs show container startup with privileged=true
```

**Evasion-resistant:** If audit logging is enabled, there is no way to use kubectl without generating an audit log entry. The only evasion is:
1. **Disabling audit logging** (requires API server restart or compromise).
2. **Deleting audit logs** (if they're written to a writable location — typically not possible without cluster-admin access to modify RBAC or the API server).
3. **Exfiltrating credentials and using kubectl from an internal Pod** (audit log entry still shows the Pod as the requestor, just with a different source IP).

**If audit logging is NOT enabled:** Detection becomes much harder and depends on correlating events from multiple lower-level sources (kubelet logs, container runtime logs, network logs), which is noisy and error-prone.
