# Rubeus — Target Evidence

What the **domain controller / KDC**, and where relevant the **service host** a forged or abused ticket is used against, log as a consequence of Rubeus activity. Event-ID mechanics that this repo already documents in depth for Kerberos ticket forging and Kerberoasting — the PAC/checksum model, the 20-minute PAC-revalidation rule, and the full Microsoft Defender for Identity (MDI) alert catalog — live in `Mimikatz/kerberos (Golden-Silver Ticket)/` and `Impacket/GetUserSPNs (Kerberoasting)/` and are **cross-linked, not re-derived** here; this page covers what's specific to Rubeus's own command surface.

## Which Commands Touch a DC at All

Refer back to `01 - Overview.md`'s bucket table before reading event tables below — it's the single most important filter for target-side evidence, since **`golden` and `silver` (without `/ldap`) generate no DC-side Kerberos event whatsoever at creation time**, matching `Mimikatz/kerberos (Golden-Silver Ticket)/`'s finding for `kerberos::golden` exactly. Only `diamond`, and `golden`/`silver` when `/ldap` is used, cross that line.

| Command | Genuine 4768 (AS-REQ)? | Genuine 4769 (TGS-REQ)? | Notes |
|---|---|---|---|
| `asktgt`, `brute`/`spray`, `preauthscan`, `asreproast` | ✅ Yes | — | Every one of these is a real AS-REQ against the real KDC |
| `asktgs`, `s4u`, `kerberoast` (default/`/aes`/`/rc4opsec`/`/tgtdeleg`) | — | ✅ Yes | Real TGS-REQ; `s4u` generates **two** (S4U2Self, then S4U2Proxy) |
| `kerberoast /nopreauth:USER` | ✅ Yes | — | Deliberately swaps to AS-REQ specifically to avoid the 4769-based detections built for normal Kerberoasting |
| `golden`, `silver` (no `/ldap`) | ❌ No | ❌ No | Fully offline forge — see `Mimikatz/kerberos (Golden-Silver Ticket)/` for the shared mechanics |
| `golden`, `silver /ldap` | ❌ No (LDAP read only) | ❌ No | LDAP/SMB traffic for PAC population, no Kerberos protocol message at all |
| `diamond` | ✅ Yes (for the base TGT) | — | **The 4768 is tied to the real template account authenticated as, not the final claimed identity** — same structural gap `Impacket/ticketer/`'s `-request` (Diamond) finding documents: an analyst checking "was a 4768 ever issued for the identity this forged ticket claims" will miss it entirely |
| `changepw` | — | — | Separate protocol (RFC 3244, port 464) — see below |

## Event Log Detail — Where Rubeus's Behavior Differs From a Generic Client

- **Ticket Encryption Type field (4768/4769)**: the `0x17`/`0x11`/`0x12`/`0x1`/`0x3` value table, and the two-layered client-preference-vs-KDC-honors-`msDS-SupportedEncryptionTypes` mechanic, are already fully documented in `Impacket/GetUserSPNs (Kerberoasting)/01 - Overview.md` — apply that table directly. The one Rubeus-specific addition: **the default (no-flag) `kerberoast` posture requests each account's highest supported enctype**, so a clean default-mode Rubeus Kerberoast run against a well-patched, AES-only domain will show `0x12` (AES256) tickets, not the `0x17` (RC4) most Kerberoast detection literature centers on — don't tune a detection to RC4-only and assume it covers Rubeus's default behavior.
- **Kerberoasting burst signature**: identical shape to what `GetUserSPNs (Kerberoasting)/01 - Overview.md`'s red-flag callout already documents (one principal, many different SPNs, tight time window) — Rubeus's default and `/aes` modes produce this pattern identically to Impacket's tool; only `/rc4opsec`/`/tgtdeleg` (which use the `tgtdeleg` trick to get a TGT first) and `/ticket:X` change the requesting identity's apparent behavior, since the TGS-REQs then originate from a ticket obtained via the GSS-API delegation trick rather than a freshly-requested TGT.
- **AS-REP Roasting burst signature**: `asreproast`'s default (no `/user`) sweep sends an AS-REQ-without-pre-auth for every `DONT_REQ_PREAUTH` account in the domain in quick succession — the domain-controller-side equivalent burst pattern to Kerberoasting's, but on 4768 instead of 4769, and specifically for accounts that **already** carry the pre-auth-disabled UAC flag (a pre-existing misconfiguration, not something Rubeus sets).
- **S4U2Self / S4U2Proxy (4769)**: both S4U legs generate separate 4769 events for the delegation-trusted account (`patsy` in the `02` examples), **not** for the impersonated user — the impersonated identity only appears inside the ticket's own PAC/cname fields, which standard 4769 auditing does not surface without deeper packet/PAC inspection. The `Transited Services` field on the S4U2Proxy-leg 4769 is the most direct native signal that constrained-delegation impersonation occurred at all.
- **Bronze Bit (CVE-2020-17049)**: no dedicated native event exists for the forwardable-flag flip itself — the detectable consequence is a **Protected Users-group member's identity appearing in a successful S4U2Proxy service-ticket grant**, which should be structurally impossible under the pre-patch behavior Bronze Bit exploits; hunt by cross-referencing S4U2Proxy target identities against Protected Users group membership rather than looking for a distinct "Bronze Bit" event.
- **`changepw` / password reset via TGT**: RFC 3244 traffic to port 464 is a distinct protocol from AS-REQ/TGS-REQ — Windows still logs the resulting password change as a standard account-management event (4723 self-service change / 4724 administrative reset, per Microsoft's own documentation of these IDs), tied to whichever identity's TGT or delegated service ticket performed the kpasswd exchange. This repo has not independently captured a live 4723/4724 pair from a Rubeus `changepw` run to confirm which of the two fires for the `/targetuser` (delegated-reset) case specifically — treat that specific mapping as an open question rather than asserted fact, and verify against a live test in your own environment before building a detection on it.
- **`golden`/`silver /ldap` SYSVOL mount**: on a DC with Object Access auditing enabled for the `SYSVOL` share, the mount/read/unmount sequence the README's own example output shows explicitly generates Event ID **5140** (Network Share Object Access) and, if detailed file-share auditing is on, **5145** (Detailed File Share) for the specific policy file read — neither is enabled by default, matching the same "AD logs nothing about a normal read by default" gap `AdFind/01 - Overview.md` already documents for plain LDAP reads.
- **Unconstrained-delegation harvesting (`monitor`/`harvest`)**: the target-side signal lives on the **delegation-enabled host itself**, not the DC — Rubeus's own design explicitly keys off that host's **Event 4624** (successful logon) to know when a fresh TGT has arrived to extract. Any account authenticating interactively or over network to a host with unconstrained delegation enabled hands its TGT to that host automatically as a side effect of the Kerberos protocol itself — this is a pre-existing AD misconfiguration Rubeus exploits, not something it causes.

## Filesystem / Registry on the Target

Most Rubeus commands leave **no filesystem or registry footprint on the DC or target service host at all** — ticket forging is local to the operator's own host, and ticket use (`/ptt`, S4U, forged-ticket service access) is a normal Kerberos authentication from the target's perspective, indistinguishable at the filesystem/registry layer from a legitimate logon using a legitimate ticket. Any subsequent filesystem/registry activity on a target reached via a Rubeus-obtained ticket (e.g., the `dir \\primary.testlab.local\C$` step in `02`'s S4U example) is standard SMB/lateral-movement evidence, already covered by this repo's `Windows/12 - Lateral Movement.md`-equivalent artifact references — not re-derived here.

## Endpoint-Security-Product Signature Behavior

- AMSI (added to .NET 4.8 directly, not just PowerShell) is positioned to inspect the managed assembly's IL/behavior regardless of delivery vector, per the README's own note under Weaponization.
- Because no official binary exists, static AV signatures are inherently brittle against Rubeus specifically — EDR products lean on **behavioral** detections instead: non-`lsass.exe` port-88 traffic, `LsaCallAuthenticationPackage()` calls from an unusual process, and the `winlogon.exe` token-duplication pattern documented in `03 - Source Evidence.md` are all realistic EDR rule targets, and none of them depend on matching a specific compiled binary's signature.

## Building a Timeline

Chain source and target evidence together in this order for a realistic Rubeus incident reconstruction:

1. **Source-host process creation** (Sysmon 1 / Security 4688) — the Rubeus process spawns, command line captured (credential material and all).
2. **Source-host network connection** (Sysmon 3) — outbound port 88/464 from that non-`lsass.exe` process.
3. **[Elevated operations only] Source-host token theft** — `winlogon.exe` handle opened, SYSTEM impersonation begins, immediately preceding an all-users `triage`/`dump`/`monitor`/`harvest` call.
4. **DC-side Kerberos event** (4768/4769, where applicable per the table above) — encryption type, requesting principal, and (for TGS-REQ) the target SPN or S4U `Transited Services` field.
5. **Target-service authentication** — whatever the forged/abused ticket was actually used for (file share access, a second RPC-based tool, etc.) — correlates against this repo's existing per-tool Target Evidence pages for whatever comes next in the chain.
6. **[Golden/Silver only]** Steps 4-5 collapse to **step 5 only** — there is no DC-side event to anchor the timeline to at creation time, only at use; cross-reference `Mimikatz/kerberos (Golden-Silver Ticket)/05 - Detection and Hunting.md`'s MDI-alert-based approach for how to still catch *use* even with a silent creation step.
