# WinDbg — Overview

> 🔴 **Red Flag Principle:** WinDbg's **Time Travel Debugging (TTD)** creates a deterministic, byte-for-byte recording of a target process from launch to crash or manual stop — a `.run` trace file that allows an attacker to replay execution backward and forward, inspect every memory read/write, and perform introspection that would normally require live debugging. On the target host, the only artifacts are the trace files themselves (`*.run`, `*.idx`); there is no debugger process running on the target, no network connection back to an attacker host (unlike live remote debugging), and no parent-child relationship to a debugger parent process. For a defender, TTD traces are both the strongest evidence of exploit development or crash-dump analysis work and the hardest to detect if an operator copies them off the network cleanly — the traces themselves are not encrypted, are large (~10-20x size of a normal memory dump), and contain the exact execution history leading up to a failure.

## History

Verified directly against Microsoft's official documentation and the Windows Driver Kit repository:

- **Official source:** Microsoft's [Debugging Tools for Windows](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/), maintained by the Windows Hardware team.
- **Current version:** WinDbg (unified), formerly released as "WinDbg Preview" in the Microsoft Store. As of 2025, the Preview and Classic versions are merged into a single modern codebase with the same underlying debugging engine — functionally equivalent.
- **Distribution channels:** (1) Direct installer download from Microsoft, (2) Microsoft Store app (`WinDbg Preview`), (3) Windows Package Manager (`winget install Microsoft.WinDbg`), (4) Included in the Windows Driver Kit (WDK) and Windows SDK (legacy `windbg.exe`).
- **License:** Proprietary / Microsoft.
- **Key distinction from Immunity Debugger:** WinDbg is **Microsoft's official debugger, built into the Windows SDK**, with full support for both **user-mode and kernel-mode debugging**. Immunity Debugger is a commercial third-party tool (user-mode Windows exploitation only) based on Olly-compatible plugins. WinDbg is free; Immunity is paid. WinDbg supports managed code (.NET) via the SOS extension; Immunity does not.
- **Time Travel Debugging (TTD):** First shipped in 2017, now fully integrated and documented. TTD is WinDbg's single most distinctive feature relative to competitors — the ability to record a complete, deterministic execution trace and replay it offline with full introspection (breakpoints, memory inspection, register reads all work backward and forward in time).
- **Current status:** Actively maintained. Last major update documented in release notes: 2025-04-04 (architecture and feature stability updates).

## How It Works

WinDbg operates in three mechanically distinct modes:

| Mode | Mechanism | Use Case |
|---|---|---|
| **Live user-mode debugging** | Attaches to a running process or launches a new one; full control over execution (breakpoints, stepping, memory inspection). Network-debuggee attachment is supported via `-remote` or remote debugging protocol. | Interactive debugging of a live process on the local host or remotely. |
| **Live kernel-mode debugging** | Connects to a target kernel via serial port, USB, 1394 (FireWire), or network (requires both machines on same physical/logical network). Requires enabled debugging boot option and kernel symbols. | Debugging kernel drivers, blue screens (STOP codes), system hangs. |
| **Offline crash-dump analysis** | Opens a memory dump file (`.dmp`; generated by crash dump feature, ProcDump, or dump utilities); no live process attachment. All commands work on the snapshot; memory/register inspection only (no modification). | Post-mortem analysis after a process/system crash. |

### Time Travel Debugging (TTD) — the differentiator

TTD records the complete execution of a process **from launch to crash or explicit stop**, capturing:
- Every instruction executed
- Every memory read/write
- Every system call
- Every API call
- All register state changes
- Exception/signal history

The recording is written to a pair of files:
- **`.run`** — the trace data (typically 10-20x the size of a normal memory dump)
- **`.idx`** — index file for fast replay navigation (typically 2x the `.run` file size)

After recording stops, TTD builds an index and allows the debugger to "rewind" to any point in the execution timeline — all standard debugging commands (`bp`, `ba`, `du`, `r`, `k`, etc.) work backward and forward within the recorded window. This is fundamentally different from a crash dump, which is a single snapshot at one point in time.

```
Attacker / Exploit Developer                         Target Process
─────────────────────────────                         ──────────────
1. WinDbg launched with -record flag         ──▶  TTD.exe hooks process at launch
   (or via UI: "Record with Time Travel")           (or via UI attach)

2. Process executes normally                  ──▶  TTD records every instruction,
   (test payload, run exploit, crash)              API call, exception, memory access

3. Process crashes or debugger stops          ──▶  .run + .idx files written to disk
   recording (Ctrl+Break)                         (no network traffic back to debugger)

4. Debugger loads trace (local or remote)    ◀──  Replay begins; debugger can seek
   and replays execution offline                   to any point, inspect state, set
                                                   breakpoints, modify view of timeline
```

### Debugger commands — the standard interface

All WinDbg commands work in user-mode, kernel-mode, and TTD replay:

| Family | Key Commands | Purpose |
|---|---|---|
| **Breakpoints** | `bp` (set breakpoint at address/symbol), `ba` (break on access to memory), `bl` (list), `bc` (clear), `bd` (disable), `be` (enable) | Stop execution at specified conditions |
| **Execution control** | `g` (go), `p` (step over), `t` (trace/step into), `gu` (step out), `gn`/`gh` (go with exception handling) | Navigate execution |
| **Memory inspection** | `d[a/b/d/p/q/u/w]` (display memory in various formats), `du` (display Unicode string), `dp` (display pointer-size values), `dd` (double-words) | Read memory at any address |
| **Registers** | `r` (display all registers), `r eax` (display specific register), `r eax=0x1234` (modify register) | View/modify CPU state |
| **Stack / Call stack** | `k`, `kb`, `kv` (display stack backtrace) | Show return addresses and local frame pointers |
| **Symbols / Disassembly** | `u` (unassemble), `uf` (unassemble function), `x` (examine symbols), `ln` (list nearest symbol) | Navigate code |
| **Analysis / Extensions** | `!analyze -v` (detailed crash analysis), `!dumpheap` (managed heap inspection via SOS), `!exception` (exception details) | Special debugger commands (prefix with `!`) |
| **Control** | `q` (quit), `qd` (quit and detach) | Exit debugger |

### Managed code (.NET) debugging via SOS extension

WinDbg can debug .NET Framework, .NET Core, and .NET 5+ applications by loading the **SOS (Special OS Support) debugging extension** (`sos.dll`):

```
0:000> .load sos.dll
0:000> !sos.help
0:000> !sos.DumpHeap          (enumerate managed heap objects)
0:000> !sos.PrintException    (show .NET exception details)
0:000> !sos.Threads           (list managed threads)
0:000> !sos.CLRStack          (managed call stack)
```

SOS must be version-matched to the .NET runtime being debugged (`.NET Framework clr.dll` vs. `.NET Core coreclr.dll`).

## Techniques / Protocols Used

| Layer | Detail |
|---|---|
| **Debugging protocols** | Microsoft's native debugging engine (DbgEng.dll, DbgHelp.dll), used by all Windows debuggers (WinDbg, Visual Studio, VS Code). TTD uses a proprietary recording format (Chromium's equivalent is the DevTools protocol, but TTD has no standardized open specification). |
| **User-mode attachment** | Windows `DebugActiveProcess()` API; debugger thread receives `DEBUG_EVENT` structures (breakpoint, exception, create thread, create process, exit thread, exit process, DLL load, etc.). |
| **Kernel-mode connection** | Serial, USB, 1394, or network (requires specialized boot and Ethernet driver). Uses KD (kernel debugger) protocol. |
| **Remote debugging** | WinDbg → target via `DbgRPC` (debugger RPC protocol) or SSH tunnel. `windbg -remote tcp:Port=<N>,Server=<host>` (server-mode) or `-remote npipe:Pipe=<N>,Server=.` (named-pipe). |
| **Crash dump format** | Windows minidump (`.dmp`, `MINIDUMP_HEADER` structure) or full memory dump. Standard format across all dump-reading tools (WinDbg, Volatility, etc.). |
| **TTD recording format** | Proprietary `.run` + `.idx` file pair. `.run` contains raw instruction/memory traces; `.idx` is an index for fast seek times. No public format specification. |
| **Symbols** | PDB (Program Database) format for executable symbols. Can be fetched from Microsoft's public symbol server (`http://msdl.microsoft.com/download/symbols/`) or configured privately. |

## Command-Line Switches — Quick Reference

### Launching WinDbg

| Switch | Purpose |
|---|---|
| `-a <ActionType>` | Action on attach: `-a t` (trace), `-a e` (event), `-a g` (go). Default is interactive breakpoint. |
| `-p <PID>` | Attach to process by PID (e.g., `windbg -p 1234`). |
| `-pn <ProcessName>` | Attach to process by name (e.g., `windbg -pn notepad.exe`). |
| `-record` | Enable TTD recording. Must be specified at launch to record from process start. |
| `<executable> [args]` | Launch a new process for debugging. Example: `windbg notepad.exe` |
| `-remote tcp:Port=<N>,Server=<host>` | Connect to a remote debugging session (client mode). |
| `-server tcp:Port=<N>` | Start a remote debugging server (server mode). |
| `-k <ConnectionOptions>` | Kernel debugging connection (e.g., `-k com:port=COM1,baud=115200`). |
| `-dump <DumpFile>` | Open a crash dump for offline analysis. |
| `-symbols <SymbolPath>` | Set symbol search path. Example: `-symbols SRV*C:\Symbols*http://msdl.microsoft.com/download/symbols/` |
| `-nologo` | Suppress startup banner. |
| `-quiet` | Suppress console output (batch mode). |

### Scripting & Automation

| Switch | Purpose |
|---|---|
| `-c "<Commands>"` | Execute a command string on launch, then exit (batch mode). Example: `windbg -p 1234 -c ".load sos.dll; !sos.Threads"` |
| `-s <BreakRate>` | (Kernel debugging) Break into debugger every N instructions. |

### TTD-specific switches

| Switch | Purpose |
|---|---|
| `-record` | Enable recording. Process must be started **with** this flag to record from the beginning. |
| `-recordFlags <Value>` | (TTD) Flags to control what gets recorded (e.g., memory writes, I/O). |

## Quick Use-Case List

1. **User-mode crash analysis** — Open a `.dmp` file generated by Windows crash dumps or tools like ProcDump; use `!analyze -v` to get automated crash triage (faulting address, exception code, likely cause).
2. **Live user-mode debugging** — Attach to a running process, set breakpoints, step through code, inspect memory/registers to diagnose hang/crash/behavior.
3. **Kernel-mode crash analysis** — Analyze a kernel memory dump (Blue Screen STOP code, driver issue). Use `!analyze -v`, `!bugcheck`, load kernel extensions for specialized analysis.
4. **Time Travel Debugging (TTD) — record exploit behavior** — Record a process exploiting a target (shellcode injection, ROP chain, heap spray) to see exact execution order, memory corruption layout, exception handling.
5. **TTD — replay and search** — Load a recorded trace and use `!tt.index` to build index, then search for specific events (memory writes at an address, exceptions, function calls) using `dx` LINQ queries.
6. **Managed code (.NET) debugging** — Load a .NET process dump or live process, load SOS extension (`.load sos.dll`), use `!sos.PrintException`, `!sos.DumpHeap`, `!sos.Threads`.
7. **Privilege-escalation exploit development** — Record a test run of a local-privesc payload (SeImpersonate, token-theft, driver-load); TTD lets you step through token operations and verify the exact state change (e.g., token handle duplication).
8. **Malware introspection** — Record a malicious binary's startup sequence (DLL injection hooks, API hooking, anti-analysis), replay offline to inspect the attacker's hidden behavior.
9. **Debugging ROP gadgets / shellcode** — Step through injected shellcode instruction-by-instruction, viewing register state and memory at each instruction. Set data breakpoints (`ba`) to break when a value is written to a specific register or memory location.
10. **Attach to running service** — Debug a Windows service (e.g., `svchost.exe`, a custom service) live; stop at API calls, inspect thread state, find race conditions.
11. **Remote kernel debugging** — Connect to a target machine's kernel debugger (over serial, USB, or network) to debug system crashes or hypervisor behavior.
12. **Binary diffing & patch analysis** — Compare crashed vs. patched versions: record both, load traces side-by-side, compare register state and memory writes at the faulting address to understand what the patch fixed.

## Prerequisites

| Prerequisite | Why Required | Scope |
|---|---|---|
| **Administrator privileges** (for user-mode, TTD) | Required to attach to most processes (exceptions: processes owned by the same user or child processes). TTD recording requires admin to hook the process. | User-mode debugging, TTD recording |
| **Kernel symbols** | Required for kernel-mode debugging and crash-dump analysis (without symbols, only raw addresses are shown, not function names). | Kernel-mode, crash-dump analysis |
| **Target process must be launchable / attachable** | TTD must start recording at process launch (no attach to existing process for TTD). For live user-mode debugging, target must not be already under a different debugger. | User-mode, TTD |
| **.NET SDK / SOS extension** (for .NET debugging) | SOS.dll must be available and version-matched to the target runtime (CLR for .NET Framework, coreclr.dll for .NET Core). Not required if debugging native code only. | Managed code (.NET) |
| **Debuggee machine must be running Windows 10 (version 1607+) or Windows 11** | WinDbg is Windows-only; target system must support the debugger's architecture (x64, ARM64). Kernel debugging requires special boot configuration. | All modes |
| **Symbol path configuration** (optional but recommended) | If symbols are not cached locally, the debugger must fetch them from Microsoft's symbol server (or a private server). Configure via `.symfix` command or `-symbols` flag. | All modes (for useful output) |

## Key Distinctions vs. Immunity Debugger

| Aspect | WinDbg | Immunity Debugger |
|---|---|---|
| **Debugger mode support** | User-mode + Kernel-mode + crash dump analysis | User-mode only |
| **Cost** | Free (Microsoft) | $2,500 USD (commercial) |
| **Platform** | Windows (built into SDK) | Windows (standalone binary) |
| **Managed code (.NET) support** | Yes (via SOS extension) | No |
| **Time Travel Debugging** | Yes (TTD, Microsoft's own) | No (third-party TTD tools exist but not integrated) |
| **Plugin architecture** | DBGENG.DLL extension API; limited scripting (JavaScript, NatVis) | Fully scriptable via Python; mona.py is a popular third-party plugin |
| **Scripting language** | JavaScript, NatVis (markup), Python (community) | Python (built-in) |
| **Community plugin ecosystem** | Smaller; Microsoft-focused (WinDbg Preview plugins in Microsoft Store) | Larger; Olly-debugger-compatible plugin model (mona.py, others) |
| **Suitable for** | Exploit developers who need kernel debugging, TTD, .NET analysis, or Windows-internal introspection; blue teams analyzing crash dumps | Exploit developers (Windows user-mode only) who prefer Python scripting and Olly-compatible plugin ecosystem |
