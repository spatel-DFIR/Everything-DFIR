# LOLBins — Overview

The root page for the `LOLBins/` folder. Unlike every other folder in `Purple Teaming/` — which covers a single offensive tool or suite (Impacket, Mimikatz, Metasploit) with real shared install steps and library code — `LOLBins/` covers **14 unrelated, independently-shipped binaries** (mostly Microsoft's own, one third-party trio) that have nothing in common except a shared attacker use case: repurposing a signed, legitimate, already-present binary to do something its vendor never intended. There is no install step to document, no shared codebase, no version-milestone history to track across the folder as a whole. What this page covers instead is the **LOLBIN concept itself**, the community catalog that names and tracks it, and the handful of genuine cross-cutting mechanical patterns that recur across several of these 14 tools despite them being otherwise unrelated. This page intentionally stays shallow; go to a sub-folder's own `01 - Overview.md` for its Red Flag Principle, verified command reference, and full evidence chain.

## What LOLBins Is

"LOLBin" — **L**iving **O**ff the **L**and **Bin**ary — describes a binary that is already present on (or trivially installable to) a target system, digitally signed and/or vendor-supplied, and intended for entirely legitimate administrative, developer, or IT purposes, but which also exposes some documented or side-effect functionality an attacker can repurpose for execution, persistence, credential access, defense evasion, or exfiltration. The core value proposition to an attacker is that the binary is **already trusted** — it's allowlisted by default in most application-control policies, it doesn't trip "unknown/unsigned executable" alerts, and its presence on the host requires no delivery step of its own.

Every other folder in `Purple Teaming/` is organized around a **tool an operator deliberately brings to an engagement** — Impacket, Mimikatz, Sliver. This folder is organized differently: around **14 binaries the target environment already has**, or can be made to have with a routine feature install. That's the structural reason `LOLBins/` reads differently from its siblings — there's a "History" section in each sub-folder's `01 - Overview.md`, but for most of the 14 it points to Microsoft's (or RARLAB's) own product documentation, not a GitHub release changelog, because these binaries are not offensive-security projects with a maintainer to interview.

The 14 covered here — `ntdsutil.exe`, `certutil.exe`, `powershell.exe`/`pwsh.exe`, `msbuild.exe`, `winrar.exe`/`Rar.exe`, `bitsadmin.exe`, `schtasks.exe`, `wmic.exe`, `sc.exe`, `netcat`/`ncat`/`socat`, `setspn.exe`, `regsvr32.exe`, `mshta.exe`, `rundll32.exe` — were sourced from the user's SEC560 personal-course-index gap analysis (`PLANNING.md` §5 R6/R9 and Wave 4), not from a single canonical "top LOLBins" list. It is explicitly not a closed set (`PLANNING.md` §5's Wave 1 row: "more added as identified").

## The LOLBAS Project

The **[LOLBAS Project](https://lolbas-project.github.io/)** (`LOLBAS-Project/LOLBAS` on GitHub) is the community-maintained catalog this whole folder leans on for abuse-technique sourcing — a structured, YAML-backed database of Microsoft-authored/OS-shipped binaries, scripts, and libraries with documented "unexpected" functionality, each entry mapped to MITRE ATT&CK and crediting the researcher who found the technique. Its own published inclusion criteria are narrower than most operators assume: a binary must be **Microsoft-authored or OS-shipped**, and its documented abuse must be genuinely **unexpected** functionality, not merely "a legitimate feature an attacker finds useful." Both boundaries matter directly to this folder, because several of the 14 sub-folders here sit right on one edge or the other of that bar — verified per-tool, not assumed:

| Tool | In LOLBAS's main catalog? | Why / why not |
|---|:---:|---|
| [`ntdsutil/`](ntdsutil/01%20-%20Overview.md) | ✅ Yes (`OtherMSBinaries`) | 1 documented command (`ifm`), credited to Tony Lambert (2020), built on Sean Metcalf's original research |
| [`certutil/`](certutil/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | Catalogued 2018-05-25 by Oddvar Moe; multiple download and encode/decode techniques |
| [`regsvr32/`](regsvr32/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | Squiblydoo technique (scriptlet loading via `/i`), credited to Casey Smith and community researchers; fileless code execution |
| [`mshta/`](mshta/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | HTML Application (HTA) loading and execution, documented abuse sourced from LOLBAS and MITRE ATT&CK T1218.005 |
| [`rundll32/`](rundll32/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | Direct DLL export invocation and Control Panel abuse, documented in LOLBAS and MITRE ATT&CK T1218.011 |
| [`msbuild/`](msbuild/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | Credited to Casey Smith (`@subTee`); 5 distinct documented commands, not just the inline-task technique most write-ups focus on |
| [`bitsadmin/`](bitsadmin/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | Catalogued 2018-05-25 by Oddvar Moe, crediting Rob Fuller and Chris Gates |
| [`schtasks/`](schtasks/01%20-%20Overview.md) | ✅ Yes (`Binaries`, thin) | Only 2 documented commands — LOLBAS's own catalog here is a floor, not a ceiling; MITRE ATT&CK's own T1053.005 procedure-example library (APT3, BRONZE BUTLER, Lazarus, Earth Lusca, and more) is the fuller abuse-breadth source |
| [`wmic/`](wmic/01%20-%20Overview.md) | ✅ Yes (`Binaries`) | Catalogued 2018-05-25 by Oddvar Moe, crediting Casey Smith for the XSL-transform "SquiblyTwo" technique |
| [`sc/`](sc/01%20-%20Overview.md) | ✅ Yes (`Binaries`, narrow) | Only 2 documented commands, both the same ADS-`binPath` trick (`create`/`config`) — LOLBAS does **not** catalogue the classic create-and-start remote-execution primitive most pentest material treats as `sc.exe`'s primary abuse; that's sourced from MITRE T1543.003 instead |
| [`winrar/`](winrar/01%20-%20Overview.md) | ❌ Zero presence | Third-party software (RARLAB) — structurally out of scope, since LOLBAS is bounded to Microsoft-authored/OS-shipped binaries |
| [`netcat/`](netcat/01%20-%20Overview.md) (netcat/ncat/socat) | ❌ Zero presence | Third-party for all three (Hobbit/OpenBSD, the Nmap Project, Gerhard Rieger respectively) — same out-of-scope reasoning as WinRAR |
| [`setspn/`](setspn/01%20-%20Overview.md) | ❌ Zero presence | Microsoft-authored, but its read/write operations on `servicePrincipalName` are ordinary, fully-documented AD administration — not the "unexpected" functionality LOLBAS requires |
| [`powershell/`](powershell/01%20-%20Overview.md) | ⚠️ Excluded from the main catalog | Only a 3-line `HonorableMentions/PowerShell.yml` entry exists (added 2024). The maintainer, Wietze Beukema, closed a GitHub issue asking why PowerShell isn't a full LOLBin on record: offensive PowerShell use is "expected" for a scripting engine, not the "unexpected" functionality the project requires |

Ten of the 14 are properly catalogued in LOLBAS (all except the three added in Wave 4 are either in the main catalog or explicitly documented elsewhere); `winrar` and `netcat` fall outside LOLBAS's scope for the same structural reason (third-party origin); `setspn` and `powershell` are both Microsoft-authored yet excluded for the identical "expected, not unexpected" reasoning, just applied to a directory-attribute utility in one case and an entire scripting engine in the other. The three Wave 4 additions (`regsvr32`, `mshta`, `rundll32`) are all properly catalogued in LOLBAS's `Binaries` category. That "expected vs. unexpected" line is worth internalizing on its own — it's the project's real inclusion bar, not "is this ever used maliciously."

## Shared Mechanics Across LOLBins

Genuine cross-cutting findings only — this folder doesn't force a "shared library" or "install & setup" narrative onto 14 tools that don't have one. What follows are the patterns that actually recur across multiple independently-built sub-folders.

### The detection problem is behavioral, not binary

Every tool in this folder is signed, expected to exist, and often business-critical — Windows Update, WSUS, and enterprise deployment tooling all lean on the exact same BITS jobs an attacker abuses for persistence; CA administrators run the same `certutil` verbs a phishing loader does; developers and CI pipelines run `msbuild.exe` against real project files thousands of times a day. **Blocking the binary is rarely a viable control**, and command-line-only detection is weaker here than it looks, because the argument shapes involved (`-urlcache -f`, `process call create`, `binPath=`) are frequently identical between legitimate administration and abuse. What actually separates the two is **context**: who ran it, what its parent process was, when relative to a normal admin/maintenance window, what the output path or target looked like, and what happened immediately before or after. Nearly every sub-folder's "Legitimate vs. Abused" comparison (`certutil/`, `msbuild/`, `winrar/`, `powershell/`) makes this same point in tool-specific terms rather than restating it as boilerplate.

### The thin-client-to-a-service pattern

Four of the 14 tools are not the process that actually does the interesting work — they're a short-lived CLI front end that hands a job to a **separate, longer-lived OS service process**, which then does the real work (and generates the real evidence) independently of whether the original CLI process still exists:

| Tool | Service that does the work | Payload executes as a child of… | Delay between command and payload |
|---|---|---|---|
| `bitsadmin.exe` | BITS (`svchost.exe -k netsvcs -s BITS`) | the BITS service host, **not** `bitsadmin.exe` | up to the 90-day job-inactivity ceiling |
| `schtasks.exe` | Task Scheduler (`svchost.exe -k netsvcs -p -s Schedule`) | that `svchost.exe` instance — **not** `schtasks.exe`, and (since Windows 10 1511) **not** `taskeng.exe` either | anywhere from immediate to months, across reboots |
| `sc.exe` | Service Control Manager (`services.exe`) | whatever `binPath=` points to, launched by the SCM | immediate on `sc start`, but a `sc config` hijack can sit dormant on an already-running trusted service indefinitely |
| `wmic.exe` | WMI (`WmiPrvSE.exe`, hosted under a shared `svchost.exe`) | `WmiPrvSE.exe`, **not** `wmic.exe`, even for a purely local, non-`/node:` call | effectively immediate, but the process-tree parent is still wrong if you're hunting `wmic.exe`'s children |

The practical consequence, stated once here rather than four times across the sub-folders: **a hunt that looks for "what did the LOLBIN spawn" will come up empty for all four of these** — the parent process an analyst needs to watch is the OS service host, not the tool the operator actually typed. `ntdsutil.exe` and `certutil.exe` are the folder's counter-examples — both do their entire abuse-relevant work inside their own single process, no service handoff involved.

### The strongest signal is often a side-effect artifact, not the invocation

Where this folder's sub-tools have a genuinely strong, evasion-resistant hunting signal, it's frequently something the tool's underlying machinery writes as an unavoidable side effect, not the command line itself: `certutil.exe`'s download verbs cache to `%LOCALAPPDATA%Low\Microsoft\CryptnetUrlCache\` regardless of the operator's chosen output path; `wmic.exe`'s XSL-transform ("SquiblyTwo") path loads the .NET CLR to run embedded script, leaving a `wmic.exe.log` CLR usage-log entry for a process with no legitimate reason to ever touch the CLR; `msbuild.exe`'s inline-task compiler writes a transient source/output temp file under `%LOCALAPPDATA%\Temp\MSBuildTemp\<GUID>` (though, unlike the other two, it's **deleted by default** unless `MSBUILDLOGCODETASKFACTORYOUTPUT=1` is explicitly set — the exception that proves the pattern isn't universal). Where a side-effect artifact like this exists, it tends to survive binary rename and several evasion flags that defeat command-line matching outright.

### No credential switches of their own

`sc.exe` and `setspn.exe` both carry no `-hashes`/`-k`/`/user:`/`/password:` equivalent — neither authenticates anything itself, both simply ride whatever Kerberos/NTLM session or token the calling process already holds (a prior `net use`, an existing domain logon, `runas`). This is a real, easily-missed contrast with `wmic.exe`'s own built-in `/user:`/`/password:` flags and with Impacket-class remote-execution tools elsewhere in this repo — an analyst looking for credential material on an `sc.exe \\target` or `setspn.exe` command line will never find it there; the actual credential-submission event happened on a separate command or logon a moment earlier.

### Installed-capability state as its own artifact — cutting both ways

`wmic.exe` and `setspn.exe` share a install-state angle from opposite directions. `wmic.exe` is a Feature-on-Demand Microsoft has already flagged for a future disabled-by-default flip (per Microsoft's January 2024 deprecated-features update) — a **defender-side hardening lever**: removing the FoD removes the binary. `setspn.exe` ships by default only on Domain Controllers; on any other host it requires the **RSAT: Active Directory Domain Services and Lightweight Directory Services Tools** Feature-on-Demand to be present — an **attacker-side prerequisite**: its mere presence on a non-DC workstation is itself a checkable, somewhat unusual artifact worth flagging during triage. Same underlying Windows capability-management mechanism, opposite practical direction.

### Content over command line

`msbuild.exe`'s entire payload lives inside a project file's XML `<Code>` element, invisible to any hunt scoped to the process command line (`msbuild.exe evil.csproj` reveals nothing). `schtasks.exe /xml` similarly smuggles a task's real action out of the visible command line and into file content. Both push the same conclusion the "thin-client" pattern reinforces from a different angle: for a meaningful share of this folder's abuse surface, **inspecting file/artifact content is where the technique is actually caught, not matching the process that launched it.**

## Sub-Folder Table of Contents

Listed in build order.

| Sub-Folder | Covers | Sharpest finding |
|---|---|---|
| [`ntdsutil/`](ntdsutil/01%20-%20Overview.md) | AD DS/LDS management CLI, repurposed via `ifm` to pull the entire domain's `ntds.dit` + SYSTEM hive using VSS internally — no LSASS access, no service to spot | Has **no network client of its own** — requires code execution already on the DC, the opposite prerequisite from DCSync — and the LOLBAS/Sigma `"ifm"`-substring detection is trivially bypassed via raw `vssadmin create shadow` |
| [`certutil/`](certutil/01%20-%20Overview.md) | CA-administration tool repurposed as a single-process downloader (`-urlcache`/`-verifyctl`/`-URL`) and Base64/hex payload smuggler (`-encode`/`-decode`) | Download verbs write an unavoidable side-effect cache to `%LOCALAPPDATA%Low\Microsoft\CryptnetUrlCache\` regardless of the operator's chosen output path — the strongest, most evasion-resistant signal in this folder |
| [`msbuild/`](msbuild/01%20-%20Overview.md) | Compiles and runs inline C#/VB entirely in-process via `UsingTask`/`CodeTaskFactory` — no compiler child process, no dropped PE binary | The payload lives in the project file's XML content, not the command line; the compiled-source temp artifact is **deleted by default** unless a debug environment variable is explicitly set |
| [`powershell/`](powershell/01%20-%20Overview.md) (`powershell.exe`/`pwsh.exe`) | Not a real LOLBAS entry at all — the maintainer explicitly rejected it as "expected" scripting-engine behavior | Module Logging (4103) and Script Block Logging (4104) are both **off by default** — this tool's entire evidentiary posture rides on logging configuration the operator doesn't control, not on any inherent tell in the binary |
| [`winrar/`](winrar/01%20-%20Overview.md) (`WinRAR.exe`/`Rar.exe`) | Legitimate archiver repurposed for password-protected exfil staging — zero LOLBAS presence, sourced from MITRE T1560.001 instead | `-hp` (not `-p`) is the flag that actually hides the archive's file listing from a DLP glance, and once the process exits the AES-256 archive is cryptographically opaque forever — capturing the command line live is the only chance |
| [`bitsadmin/`](bitsadmin/01%20-%20Overview.md) | Thin CLI client to the BITS service's job lifecycle — download and `SetNotifyCmdLine` execution both happen asynchronously inside the service host | The notify-command payload can fire days after job creation as a child of `svchost.exe -k netsvcs -s BITS`, breaking the standard "hunt what the LOLBIN spawned" playbook |
| [`schtasks/`](schtasks/01%20-%20Overview.md) | Thin CLI client to Task Scheduler — the task's action executes later, as a child of `svchost.exe` hosting the Schedule service, not `schtasks.exe` and not `taskeng.exe` (retired since Windows 10 1511) | Event ID 129 names the exact PID Task Scheduler assigned to a fired task instance; Tarrask's technique of deleting only the `TaskCache\Tree\...\SD` registry value hides a task from `schtasks /query` while the XML file and both event logs survive untouched |
| [`wmic/`](wmic/01%20-%20Overview.md) | WMI CLI client — splits into the `Win32_Process.Create()` family (spawns via `WmiPrvSE.exe`) and the XSL-transform "SquiblyTwo" family (never calls `Create()`, never spawns `WmiPrvSE.exe`) | SquiblyTwo's CLR load leaves a `wmic.exe.log` usage-log entry — a process with no legitimate reason to ever load the .NET CLR |
| [`sc/`](sc/01%20-%20Overview.md) | Thin CLI client to the Service Control Manager (MS-SCMR) — no credential switches of its own | `sc config` on an already-installed service fires **neither** Event 4697 nor 7045 (both install-only) — a pure `binPath=` hijack of an existing, trusted service leaves no native event-log signal at all |
| [`netcat/`](netcat/01%20-%20Overview.md) (netcat/ncat/socat) | Three points on one maturity curve — raw socket pipe, TLS/proxy-enhanced, fully generalized relay — grouped as one page; zero LOLBAS presence for all three | Whichever shell they spawn is always a direct child of the network tool itself — the single most durable process-tree tell in this folder, surviving rename, recompilation, and TLS wrapping |
| [`setspn/`](setspn/01%20-%20Overview.md) | Native SPN read/write CLI — recon role (`-Q`, equivalent to `GetUserSPNs.py`'s enumeration leg) and a write role (`-S`) that most other Kerberoasting tooling can't do | `setspn -S` can **manufacture** an SPN on any writable account that had none, turning a non-roastable account into a roastable one on demand ("Targeted Kerberoasting") — a capability beyond simple enumeration |
| [`regsvr32/`](regsvr32/01%20-%20Overview.md) | COM/ActiveX registration utility repurposed via Squiblydoo (`/i:<URL>` scriptlet loading) for fileless JScript/VBScript execution — no child process, registry bypass | The `/i:` argument shape is unambiguous and survives binary rename; Squiblydoo loads and executes scriptlets (XML-embedded JScript/VBScript) entirely in-process, leaving the payload source code readable in the scriptlet XML if recovered |
| [`mshta/`](mshta/01%20-%20Overview.md) | HTML Application (HTA) host repurposed to download and execute remote `.hta` files containing embedded JScript/VBScript — fileless code execution with full system API access, UAC bypass on legacy OS | The HTA download URL in the command line is **forensically invaluable**; unlike browser JavaScript, HTA script runs outside the sandbox with unrestricted WScript.Shell/ActiveX/file I/O access |
| [`rundll32/`](rundll32/01%20-%20Overview.md) | DLL export invocation utility repurposed to load and call arbitrary DLL functions — direct malicious DLL execution or abuse of legitimate DLL exports (shell.cpl, etc.) | Command-line DLL path/export name is the **strongest signal**; unlike process-spawning techniques, rundll32 DLL execution happens in-process and produces no parent-child evidence unless the DLL's own code spawns a child |
