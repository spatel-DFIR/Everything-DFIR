# Metasploit — msfvenom — Source Evidence

Evidence left on the **build/operator** host — the machine msfvenom was run *from* to generate a payload. msfvenom is a standalone CLI script, not the interactive `msfconsole` — it does **not** write to `~/.msf4/history`, does not touch the Framework's PostgreSQL database, and creates no session/loot records the way `msfconsole`-driven activity does (contrast with `../Meterpreter/03 - Source Evidence.md`, which covers that richer operator-side trail for the handler/session side of an engagement). What msfvenom leaves behind is closer to a generic CLI-tool footprint plus the generated payload file(s) themselves.

## Shell History

| Shell | File | Notes |
|---|---|---|
| bash | `~/.bash_history` | The **single richest artifact** for msfvenom specifically — the full invocation, including `-p` (payload choice reveals platform/arch/staging intent), `LHOST`/`LPORT` (the intended callback destination — directly actionable for blue-team blocking/monitoring), `-x` (reveals which legitimate binary was trojanized, if any), and `-o` (the exact output filename/path to hunt for) |
| zsh | `~/.zsh_history` | Same scope as bash; `EXTENDED_HISTORY` adds a timestamp prefix if enabled, directly useful for timeline building |
| fish | `~/.local/share/fish/fish_history` | YAML-structured with a native `when:` Unix timestamp per command — easiest to correlate without extra tooling if the operator used fish |

Because generation is a single, self-contained command (no interactive session the way `msfconsole` or `psexec.py` produces), the **entire operational intent of a msfvenom invocation is typically visible in one history line** — a higher information density per artifact than most other tools in this module.

A `-l payloads`/`-l encoders`/`-l formats`/`--list-options` line in the same history is lower-value on its own — it's reconnaissance of the tool, not a build — but a cluster of listing commands immediately preceding a real `-p ... -o ...` invocation is a useful behavioral marker of an operator who was still choosing their payload/encoder/format rather than running a pre-scripted, rehearsed command line.

## Generated Payload Files

| Artifact | Notes |
|---|---|
| Output file at the `-o` path | The generated payload itself, sitting on the operator's filesystem — file type/extension matches whatever `-f` format was chosen (`.exe`, `.dll`, `.apk`, `.elf`, `.bin` for raw, etc.) |
| File hash | If the operator kept the file after delivering it (common — reused across multiple targets in an engagement, or kept for the write-up), its hash is a direct, provable link between the build host and whatever executed on the target — correlate against `04 - Target Evidence.md`'s target-side hash artifacts |
| stdout-piped output with no `-o` | If the operator omitted `-o` and piped output directly into another tool (a second msfvenom invocation for chained encoding, or straight into a delivery mechanism), **no standalone file exists on the build host at all** — the shell history line is then the only build-host evidence of that specific payload's content |
| Working-directory remnants | Template files supplied via `-x` remain on disk independent of the payload-generation event — their presence/mtime near a msfvenom invocation timestamp is corroborating evidence for a template-injection scenario |

## Live Process State

```bash
ps aux | grep -i msfvenom
```
msfvenom runs as a short-lived Ruby process — unlike `msfconsole`'s long-lived interactive session, a single generation invocation typically completes in seconds, so live process-state capture only matters if you catch the box mid-generation (large payloads, `--smallest` trying every encoder, or heavy `-i` iteration counts can extend this window). Full argv — including `LHOST`/`LPORT` and any inline path arguments — is visible via `/proc/<pid>/cmdline` to any local user on a shared operator box.

## Framework Installation Artifacts

| Artifact | Command | Notes |
|---|---|---|
| Framework version | Check the installed `metasploit-framework` package/gem version, or `git log` if run from a source checkout | Payload/encoder module content (and therefore exact generated bytes for a given `-p`/`-e` combination) can shift between Framework versions — a hash-based IOC needs to be version-aware |
| Default template files | `msf/data/templates/` under the Framework install | Confirms what a *default* (no `-x`) generated executable's non-payload bytes look like on this specific install — useful for differential analysis against a suspected msfvenom output found elsewhere |
| Custom modules | Any operator-authored payload/encoder modules under `~/.msf4/modules/` (the Framework's user-module directory) | Independent of a specific msfvenom run, but establishes whether the operator had non-stock payload/encoder capability beyond what ships in the base Framework |

## Network Evidence

msfvenom itself makes **no network connections** — generation is entirely local. The only network evidence tied to this build host is indirect:

| Artifact | Notes |
|---|---|
| `LHOST` value in shell history | Reveals the operator's intended callback IP — if this matches the build host's own address, correlate against that host's outbound connectivity/firewall posture for the follow-on handler |
| Handler process, if run from the same box | If `msfconsole`'s `exploit/multi/handler` is later run on this same machine to catch the generated payload, that activity is covered by `../Meterpreter/03 - Source Evidence.md` — a distinct process and artifact set from msfvenom's own generation event |

## OS-Level Audit Trail

```bash
ausearch -x msfvenom 2>/dev/null
ausearch -x ruby 2>/dev/null    # msfvenom runs under the ruby interpreter
```
As with any CLI tool in this module, `auditd` syscall records (if enabled) are the artifact class most likely to survive a shell-history wipe, since they're generated at the kernel level independent of the shell.

## Memory Forensics

If the operator box is imaged as part of an insider-threat or compromised-infrastructure investigation, a still-running (or recently-exited-but-uncollected) msfvenom process's memory can retain the fully-generated payload bytes and any credential-adjacent option values passed on the command line, even past process exit due to Ruby's garbage-collection timing — a full memory capture is the recovery path for a payload that was generated, piped directly into a delivery mechanism, and never written to disk with `-o`.

## Relationship to msfconsole/Handler State

msfvenom's operator-side footprint is **deliberately thin by design** compared to `msfconsole`-driven activity — it's a single-shot generator, not a persistent framework session. If the same engagement also involved standing up a handler (`exploit/multi/handler`) to catch the generated payload's callback, that activity produces the much richer `~/.msf4/history`, database, and loot-directory trail documented in `../Meterpreter/03 - Source Evidence.md` — the two are separate artifact sets on potentially the same host, and a full reconstruction of "what did this operator do" needs both.

## Timeline Correlation Value

A msfvenom shell-history timestamp (or `auditd` execve record) marks the **build** event — this precedes delivery and execution by an unknown, engagement-dependent interval (the file might sit on the operator's disk for hours or days before being delivered). The strongest timeline anchor connecting this host to a specific victim is a **file-hash match**: the same SHA1/SHA256 recovered from this build host's `-o` output (or reconstructed from the exact `-p`/`-e`/`-x`/`-f` combination in shell history) appearing in the target-side filesystem/Prefetch/Amcache artifacts covered in `04 - Target Evidence.md`. Absent a surviving output file, the shell-history command line itself — payload path, `LHOST`/`LPORT`, template path — is the next-best correlator against target-side network-connection and process-creation timestamps.
