# Metasploit — RPC and Daemon (msfrpcd / msfd) — Target Evidence

"Target" means something different on this page than elsewhere in this module. `msfrpcd`/`msfd` are control-plane services — they don't themselves touch an exploited host any differently than `../msfconsole/` does (per-module target footprint lives in `../Exploit Modules/`, `../Auxiliary Modules/`, `../Post-Exploitation Modules/`, `../Meterpreter/`, and `../Metasploit PsExec (exploit-windows-smb-psexec)/`, cross-linked below rather than re-derived). What **is** genuinely unique to this sub-tool is the daemon itself *as* a target: its network-layer fingerprint when something else probes it, and the evidence left when an external party — an attacker who found someone else's forgotten instance, a red team assessing their own exposed infrastructure, or a hunter auditing the estate — connects to or authenticates against a live `msfrpcd`/`msfd`.

## Network/Service Fingerprint

`msfrpcd`/`msgrpc`'s `Rex::Proto::Http::Server` sets an HTTP `Server` response header of exactly **`Rex`** by default (`Rex::Proto::Http::Server::DefaultServer = "Rex"` in the Framework source), unless an operator has explicitly overridden it — a concrete, verifiable string to grep for in any HTTP response from a candidate port:
```bash
curl -sk -o /dev/null -D - https://10.10.10.5:55553/ | grep -i '^Server:'
# Server: Rex
```
Beyond the header, the service accepts `POST` only, to a specific URI (default `/api`), and requires an exact `Content-Type: binary/message-pack` — any other method, path, or content type returns one of a small, distinctive set of error strings (`"Invalid Request Verb"`, `"Invalid Content Type"`, `"Invalid Message Format"`, `"Unknown API Group"`) generated by `Msf::RPC::Service#process`'s `ArgumentError` handling. `health.check` requires no authentication and returns a structured MessagePack response — the single safest, most reliable confirmation that a candidate port is genuinely `msgrpc` and not an unrelated service (see `02 - Hands-On Use Cases.md`'s "Finding an Exposed msfrpcd/msfd Instance").

`msfd`, having no protocol framing at all, fingerprints even more simply: a raw TCP connection to the port either immediately streams a Metasploit ASCII-art banner and an `msf6 >` prompt (unauthenticated console access confirmed), or the connection is refused/reset/hangs with no response (filtered by `-A`/`-D`, or the port isn't `msfd`). There is no intermediate "authentication challenge" state to observe — `msfd` either hands over a shell immediately or it doesn't respond at all.

## Evidence of Probing or Intrusion Against the Daemon

| Signal | Where it's visible | Notes |
|---|---|---|
| Repeated failed `auth.login` attempts | Packet capture (only if `-S`/no-TLS, or TLS intercepted); daemon-host `service.tokens` never populated for failed attempts | Each failed login incurs a deliberate random **0.5–3.5 second delay** before the 401 response (`Msf::RPC::RPC_Auth#rpc_login_noauth`'s anti-bruteforce stall) — a distinctive timing signature: a burst of connections each taking 0.5s+ to get a response, with no successful token issued, is consistent with credential brute-forcing against `msgrpc` specifically, not a generic connection-refused scan |
| A successful `auth.login` followed immediately by broad enumeration calls (`module.exploits`, `db.hosts`, `session.list`, `core.version`) | Packet capture, or daemon-host `service.tokens` gaining a new entry | Consistent with an attacker who's just obtained valid credentials (or exploited a weak/default password) doing initial situational-awareness against the instance before further action |
| A new TCP connection to `msfd`'s port immediately followed by console-command traffic with no prior handshake | Packet capture, `ss -tnp` on the daemon host showing an unexpected established connection | Because there's no auth step, "connection accepted" and "attacker has a shell" are the same event — there's no intermediate state that distinguishes a legitimate connection from a hostile one at the protocol level; source-IP context is the only discriminator |
| `db.import_data`/`db.report_host`/`module.execute` calls originating from an unfamiliar token or source IP | Framework database `sessions`/`hosts`/`creds` tables gaining records with no corresponding operator-side artifact (`../msfconsole/03 - Source Evidence.md`) | The strongest sign that a *different* party than the daemon's legitimate operator is driving it — new database activity with no matching resource script, shell history, or known automation job on the operator's own controller host |

Because RPC-driven activity and console-driven activity write to the **identical** database tables (see `03 - Source Evidence.md`'s Daemon Host: Database and Token Records), distinguishing "our own automation ran this" from "someone else authenticated to our daemon and ran this" depends entirely on correlating database timestamps against the known-good operator/automation host's own artifact trail — there's no database-level flag that marks a record's origin as RPC vs. console vs. a hostile third party.

## What Happens Once a Module Actually Fires

Whether triggered via `console.write "run\r\n"` or `module.execute`, the resulting module/payload execution is **mechanically identical** to firing the same module from an interactive `msfconsole` session — the RPC layer changes nothing about what lands on the actually-exploited target:

- **Meterpreter payloads** — reflective in-memory loading, TLV protocol, extension loading, and the full Sysmon/Event-Log/memory-forensics signature set are covered in `../Meterpreter/04 - Target Evidence.md`. Not re-derived here.
- **Exploit-delivered payloads** — the delivery mechanism's own filesystem/registry/event-log footprint (an EternalBlue-class kernel exploit, a service-based push like `../Metasploit PsExec (exploit-windows-smb-psexec)/04 - Target Evidence.md`) is documented on that module category's own page.
- **`multi/handler` catch traffic** — same network-direction reasoning `../msfconsole/04 - Target Evidence.md` documents (target-initiated outbound connection for `reverse_tcp`/`reverse_http(s)`, operator-initiated for `bind_tcp`) applies unchanged whether the handler was configured via `console.write` or a direct `job`/`module` RPC call.

## Building a Timeline

Two timelines matter here, and they can be built independently: **(1) the daemon-as-target timeline** — port reachable (network-baseline/scan data) → first connection from an unfamiliar source (`ss`/packet capture) → `auth.login` success or `msfd` shell handed over → subsequent RPC calls or console commands (packet capture if unencrypted, or database-record creation timestamps if not) — this is the timeline for investigating whether *the daemon itself* was compromised or abused by an unauthorized party. **(2) the downstream-exploitation timeline** — whatever module/payload the daemon was used to drive, correlated against the target-side timestamps documented on that module category's own Target Evidence page, exactly the same correlation principle `../msfconsole/04 - Target Evidence.md`'s Building a Timeline section uses. The connecting link between the two is the database `sessions.opened_at` record (`03 - Source Evidence.md`) and — if TLS wasn't in use — the packet-level `auth.login`/`module.execute`/`console.write` timestamps that show exactly which authenticated party initiated the module run that produced timeline (2)'s target-side evidence.
