# Impacket — secretsdump.py — Target Evidence

`secretsdump.py`'s three extraction paths (`01 - Overview.md`) leave **three structurally different** target-side evidence trails — there is no single "here's what secretsdump.py looks like on the target" answer. This file is organized by path for exactly that reason; don't assume evidence from one section applies to a run that used a different mode.

## Path 1 — Remote Registry (SAM / LSA Secrets / Cached Creds)

### Filesystem

| Artifact | Detail |
|---|---|
| Temporary hive-copy file | **`%SystemRoot%\Temp\<8-random-ASCII-letters>.tmp`** — a full copy of the live `SAM` and/or `SECURITY` hive, written by `BaseRegSaveKey` (MS-RRP), one file per hive requested. Deleted after being read back over SMB, but the create→read→delete cycle happens in a **short, tight window** — recoverable from `$MFT`/USN Journal analysis even after deletion, and via the same `$MFT`/journal even if the delete step failed (network interruption, EDR blocking the delete) |
| Prefetch / Amcache / ShimCache | **None generated by this path** — no new executable runs on the target; only RPC calls against an already-running service process (`svchost.exe` hosting `RemoteRegistry`) |

### Registry

| Key | Detail |
|---|---|
| `HKLM\SYSTEM\CurrentControlSet\Services\RemoteRegistry\Start` | **Not modified** in the common case (service already enabled, just stopped) — only touched if the service was found **disabled** (`Start=4`), in which case `secretsdump.py` sets it to demand-start (`Start=3`) before starting it, then restores it to `4` on cleanup. **A host where this key shows an unexpected value, or where its LastWrite time doesn't match a legitimate change-management window, is itself worth investigating** |
| Boot-key material — `HKLM\SYSTEM\CurrentControlSet\Control\Lsa\{JD,Skew1,GBG,Data}` | Read-only access, pre-existing configuration, not evidence generated by the run — same as the equivalent note in `Mimikatz/lsadump (DCSync)/04 - Target Evidence.md`'s "sam/secrets/cache" section |

### Windows Event Logs

| Log | Event ID | Signal |
|---|---|---|
| **System** | **7036** | Service Control Manager start notification for `RemoteRegistry` — **this fires on ordinary Remote Registry usage too** (Group Policy management tools, some backup/inventory software), so it's a necessary-but-not-sufficient signal on its own. **There is no equivalent to psexec's Event 7045 here** — no new service is created, so there's nothing to "install" |
| Security | 4624 (Logon Type 3) | Inbound SMB authentication — check `AuthenticationPackageName` for the auth variant used |
| Security | 5140 / 5145 | `ADMIN$` share access, including the specific file read of the temp `.tmp` hive copy — the exact filename appears here if object-access auditing (5145) is enabled |
| Security | 4656 / 4663 | Object access to the `RemoteRegistry` service's SCM object and/or the `HKLM\SAM`/`HKLM\SECURITY` registry keys **only if a SACL happens to be configured on them** — uncommon by default, same rarity caveat that applies throughout this repo's registry-based hunts |
| Security | 4688 | Process creation — **not directly relevant**, since this path executes no new process on the target; useful only if the operator pivots into command execution from the same session via a different tool |

### Sysmon (if deployed)

| Event ID | Signal |
|---|---|
| 11 (File Create) | The temp hive-copy file(s) landing in `%SystemRoot%\Temp\` — matches an 8-random-letter `.tmp` filename pattern, the **strongest Sysmon-level signal for this path** |
| 23 (File Delete) — if `FileDeleteLogged`/`FileDelete` is configured | The corresponding cleanup delete of the same temp file, closing the create→delete pair |
| 3 (Network Connection) | Inbound SMB (445) from the operator's source, if the DC/host's own Sysmon config logs inbound (uncommon default tuning) |
| 18 (Pipe Connected) | Connection to `\PIPE\winreg`, `\PIPE\svcctl` — less commonly hunted on than the psexec-family's `RemCom_*` pipes since `winreg`/`svcctl` traffic has many legitimate sources, but a useful corroborating signal alongside the File-Create event above |

### Network-Layer Evidence

| Source | What It Shows |
|---|---|
| Zeek `dce_rpc.log` | `winreg` and `svcctl` operations (`BaseRegSaveKey`, `OpenSCManagerW`, etc.) visible as named DCE/RPC operations, independent of host-based logging |
| Zeek `smb_files.log` | The temp `.tmp` file write, then read, then delete against `ADMIN$` — visible with filename and size even without endpoint logging |

### Endpoint Security Product Signatures

Most modern EDR products carry **behavioral** detection for "remote registry hive save followed by SMB exfil of the saved file" as a known credential-dumping pattern (this is the same technique family as `pwdump`/`fgdump`, decades old) — this is typically a heuristic/behavioral rule rather than a static file signature, since no attacker file is ever written. A host with EDR that shows no alert despite this pattern is worth checking for exclusions/tamper rather than assuming the technique is undetectable.

## Path 2 — DRSUAPI (DCSync-Equivalent NTDS Pull)

`secretsdump.py -just-dc`/`-just-dc-ntlm`/`-just-dc-user`/`-ldapfilter` speak the **identical MS-DRSR protocol call** (`IDL_DRSGetNCChanges`) that Mimikatz's `lsadump::dcsync` does — this is not a similar technique, it is the **same RPC operation from a different client implementation**. Every byte of the target-side evidence trail — the complete absence of filesystem/registry artifacts, the Event 4662 signature and its non-default audit-policy/SACL prerequisites, the network-layer `drsuapi` signal, the Microsoft Defender for Identity alert 2006 behavior, and the "the only distinguishing fact is *who* asked, never *how*" framing — is covered in full in **`Mimikatz/lsadump (DCSync)/04 - Target Evidence.md`**. Read that file for this path; it is not re-derived here.

**What's specific to `secretsdump.py`'s own implementation, beyond what that note covers:**

- **`-resumefile`** leaves no target-side artifact of its own — the checkpoint state lives entirely on the operator's machine (`03 - Source Evidence.md`). A resumed pull simply resumes the same `IDL_DRSGetNCChanges` round-trip pattern from wherever the USN watermark left off; from the DC's perspective it's indistinguishable from a second, later replication session by the same principal.
- **`-just-dc-user`/`-ldapfilter`** narrow which objects are requested but generate the **same event structure** as a full pull, just fewer/one `IDL_DRSGetNCChanges` calls — the volumetric discriminator described in `Mimikatz/lsadump (DCSync)/04 - Target Evidence.md`'s "Building a Timeline" section (many 4662 hits from one `SubjectUserSid` in a tight window = full-domain pull) applies identically to distinguishing a `secretsdump.py -just-dc` from a `-just-dc-user` run.
- **`-trust-keys`/`-just-trust-keys`** replicate trusted-domain-object (TDO) secrets specifically — these appear in the same Event 4662 stream as regular account replication, since TDOs are themselves AD objects subject to the same extended-rights check; there is no separately-cataloged event signature for "trust secrets specifically" versus "account secrets."

## Path 2 — VSS / WMI-Shadow-Snapshot Fallback

`-use-vss` and `-use-remoteSSWMI` are a **fundamentally different, older, and noisier** technique than DRSUAPI mode — despite both being reachable via the same `-just-dc`-adjacent NTDS-extraction goal, they require code-execution-equivalent access on the DC and leave a correspondingly heavier trail.

### `-use-vss` (default exec method: `smbexec`)

| Artifact | Detail |
|---|---|
| Process creation | `vssadmin.exe list shadows` and (if no usable existing shadow) `vssadmin.exe create shadow /For=<drive>`, launched via whichever `-exec-method` was selected (`smbexec` by default — see `Impacket/smbexec/`'s own service-based execution artifacts for that leg's signature; `wmiexec`/`mmcexec` leave DCOM/WMI-based execution artifacts instead) |
| Filesystem | `%SYSTEMROOT%\Temp\<8-random-letters>.tmp` — the copied `ntds.dit` extracted from the shadow snapshot, same random-naming convention as Path 1's hive-copy temp files, plus a `\Temp\__output` relay file used to read back command output from the exec method |
| Security Event 8222 | "The VSS service is shutting down due to idle timeout" / VSS shadow-copy creation activity — check for a `vssadmin create shadow` event correlating with the pull window |
| Sysmon 1 (Process Create) | `vssadmin.exe` launching with `list shadows`/`create shadow` arguments — a distinctive, rarely-legitimate-outside-backup-software command line on a Domain Controller specifically |
| Sysmon 11 (File Create) | The `ntds.dit` copy landing in `%SYSTEMROOT%\Temp\` — **`ntds.dit` sitting anywhere outside `%SystemRoot%\NTDS\` is itself a strong anomaly** on a DC |
| Cleanup | The created shadow copy is deleted afterward (`vssadmin delete shadows /shadow="{<id>}"`) **only if `secretsdump.py` itself created it** — if an existing shadow was reused, nothing is torn down, meaning a stale shadow copy surviving on a DC can itself be a residual artifact worth checking (`vssadmin list shadows`) |

### `-use-remoteSSWMI` (DCOM/WMI shadow snapshot, no `vssadmin.exe`)

| Artifact | Detail |
|---|---|
| Process creation | **None for the snapshot step** — `Win32_ShadowCopy.Create()` is invoked via DCOM/WMI, not a spawned `vssadmin.exe` process. This specifically evades any hunt keyed on `vssadmin.exe` command-line arguments |
| WMI-Activity operational log | `Microsoft-Windows-WMI-Activity/Operational` records the `Win32_ShadowCopy` class method invocation — this is the **primary signal** for this variant, replacing the process-creation signal the plain `vssadmin`-based method provides |
| DCOM/RPC network layer | An `IWbemLevel1Login`/`IWbemServices` DCOM session from the operator's source — visible via Zeek's DCE-RPC analyzer or NetFlow the same way `wmiexec.py`'s own WMI-based execution is (see `Impacket/wmiexec/04 - Target Evidence.md` for the general WMI-over-DCOM network signature, not re-derived here) |
| Filesystem | Same `%SYSTEMROOT%\Temp\<random>.tmp` copy-out pattern as the `vssadmin`-based method, once the snapshot exists |

## Path 3 — Offline / Local Mode

> 🔴 **This mode leaves no target-side evidence at all — say so plainly rather than padding this section.** `secretsdump.py LOCAL`/`-sam`/`-security`/`-system`/`-ntds` parses files that are **already on the analysis machine** when the tool runs. There is no network connection, no SMB session, no RPC call, no registry access, no process execution against a remote target — nothing for a Windows event log, Sysmon, or a network sensor on the *original* target host to ever observe, because `secretsdump.py`'s own execution never touches that host.

**The evidence that matters for this path belongs to a different tool entirely — whatever copied the `SYSTEM`/`SAM`/`SECURITY`/`ntds.dit` files off the original target in the first place.** Depending on how that happened, look at:

- A local `vssadmin create shadow` + manual file copy off the resulting snapshot — Event 8222, Sysmon 1 for `vssadmin.exe`, Sysmon 11 for the copied files, same as this file's own VSS-fallback section above, but originating from **interactive/local** execution on the source host rather than a remote RPC-driven exec method
- `ntdsutil.exe ifm` ("Install From Media") — a legitimate AD-administration command frequently abused to produce a clean, portable `ntds.dit` + registry-hive export bundle in one step; its own process-creation and file-output footprint is a distinct artifact set, out of scope for this note (see the planned `LOLBins/ntdsutil/` sub-folder)
- A backup-software restore, a mounted VHD/disk image, or physical media — each with its own, unrelated evidence trail
- Simple `reg save HKLM\SAM` / `reg save HKLM\SYSTEM` / `reg save HKLM\SECURITY` run locally and interactively on the source host (rather than via `secretsdump.py`'s own remote winreg path) — generates local process-creation evidence for `reg.exe` itself, again a different tool's signature

**Practical implication for an investigation:** if a `secretsdump.py`-produced `.sam`/`.secrets`/`.ntds` output file turns up on a suspected operator's machine (`03 - Source Evidence.md`) but the corresponding target DC/host shows **no** Path 1 or Path 2 evidence whatsoever, offline/local mode against exfiltrated hive files is the most likely explanation — pivot the investigation toward **how those files left the original host**, not toward looking harder for a `secretsdump.py`-specific signature that was never going to exist.

## Building a Timeline

Because the three paths are evidentially disjoint, a timeline has to be built **per path**, then cross-referenced against `03 - Source Evidence.md`'s operator-side artifacts:

- **Path 1:** `4624 (Type 3 logon) → svcctl RemoteRegistry status-check/start → winreg BaseRegSaveKey → Sysmon 11 (temp .tmp file create) → SMB file read (5145) → Sysmon 23/file delete → (RemoteRegistry restored to prior state)` — typically seconds to low minutes end-to-end.
- **Path 2 (DRSUAPI):** see `Mimikatz/lsadump (DCSync)/04 - Target Evidence.md`'s timeline — `[DC-locator DNS] → [RPC bind, TCP 135 + dynamic port] → [IDL_DRSBind] → [IDL_DRSGetNCChanges → Security 4662, if audited] → [reply parsed on operator's machine]`. A `-resumefile`-driven multi-session pull shows this sequence **repeating across multiple, possibly widely-separated time windows** from the same `SubjectUserSid` — don't assume a single contiguous session.
- **Path 2 (VSS fallback):** `[exec-method's own execution artifacts — see the relevant sibling Impacket sub-tool's 04] → vssadmin list/create shadow (Event 8222, Sysmon 1) → file copy to %SYSTEMROOT%\Temp\ (Sysmon 11) → SMB read-back → shadow deletion (if created) → temp file cleanup`.
- **Path 3:** **no target-host timeline exists** — only the operator-side output-file timestamp (`03 - Source Evidence.md`) and whatever separate tool's trail explains how the source hive files were originally exfiltrated.
