# Immunity Debugger — Source Evidence

Evidence of debugging activity leaves traces on the **attacking/source machine** where Immunity Debugger itself is running.

## Process & Execution Artifacts

### Debugger Process Creation

**Process Tree:**
```
explorer.exe (or cmd.exe)
  └─ Debugger64.exe (or Debugger.exe for 32-bit)
       └─ vulnerable.exe (debuggee, child process with DEBUG_PROCESS flag)
            └─ Any child processes spawned by the debuggee (grandchildren of Debugger64.exe)
```

**Parent Process Anomaly:**
- Immunity Debugger explicitly launches the debuggee as a child process via the Windows Debug API.
- A legitimate application rarely spawns another copy of itself or arbitrary binaries.
- **Detection Signal:** `Debugger64.exe` → `arbitrary-binary.exe` parent-child relationship is suspicious on a user's machine (would be expected on a malware analyst's or exploit-dev's workstation, but suspicious in an enterprise endpoint).

### Process Handle & Privilege Context

- Immunity Debugger typically runs in the **user's own security context** (same user token that launched it).
- However, debugging certain processes (especially services or SYSTEM-owned processes) requires **elevated privileges** (Administrator/SYSTEM).
- **Command Line:** `Debugger64.exe <binary>` or `Debugger64.exe -p <PID>`.
- **Privilege Escalation Signal:** If a non-admin user runs Immunity Debugger and later debugs a SYSTEM process, a UAC prompt or privilege escalation indicator would appear (though the escalation itself leaves audit trails on the target, not the source).

## Shell History & Command Artifacts

### Command Prompt / PowerShell History

**PowerShell History (typical location):**
- File: `%APPDATA%\Microsoft\Windows\PowerShell\PSReadline\ConsoleHost_history.txt`
- If PowerShell was used to launch Immunity Debugger:
  ```powershell
  C:\path\to\Debugger64.exe C:\vulnerable.exe
  ```
  This command is logged in the PowerShell history.

**cmd.exe History:**
- Not persisted by default (unless `doskey /history` is manually run in a batch script).

**Bash History (if running on Windows with WSL or Git Bash):**
- `.bash_history` in the user's home directory.

### Recent Files & MRU

- **Windows Recent Files:** If Immunity Debugger was launched via Windows Explorer or the Start menu, the binary path may appear in the MRU (Most Recently Used) registry key.
- **File:** `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RecentDocs`
- **Immunity Binary Path:** If `Debugger64.exe` was opened from a non-standard location, the path might be cached.
- **Debugger Project Files (.udd):** Immunity Debugger can save project files (`.udd` extension) with metadata about debugging sessions, including target binary path and breakpoints. These files persist in whatever folder the operator saved them to.

## Network Artifacts

### Local Network Connections

**Immunity Debugger & Local Debugging:**
- Immunity Debugger communicates with the debuggee **only via the local Windows Debug API**, not via network protocols.
- No outbound network traffic is generated by Immunity Debugger itself during normal debugging.

### Remote Debugging (If Used)

- Immunity Debugger does not support remote debugging via its own protocol.
- However, if an operator uses Immunity Debugger to develop an exploit that uses a **C2 payload** (e.g., Metasploit meterpreter or Cobalt Strike beacon), the **C2 traffic** is generated by the debuggee, not by Immunity Debugger.
- **Network Evidence:** Only the debuggee's network connections are visible; Immunity Debugger itself leaves no network signature.

## Cached Credentials & Secrets

### No Credential Caching by Immunity Debugger

Immunity Debugger does not cache or store credentials (usernames, passwords, tokens) from the debugged applications. However:

**Debugged Application's Credentials:**
- If the debugged binary is a vulnerable service or application that handles credentials, inspecting the **debuggee's memory** (via Immunity's Read Memory function) may expose those credentials in plaintext or hashed form.
- **Evidence:** Memory dumps or crash dumps created during debugging may contain sensitive data.

**PyCommand Script Artifacts:**
- If an operator writes a PyCommand script (Python code in Immunity) that extracts credentials or sensitive data from the debugged process, that script may be logged or cached.
- **File:** Custom PyCommand scripts are typically stored in `%APPDATA%\Roaming\Immunity Inc\Debugger\mona\` or a custom plugins folder.

## Filesystem Artifacts

### Immunity Debugger Installation

**Binary Location:**
- Typical: `C:\Program Files\Immunity Inc\Debugger\` (official install) or a custom path if installed elsewhere.
- **Detection Signal:** Finding `Debugger64.exe` outside its standard install path (e.g., in temp directory or a staging folder) is suspicious.

### Project Files (.udd)

**Format:** Immunity Debugger saves debugging sessions as `.udd` (Immunity Debugger Data) files.
- **Location:** Wherever the operator saves them (could be Desktop, Documents, a temporary folder, or a specific project directory).
- **Content:** .udd files contain:
  - Target binary path (full path to the debuggee).
  - Breakpoint locations and metadata.
  - Analyze/bookmark annotations.
  - Memory snapshot (optional, if saved).

**Example .udd File Timeline:**
- Created when: operator runs Immunity and opens a binary, then File → Save Session.
- Modified when: operator continues debugging (breakpoints added/removed, annotations added).
- **Forensic Value:** A .udd file created 2 hours before an exploit is deployed suggests the operator was preparing/testing the exploit locally.

### Minidump Files (.dmp)

**Format:** Windows minidump files created during crash analysis.
- **Location:** Saved manually by operator via File → Save Crash Dump, or automatically if Immunity Debugger is configured for auto-save.
- **Typical Paths:** Desktop, Documents, or a project folder.
- **Content:** Full process memory snapshot + exception context (register state, stack trace).
- **Forensic Value:** A recent .dmp file with a stack frame pointing to exploit-development code (e.g., `strcpy` overflow, ROP chain setup) indicates active exploit development.

### Debugger Plugin Folder

**mona.py Plugin Location:**
- Installed to: `%APPDATA%\Immunity Inc\Debugger\PyCommands\` or `plugins/` subdirectory.
- **Detection Signal:** Presence of `mona.py` in the Immunity plugins folder indicates the operator has set up advanced crash analysis capabilities.

## OS-Level Audit Trail

### Event Log Entries (Windows Security Event Log)

Immunity Debugger's own process creation is logged:
- **Event ID 1 (Sysmon)** or **Event ID 4688 (Windows Security Log):** Process creation event for `Debugger64.exe`.
  - Parent: `explorer.exe` (if launched from Start Menu) or `cmd.exe`/`powershell.exe` (if launched from command line).
  - Command Line: `Debugger64.exe <target-binary>` or `Debugger64.exe -p <PID>`.
  - User: The logged-in user's SID.

### Debug API Calls

- Windows does not generate security event-log entries for Debug API calls (`DebugActiveProcess`, `SetThreadContext`, etc.) by default.
- No UAC prompt is required for debugging unprivileged processes.
- **However:** Debugging a SYSTEM or administrator-owned process triggers a UAC prompt (if UAC is enabled), which IS logged.

### Debuggee Process Termination

- When Immunity Debugger exits or detaches, the debuggee process typically also terminates (unless detached explicitly).
- **Event ID 4689 (Windows Security Log):** Process termination event for the debuggee.
  - This event alone is not suspicious (processes exit normally), but if correlated with a recent `Debugger64.exe` creation, it suggests debugging activity.

## Memory & Volatile State

### RAM Artifacts

**Active Debugging Session:**
- While Immunity Debugger is running, its own memory contains:
  - The target binary's full memory image (copied from the debuggee process).
  - Breakpoint metadata, instruction patches (0xCC bytes), register state snapshots.
  - Python script state (if PyCommand scripts are in use).

**Memory Forensics:**
- A live memory dump (created while Immunity Debugger is actively debugging) captured via tools like Belkasoft Evidence Center or Volatility would show:
  - `Debugger64.exe` process memory with embedded copies of the debuggee's binary.
  - Breakpoint addresses and handler pointers.
  - PyCommand state (if Python code was executing).

**Indicator:** Presence of `Debugger64.exe` with unusually large memory footprint (because it contains a full copy of the debuggee process's memory).

## Timeline Correlation with Target-Side Evidence

### Exploit Development Workflow Timeline

**Typical Operator Activity:**

| Time | Source Activity | Target Activity | Correlation Signal |
|---|---|---|---|
| T-2h | Debugger64.exe launched locally, crash input generated | — | .udd file created; Python script in PyCommands folder modified |
| T-1.5h | mona.py !analyze run; pattern offset calculated; PoC shellcode injected | — | mona.py command output logged (if PyCommand logging is enabled) |
| T-1h | Exploit binary compiled/staged locally; File → Save Session | — | .udd file timestamp updates; exploit.exe file created |
| T-30m | Exploit tested locally (multiple Debugger launches/crashes) | — | Repeated Debugger64.exe process creation/termination events |
| T0 | Exploit.exe launched (no longer in debugger) | Crash/code execution observed on target | Process creation: exploit.exe (not under Debugger64.exe) |
| T+5m | — | Post-exploitation activity begins (new accounts, lateral movement, etc.) | — |

**Timeline Correlation Analysis:**
- If target shows evidence of exploitation at time T0, and source machine shows a cluster of Immunity Debugger activities in the T-2h to T0 window, this strongly suggests the exploit was developed locally and then deployed.

## Summary: Detecting Immunity Debugger Activity on Source Machine

| Artifact | Location | Signal |
|---|---|---|
| **Debugger64.exe binary** | Default: `C:\Program Files\Immunity Inc\Debugger\` | Process creation events, parent-child relationships |
| **.udd project files** | User-defined (Desktop, Documents, or project folder) | File timestamps, breakpoint/binary metadata |
| **.dmp crash dumps** | User-defined, typically temp/project folder | Minidump format, exception context, memory snapshot |
| **mona.py plugin** | `%APPDATA%\Immunity Inc\Debugger\PyCommands\` | File presence, recent modification timestamp |
| **PyCommand scripts** | `%APPDATA%\Immunity Inc\Debugger\` or custom plugins folder | Custom Python code for crash analysis/exploit crafting |
| **PowerShell history** | `%APPDATA%\Microsoft\Windows\PowerShell\PSReadline\ConsoleHost_history.txt` | Command line: `Debugger64.exe <binary>` |
| **Event Log: Process Creation** | Event ID 1 (Sysmon), Event ID 4688 (Security) | `Debugger64.exe` launch, parent-child with debuggee, timestamp |
| **Event Log: Process Termination** | Event ID 5 (Sysmon), Event ID 4689 (Security) | Debuggee termination (often correlates with Debugger exit) |
| **RAM (live memory dump)** | Volatile memory | `Debugger64.exe` with large memory footprint containing debuggee image |
| **Recent Files MRU** | `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RecentDocs` | Debugger64.exe or debuggee binary path in MRU list |
