# PsExec (Sysinternals) — Target Evidence

Evidence left on the **target/destination** host. This is the deep end of the note — genuine PsExec's evidence trail spans filesystem, registry, three logging subsystems (Security, System, Sysmon), and the network layer, and several of the artifacts here have no equivalent in Impacket's `psexec.py` at all.

## Filesystem

| Artifact | Detail |
|---|---|
| Dropped service binary | `C:\Windows\System32\PSEXESVC.exe` by default — **note the `System32` subfolder**. `ADMIN$` maps to `C:\Windows\`, and PsExec specifically writes one level deeper than that root. This is a real, checkable difference from Impacket's `psexec.py`, which drops its RemCom-derived binary directly into `C:\Windows\` root — see the comparison at the bottom of this file. Name changes with `-r` (per `01`'s finding, the dropped filename shifts together with the service-name override) |
| Second dropped file (if `-c` used) | A **separate**, operator-chosen local file uploaded and executed as the actual payload — see `02 - Hands-On Use Cases.md`. Two independent files, two independent hashes, potentially different locations if a custom `-w` working directory was also used |
| File hash | The **default, unmodified** `PSEXESVC.exe` has a stable hash tied to the specific PsExec/`PSTools.zip` release in use — a real, if version-pinned, hash-matching opportunity. This is defeated entirely if the operator supplied a custom-built or patched service binary (documented in real incidents as the `FRAMEPKG.EXE` case), the direct PsExec analog of Impacket's own `-file` evasion caveat |
| Prefetch | `C:\Windows\Prefetch\PSEXESVC.EXE-<HASH>.pf` (or the renamed equivalent) — created if the binary fully executes and Prefetch tracing is enabled. See `Windows/06 - Evidence of Program Execution/Prefetch.md` |
| Amcache / ShimCache | Both record the dropped binary's path and hash; Amcache additionally a compile timestamp, which — for the default unmodified binary — is a fixed value tied to the `PSTools.zip` build, not a genuine "first seen in the wild" indicator. See `Windows/06 - Evidence of Program Execution/Amcache.md` and `.../ShimCache (AppCompatCache).md` |
| Zone.Identifier / MOTW | **Absent.** Delivery is over SMB, not web/email/an archive extraction, so no Mark-of-the-Web alternate data stream is ever written — a fresh, MOTW-less binary sitting in `System32` is itself a subtle tell |

## The .key File — the Tool's Strongest Single Artifact

Starting with **PsExec v2.30 (early 2021)**, every single invocation — regardless of `-r`, `-s`, `-accepteula`, or any other flag — drops a small file on the target:

```
C:\Windows\PSEXEC-<source-hostname>-<8-hex-characters>.key
```

The `<source-hostname>` segment is the **NetBIOS/computer name of the machine PsExec was launched from** — this is direct, first-party source attribution written by the tool itself, with no equivalent artifact anywhere in Impacket's `psexec.py`. Multiple independent write-ups (a dedicated technical breakdown of the artifact, corroborated by a USN-Journal-focused forensics piece) confirm:

- It's written on **every** invocation against a given target, not conditionally.
- Its creation is recorded in the **USN Journal** (`$J`, parseable with tools like `MFTECmd.exe`) and in **Sysmon Event ID 11** (File Create) if deployed — meaning it can be recovered even after the file itself is later deleted, as long as the journal/log entry hasn't rolled off.
- `PSEXESVC.exe`'s own **Prefetch** file, once it exists, references the `.key` file(s) it accessed — giving a second, independent recovery path via `PECmd.exe`-style Prefetch parsing.
- **Nothing about `-r` touches this file's naming pattern or its unconditional creation** — it's generated by logic entirely separate from the service-name/pipe-name mechanism `01`'s red-flag callout centers on.

The one honest caveat: this artifact requires **PsExec v2.30 or later** on the operator's side. An older PsExec build (still in circulation on many admin workstations that haven't been updated) will not produce it — verify the operator's tooling generation is unknown before relying on its absence as evidence PsExec *wasn't* used.

## Registry

| Key | Detail |
|---|---|
| `HKLM\SYSTEM\CurrentControlSet\Services\PSEXESVC` (or the `-r`-renamed equivalent) | Newly created service key. `ImagePath` points at the dropped binary; `Start=3` (`SERVICE_DEMAND_START` — it never auto-starts on boot, only runs because `psexec.exe` explicitly started it once) |
| Service lifecycle anomaly | A service created, started once, and deleted within seconds-to-minutes is itself anomalous — legitimate installers create services that persist with normal start-type conventions, not a tight create-start-stop-delete cycle |
| `EulaAccepted` — **not present on the target** | This artifact lives on the **operator's source host**, not here — a common mix-up worth correcting explicitly. See `03 - Source Evidence.md` |

## Windows Event Logs

| Log | Event ID | Signal |
|---|---|---|
| **System** | **7045** | "A service was installed in the system" — captures `ServiceName` (`PSEXESVC` or the `-r` override), `ImagePath`, `ServiceType`, `StartType`, `Account`. The single highest-value native event-log signal for this tool, same as it is for the general remote-service primitive in `Windows/10 - Persistence Mechanisms/Services.md` |
| System | 7036 | Service Control Manager start/stop notification, moments after 7045, then again on the stop half of cleanup |
| Security | 4624 (Logon Type 3 — Network, or **Type 2** if `-u` triggered explicit-credential logon in some configurations) | Inbound SMB authentication from the operator's source IP; check `AuthenticationPackageName` for `NTLM` vs `Kerberos` |
| Security | 4672 | Special privileges assigned to the new logon — confirms an admin-equivalent token |
| Security | 5140 | Network share object accessed — `ADMIN$` from the operator's source IP |
| Security | 5145 | Detailed share-file access (only with the more granular object-access auditing subcategory enabled) — shows the exact write into `System32\PSEXESVC.exe` |
| Security | 4697 | Security-log twin of System 7045 — only present if "Audit Security System Extension" is explicitly enabled (far less commonly on than 7045 by default) |
| Security | 4688 | Process creation — if command-line auditing is enabled, shows `PSEXESVC.exe` launching, then the requested command, as a process chain |
| Security | 4689 | Process termination — the tail end of cleanup |

## Sysmon (if deployed)

| Event ID | Signal |
|---|---|
| 1 (Process Create) | `PSEXESVC.exe` launching under `services.exe`, then the requested command as its child — **check the `User` field**: per `01`'s finding, this shows the impersonated caller by default, or `NT AUTHORITY\SYSTEM` only if `-s` was used, unlike Impacket's `psexec.py`, which is always SYSTEM |
| 3 (Network Connect) | Inbound TCP 445 connection from the operator |
| 11 (File Create) | The `PSEXESVC.exe` write into `System32\`, a **second** File Create for the `.key` file (per above — this event is what makes the `.key` artifact recoverable even after deletion), and a third if `-c` uploaded a separate payload |
| 13 (Registry Value Set) | Service key creation under `CurrentControlSet\Services\` |
| **17 / 18 (Pipe Created / Pipe Connected)** | `\\.\pipe\psexecsvc` handshake pipe plus the per-invocation `PSEXESVC-<hostname>-<pid>-std{in,out,err}` pipes — see [Named Pipe Detail](#named-pipe-detail) below |

## Named Pipe Detail

| Pipe | Purpose | Survives `-r`? |
|---|---|---|
| `\\.\pipe\psexecsvc` | Initial handshake — client and server exchange version numbers before anything runs | **No** — the prefix is read from the service binary's own on-disk filename, which shifts with `-r` per `01`'s finding |
| `PSEXESVC-<hostname>-<pid>-stdin` | Per-invocation input relay | Same — becomes `<r-name>-<hostname>-<pid>-stdin` |
| `PSEXESVC-<hostname>-<pid>-stdout` | Per-invocation output relay | Same |
| `PSEXESVC-<hostname>-<pid>-stderr` | Per-invocation error output relay | Same |

**This is the opposite of the RemCom pipe family Impacket's `psexec.py` uses** (`\PIPE\RemCom_communicaton`, hardcoded regardless of the dropped binary's filename — see `../Impacket/psexec/04 - Target Evidence.md`). A hunt built to catch Impacket's psexec.py by pipe name alone will not catch a renamed genuine PsExec session, and vice versa — treat the two pipe families as entirely independent signatures, not interchangeable.

## Network-Layer Evidence

| Source | What It Shows |
|---|---|
| Zeek `smb_files.log` / `smb_mapping.log` | Tree-connect to `ADMIN$`, followed by a file write matching `PSEXESVC.exe` (or its `-r`-renamed equivalent) plus the `.key` file, both under `System32\`/`Windows\` respectively |
| Zeek `dce_rpc.log` | The `svcctl` operations sequence — `OpenSCManagerW`/`CreateServiceW`/`StartServiceW` — visible as named DCE/RPC operations against `\PIPE\svcctl`, independent of host-based logging entirely |
| NetFlow / firewall logs | A short burst of TCP 445 traffic from one internal host to another — often the first indicator available where endpoint logging is thin, especially valuable for the fleet-wide scenario in `02 - Hands-On Use Cases.md`, where many hosts show the identical pattern in a tight window |

## Endpoint Security Product Signatures

Because genuine PsExec is a common, legitimate admin tool, most mainstream AV/EDR products treat it as a **known-good, allowlisted binary by default** rather than a hacktool signature — the opposite posture from Impacket's `psexec.py`, whose bundled RemCom-derived binary is widely signature-matched (per `../Impacket/psexec/04 - Target Evidence.md`). Some products flag PsExec heuristically as a "remote admin"-class tool regardless (Microsoft's own PsExec documentation explicitly notes some AV scanners report this, calling it a known false-positive-adjacent behavior, not evidence of infection). **The practical consequence:** an environment relying on EDR/AV alone to flag "hacktool" activity may see nothing at all for a well-executed genuine PsExec session — the event-log and named-pipe evidence above is the primary detection surface, not the endpoint product's own verdict.

## Memory Forensics

`PSEXESVC.exe` runs as a distinct, short-lived process under `services.exe` — if memory is captured while it's still resident, standard process-listing/injection-detection tooling (see `Windows/17 - Memory Forensics/Memory Analysis (Processes, Injection, Rootkits).md`) shows it as a normal, non-injected, un-hidden process with no rootkit behavior of its own. Its forensic value in memory is mainly recovering the exact command relayed through the named-pipe channel, which may not otherwise be captured if 4688 process-creation auditing wasn't enabled for whatever child process it spawned.

## Building a Timeline

The tightest, highest-confidence anchor sequence: **4624 (Type 3 logon) → 5140 (share access) → Sysmon 11 (File Create for PSEXESVC.exe) → Sysmon 11 (File Create for the `.key` file, milliseconds later) → System 7045 (service install) → System 7036 (service start) → Sysmon 1 (process create, check the User field for impersonated-vs-SYSTEM) → Sysmon 17/18 (pipe create/connect) → [operator activity] → 7036 (stop) → Security 4689 → file deletion.** All typically land within a span of seconds to low minutes on a normal, uninterrupted run — a wider spread suggests either an interrupted cleanup or a deliberately slower, evasive operator. The `.key` file's creation timestamp is worth pulling out specifically: it directly names the source host, closing the loop back to `03 - Source Evidence.md`'s own timeline anchor on that machine.

## Distinguishing from Impacket's psexec.py

> 🔴 **Critical for triage — don't conflate the two.** Both tools produce the same end result (a remote shell over SMB via a temporary service), but every default artifact differs. Use this table to know immediately which tool you're looking at:

| Signal | Genuine Sysinternals PsExec (this page) | Impacket's `psexec.py` (`../Impacket/psexec/`) |
|---|---|---|
| Default service name | `PSEXESVC` | Random 4-character mixed-case string |
| Default dropped binary | `PSEXESVC.exe`, in `ADMIN$\System32\` | Random 8-character mixed-case `.exe`, in `ADMIN$` **root** (`C:\Windows\`) |
| Named pipe family | `psexecsvc` / `PSEXESVC-<host>-<pid>-std*` — name **derived from the binary's own filename**, shifts with a rename | `RemCom_communicaton` (fixed, hardcoded, preserves a 20-year-old typo) + `RemCom_std*<machine><pid>` |
| Default execution context | **Impersonated caller** — SYSTEM only with `-s` | **Always SYSTEM** — no impersonation option exists |
| Binary provenance | Real, Authenticode-signed Microsoft binary | From-scratch Python reimplementation of RemCom's service binary — no Microsoft signature, no relation to the genuine tool's code at all |
| Unique unconditional artifact | `PSEXEC-<source-hostname>-<8-hex>.key` in `C:\Windows\` (v2.30+) | None equivalent |
| Rename/evasion flag | `-r` (service name + binary + pipes shift together) | `-service-name` / `-remote-binary-name` (independently randomizable), `-file` (swap the dropped binary's hash entirely) |
| Pass-the-hash / pass-the-ticket | Not supported — cleartext password or existing session only | `-hashes` (NTLM), `-k`/`-aesKey`/`-keytab` (Kerberos) |

See `Windows/12 - Lateral Movement.md` for the broader PsExec-family comparison table (Impacket vs. Sysinternals vs. `wmiexec.py`/`smbexec.py`) and `Windows/10 - Persistence Mechanisms/Services.md` for the general service-based persistence/execution artifacts this note deliberately doesn't re-derive.
