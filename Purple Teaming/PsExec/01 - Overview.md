# PsExec (Sysinternals) — Overview

> 🔴 **Red Flag Principle:** Every real intrusion write-up fixates on the default service name `PSEXESVC` — but that's the weakest signal this tool leaves. The `-r` switch renames the service, and because the per-session named pipes are generated by the dropped executable **reading its own on-disk filename at runtime** (not a hardcoded string), renaming cascades through the service name, the dropped binary, *and* the pipe names all at once. What survives that entire rename chain: the PE `OriginalFileName`/`InternalName` metadata baked into the binary at compile time (`psexesvc.exe` / "PsExec Service Host" — unaffected by what the file is called on disk), and — starting with PsExec v2.30 (2021) — a `PSEXEC-<source-hostname>-<8-hex>.key` file dropped in `C:\Windows\` on **every single invocation**, which directly names the operator's own source host and has no `-r`-equivalent suppression flag at all. **Anchor hunts on the `.key` file and PE metadata, never on the literal string `PSEXESVC`.**

## History

**This is genuine Sysinternals PsExec — a real, Microsoft-signed binary — not Impacket's `psexec.py`.** The two are frequently conflated because they produce the same *outcome* (a remote SYSTEM/admin-context shell over SMB), but they are completely independent implementations with different mechanics, different default artifacts, and different evidence trails. Every place this note says "distinct from Impacket," it means `Impacket/psexec/` elsewhere in this repo — cross-linked throughout rather than re-deriving the shared SVCCTL/`ADMIN$` mechanics both tools ultimately rely on.

- **Author: Mark Russinovich**, co-founder (with Bryce Cogswell) of **Sysinternals**, which began in 1996 hosting Russinovich's advanced Windows system-internals utilities. PsExec shipped as part of the **PsTools** suite; Russinovich's own July 2004 *Windows IT Pro Magazine* article on advanced PsExec usage (still linked from the tool's own Microsoft Learn page) confirms the tool was mature and in wide use by 2004.
- **Microsoft acquired Sysinternals in July 2006.** PsExec has been maintained and redistributed directly by Microsoft ever since, under the Sysinternals brand — verified live against the current official page, [learn.microsoft.com/sysinternals/downloads/psexec](https://learn.microsoft.com/en-us/sysinternals/downloads/psexec).
- **Current version verified live for this note: v2.43**, dated April 11, 2023 per the official Microsoft Learn page's own "Published" date — treat any specific version number as a snapshot, not a fixed fact, and re-check the live page at time of use. PsExec ships inside `PSTools.zip` alongside the rest of the PsTools suite (`PsList`, `PsKill`, `PsLoggedOn`, etc.).
- **This is a real, Authenticode-signed Microsoft binary** — a categorically different provenance story from every credential/exploitation tool elsewhere in this module. Where Cobalt Strike or Mimikatz raise "this binary shouldn't be here at all," PsExec raises "this legitimate admin tool is being used against evidence of unauthorized access" — the signature itself is not suspicious; its *presence, timing, and context* are. Binary-provenance checks (Authenticode signature validity, publisher = Microsoft, matching the current `PSTools.zip` hash) matter here in a way they structurally cannot for Impacket's from-scratch Python reimplementation, which has no signature to check at all.
- **MITRE ATT&CK tracks it as Software [S0029](https://attack.mitre.org/software/S0029/)** ("PsExec"), created 2017 and separate from the generic [T1569.002](https://attack.mitre.org/techniques/T1569/002/) (System Services: Service Execution) technique it's the canonical procedure example for — verified live.
- **The dual-use reality:** PsExec is a legitimate, extremely common sysadmin tool (software deployment, patch push, remote diagnostics) with an enormous legitimate install base — the same "living-off-a-tool-that's-not-actually-living-off-the-land, bring-your-own-legitimate-binary" pattern this repo's `Rclone/` and `AnyDesk/` pages document. Nothing about the file itself is malicious; only its context is.

**A real, source-conflicting detail worth stating honestly:** whether `-r` renames *only* the SCM service registration (Microsoft's own doc phrasing — "the name of the remote service to create or interact with") or also the dropped binary's on-disk filename isn't spelled out in Microsoft's own documentation. Independent technical write-ups reverse-engineering the protocol (a detailed blog walkthrough of the client/server handshake, and a 2025 SensePost protocol analysis) both confirm the per-session pipe name prefix is read from the service executable's own filename at runtime rather than hard-coded — which means that in practice, an operator supplying `-r <name>` ends up with the service, the dropped binary, and the resulting pipes all shifted to that one custom value together. This is corroborated by real incident reporting of a financially-motivated group dropping a renamed service binary (`FRAMEPKG.EXE` in place of `PSEXESVC.EXE`) alongside a matching custom service name. Treat this as independently-verified-via-technical-analysis, not an explicit line in Microsoft's own docs.

### Default execution context — the sharpest mechanical difference from Impacket

**Sysinternals PsExec does NOT run as SYSTEM by default.** Per Microsoft's own documentation: "If you omit a user name, the process will run in the context of your account on the remote system, but will not have access to network resources (because it is impersonating)." The remote process only runs as SYSTEM if the operator explicitly passes `-s`. This is the inverse of Impacket's `psexec.py`, which **always** runs as SYSTEM because execution happens purely through the SCM with no impersonation logic at all (see `../Impacket/psexec/01 - Overview.md`). A Sysinternals PsExec session showing the connecting/authenticated account (not SYSTEM) as the process token in Sysmon 1 / Security 4688 is expected default behavior for this tool specifically, not evidence of a misconfiguration — check for `-s` in the source-side command line (`03 - Source Evidence.md`) to know which context to expect on the target.

### Cleanup behavior

On a clean exit, PsExec stops and deletes the `PSEXESVC` service and deletes the dropped binary from `ADMIN$\System32` — mirroring Impacket's own best-effort cleanup. A killed connection, a crashed session, or EDR blocking the delete RPC leaves an **orphaned service and binary** behind, which is itself a common real-world artifact (multiple sysadmin forums document manually cleaning up leftover `PSEXESVC` services after a failed run).

## Techniques / Protocols Used

| Layer | Detail |
|---|---|
| Transport | SMB (TCP 445) |
| Authentication | Whatever Windows itself negotiates for the SMB session (NTLM or Kerberos) using the invoking user's own token, or explicit alternate credentials via `-u`/`-p`. **No dedicated pass-the-hash, pass-the-ticket, or key-based auth switch** — a real capability gap versus Impacket's `-hashes`/`-k`/`-aesKey`/`-keytab` |
| File delivery | SMB write to `ADMIN$` → `C:\Windows\System32\PSEXESVC.exe` |
| Remote execution | MS-SCMR (Service Control Manager Remote Protocol) over `\PIPE\svcctl` — `OpenSCManagerW` → `CreateServiceW` → `StartServiceW` |
| Interactive I/O | PsExec's own named-pipe protocol — `\\.\pipe\psexecsvc` (handshake) + per-invocation `PSEXESVC-<hostname>-<pid>-std{in,out,err}` |
| Execution context | The connecting/impersonated account by default; SYSTEM only with `-s` |
| MITRE ATT&CK | [S0029](https://attack.mitre.org/software/S0029/) (PsExec), riding on [T1569.002](https://attack.mitre.org/techniques/T1569/002/) (Service Execution) and [T1021.002](https://attack.mitre.org/techniques/T1021/002/) (Remote Services: SMB/Windows Admin Shares) |

## Command-Line Switches — Quick Reference

Verified verbatim against the official [Microsoft Learn PsExec page](https://learn.microsoft.com/en-us/sysinternals/downloads/psexec) (by Mark Russinovich, published/updated 2023-03-30). Written for a reader who has never run the tool.

**Syntax:**
```
psexec [\\computer[,computer2[,...] | @file]][-u user [-p psswd]][-n s][-r servicename]
       [-h][-l][-s|-e][-x][-i [session]][-c [-f|-v]][-w directory][-d][-<priority>]
       [-g n][-a n,n,...][-accepteula][-nobanner] cmd [arguments]
```

| Switch | Plain-English meaning |
|---|---|
| `\\computer[,computer2,...]` | Target host(s). Omit to run locally; `\\*` runs against **every computer in the current domain** |
| `@file` | Run against every computer named in a text file — the fleet-wide targeting mechanism |
| `-u user` | Alternate username to authenticate as on the target (`Domain\User` syntax) |
| `-p psswd` | Password for `-u`. Omit and you're prompted for a hidden password instead — avoids the password ever touching a command line/history at all |
| `-n s` | Connection timeout, in seconds, for reaching the remote computer(s) |
| `-r servicename` | Name of the remote service to **create or interact with** — overrides the default `PSEXESVC`. See the "How It Works" note above on why this cascades further than the name alone |
| `-h` | On Vista and later, run the process with the account's **elevated token**, if one is available (UAC bypass for an already-admin account, not a privilege-escalation exploit) |
| `-l` | Run as a **limited user** — strips Administrators-group membership, restricts to Users-group privileges (Low Integrity on Vista+) |
| `-s` | Run the remote process in the **System account** — the flag that makes execution match Impacket's always-SYSTEM default |
| `-e` | Don't load the specified account's user profile |
| `-x` | Display the UI on the **Winlogon secure desktop** (local system only) |
| `-i [session]` | Run interactively, attached to the specified desktop session (console session if omitted). **Required** for any console app that needs redirected stdin/stdout/stderr to work at all |
| `-c` | **Copy** the specified local executable to the target before running it. Omit it and the command must already exist in the target's system path |
| `-f` | Paired with `-c` — copy even if the file already exists on the target (force-overwrite) |
| `-v` | Paired with `-c` — copy only if the local file has a higher version number or is newer than what's already on the target |
| `-w directory` | Working directory for the process on the target |
| `-d` | Don't wait for the process to terminate — fire-and-forget, non-interactive |
| `-<priority>` | One of `-low`, `-belownormal`, `-abovenormal`, `-high`, `-realtime`, or `-background` (Vista+, low memory/IO priority) — sets process scheduling priority on the target |
| `-g n` | (Documented as a separate memory/processor-affinity control alongside `-a` in some PsExec builds; treat as a minor scheduling knob, not security-relevant) |
| `-a n,n,...` | Restrict the process to specific CPU cores (e.g. `-a 2,4`) |
| `-accepteula` | Suppress the interactive EULA dialog — **required for any unattended/scripted invocation**, since without it a first-run prompt hangs waiting for a click. Still writes the `EulaAccepted` registry value (see `03 - Source Evidence.md`) — it doesn't avoid the artifact, only the dialog |
| `-nobanner` | Suppress the startup banner/copyright text in console output |
| `cmd [arguments]` | The program to run and its arguments. File paths in `arguments` must be **absolute paths on the target**, not the operator's own machine |

## Quick Use-Case List

- Baseline remote shell using the operator's own already-authenticated session (no `-u`)
- Interactive SYSTEM-context shell via `-s -i`
- Alternate-credential execution via `-u`/`-p`
- One-off, non-interactive, fire-and-forget command execution (`-d`)
- Uploading and running a custom local tool instead of relying on the built-in relay (`-c`, with `-f`/`-v` overwrite control)
- Service/binary/pipe renaming to evade signature-based detection (`-r`)
- Fleet-wide execution across every computer in the domain (`\\*`) or an explicit target list (`@file`)
- Elevated-token execution on an already-privileged account (`-h`)
- Limited-user / low-integrity execution for controlled testing (`-l`)
- Fully unattended/scripted invocation (`-accepteula -nobanner`)
- CPU-affinity/priority-constrained execution (`-a`, `-<priority>`) — a legitimate-admin-tooling pattern worth recognizing as low-signal on its own
- Interactive desktop-session targeting beyond the console session (`-i <session>`)
- Chained use immediately after credential harvesting from another tool already in this repo (Mimikatz, Impacket's `secretsdump`, BloodHound-informed targeting)
- Deliberate operator choice of the *signed* Sysinternals binary specifically, to blend into legitimate admin-tooling baselines rather than trigger a generic "hacktool" heuristic the way an unsigned reimplementation might

Full walkthroughs with commands and MITRE ATT&CK mapping for every item above live in `02 - Hands-On Use Cases.md`.

## Prerequisites

| Requirement | Notes |
|---|---|
| Credential material | The operator's own already-authenticated session (default), or explicit `Domain\User` + password via `-u`/`-p`. **No hash, ticket, or key-based auth path** — a real capability gap versus Impacket's `psexec.py` |
| Privilege on target | Authenticating account must be a **local administrator** on the target — required for `ADMIN$` write access and `SC_MANAGER_CREATE_SERVICE` rights |
| Network reachability | TCP 445 (SMB) to the target — no alternate port option, unlike Impacket's `-port 139` fallback |
| `ADMIN$` share enabled | Default on domain-joined Windows hosts; disabled/hardened environments (a documented mitigation — see `05 - Detection and Hunting.md`) block this tool entirely |
| No elevation on the operator's own host for the basic case | Running `psexec.exe` itself needs no local admin rights — only the *target-side* account needs admin rights on the target |
| EULA acceptance | First interactive run (or `-accepteula` for scripted use) writes the `EulaAccepted` registry value on the operator's own host — see `03 - Source Evidence.md` |
