# Certify — Source Evidence

What the **host running Certify** (whether that's `Certify.exe` on disk, a reflectively-loaded assembly, or a PowerShell wrapper) leaves behind — as distinct from `04 - Target Evidence.md`'s coverage of the CA/AD CS infrastructure and domain controller Certify talks *to*. Certify's evidentiary profile differs from a pure Kerberos-abuse tool like Rubeus in one important way: it routinely generates and handles **private key material locally**, not just credential-adjacent request traffic — a captured Certify run can leave the operator's own host holding the same walk-away credential the whole attack was built to obtain.

## Weaponization and Delivery Artifacts

**No official Certify binary exists to fingerprint against** — same posture as Rubeus/SharpUp, verified in `01 - Overview.md`'s History section (zero GitHub releases/tags, ever). Concrete consequences:

- **PE metadata is not a reliable static indicator** — `AssemblyTitle`/`AssemblyProduct`/filename are all operator-set at compile time.
- **Compiled-to-disk EXE**: standard AV signature scanning applies, but is brittle against a custom compile.
- **PowerShell-hosted (base64-reflection loader)**: the README's own documented pattern — `[Convert]::ToBase64String(...)` of the compiled assembly, loaded via `[System.Reflection.Assembly]::Load()`, invoked via `[Certify.Program]::Main()` or `::MainString()` (the latter specifically built for PSRemoting, redirecting stdout to a returned string rather than the console). Standard PowerShell v5 protections apply — AMSI, Script Block Logging (4104), Module Logging (4103) — see `LOLBins/powershell/` for the underlying mechanics.
- **Unmanaged assembly execution** (Cobalt Strike `execute-assembly`, Covenant, Sliver): CLR hosted inside a process that may not normally run .NET — a strong anomaly signal independent of anything Certify-specific.
- **Build-configuration signal**: a binary built from the `Disarm` configuration (see `01`'s History) is provably incapable of anything beyond the three enumeration verbs — if a suspect Certify sample is recovered, checking for the presence of `CertForge`/`CertRequest`/`ManageCa`/`ManageTemplate`/`ManageSelf` types via a simple `.NET` reflection dump (`ildasm`, `dnSpy`, or `Get-Type` against a loaded assembly) immediately answers whether weaponization was even compiled in.

## Command-Line / Shell History

- Every verb's full switch string lands in `ConsoleHost_history.txt` (interactive PowerShell) or Sysmon Event ID 1's `CommandLine` field if invoked as a standalone process.
- **Target-identity and infrastructure strings appear directly on the command line**, even though Certify has no raw-password/hash switch the way Rubeus does: `--ca SERVER\CA-NAME`, `--template NAME`, `--upn`/`--dns`/`--email` (the impersonated identity itself, in plain text — `--upn administrator@ghostpack.local` on a command line is as unambiguous a statement of intent as a stolen hash would be), `--target NAME` (`request-agent`'s impersonation target), and every file path passed via `--agent-pfx`, `--ca-cert`, `--cert-pfx`, `--out-file`, `--output-path` are all literal, unobfuscated arguments.
- `-p`/`--password`/`--ca-pass`/`--agent-pass`/`--cert-pass`/`--output-pass` **are** raw-secret switches when used — but Certify's own source (`ReadPasswordMasked()`, present in `EnumCas.cs`, `EnumTemplates.cs`, and `CertRequest.cs`) prompts interactively with masked input whenever a username/cert path is supplied without its paired password, specifically to keep that value off the command line. An operator who instead supplies `-p`/`--ca-pass` etc. directly on the command line is bypassing a safeguard the tool itself provides — worth noting as an operator OPSEC lapse, not a tool limitation, when found in captured command-line telemetry.

## Local Certificate and Private Key Material — the Distinctive Certify Artifact

This is where Certify's source-side evidentiary picture diverges most from a pure ticket-abuse tool:

- **Default output is console text, not a file.** `request`, `request-agent`, `request-download`, and `request-renew` all print the resulting PFX (base64) or PEM (cert + private key) directly to stdout — **no file is written to disk unless the operator explicitly redirects it** (shell `>`, or Certify's own `--out-file`, which per `01` redirects *all* console output — banner, status lines, and the base64 PFX/PEM blob together — into one plaintext file). A `--out-file` target is therefore the single highest-value local artifact if recovered: it contains not just evidence Certify ran, but the actual minted private key and certificate in reusable form.
- **`forge` is the one verb with a dedicated file-output switch** (`--output-path`/`--output-pass`) — a forged golden certificate written this way lands on disk as a normal PFX file, discoverable by any file-system sweep for `.pfx`/`.p12` extensions in non-standard locations (`C:\Temp`, `C:\Users\<user>\Downloads`, `C:\ProgramData`, etc.).
- **`--install` writes into the Windows certificate store, not a flat file** — `CX509Enrollment.InstallResponse()` (`request`/`request-agent`/`request-download`) lands the certificate and its private key in the current context's `My` store (`CurrentUser\My` normally, `LocalMachine\My` with `--machine`). **A source-verified detail worth flagging**: `CertEnrollment.cs`'s `CreatePrivateKey()` unconditionally sets `ExportPolicy = X509PrivateKeyExportFlags.XCN_NCRYPT_ALLOW_EXPORT_FLAG` on every private key Certify generates — meaning **every certificate Certify installs is deliberately marked exportable**, regardless of the target template's own policy. A cert discovered in a user's or machine's `My` store that is (a) exportable and (b) not something the account owner recalls requesting is a real, checkable local artifact — `certutil -store My` or `Get-ChildItem Cert:\CurrentUser\My` surfaces it directly.
- **`manage-self --dump-certs` output is the same pattern as `request`** — base64 PFX printed per certificate found in the local machine store, subject to the same `--out-file`/shell-redirect caveat.
- **The forged-certificate EKU fingerprint** — a genuinely distinctive static signature, found by reading `CertForge.cs`'s `GenerateCertificate()` directly: every certificate produced by the `forge` verb hardcodes the **same five EKUs simultaneously** — `Any Purpose`, `Client Authentication`, `PKINIT Client Authentication`, `Smartcard Logon`, and `Certificate Request Agent` — regardless of what the operator actually needs the cert for. A real CA-issued certificate from a legitimately-scoped template almost never carries all five of these together; a `.pfx`/certificate recovered anywhere (operator's own host, or later on a compromised target as dropped persistence) presenting this exact EKU combination is a strong, source-confirmed indicator it was produced by Certify's `forge` command specifically, distinguishable from an ESC1-abused certificate requested against a real (if misconfigured) CA template.

## Process and Network Artifacts

- **Outbound LDAP/LDAPS (389/636)** for every enumeration command, sourced from the Certify process (or its host process, if reflectively loaded) — visible in `netstat`/`Get-NetTCPConnection` as a non-`lsass.exe`/non-`svchost.exe` process holding an LDAP connection to a domain controller.
- **Outbound SMB (445) to the CA server** for `enum-cas`'s ESC6/ESC7/ESC11/ESC16 remote-registry reads — a distinct connection from LDAP, worth correlating separately since it targets the CA host specifically, not necessarily a domain controller.
- **DCOM/RPC to the CA** for every `request*`/`manage-ca` call — typically rides SMB (445) plus a dynamic RPC endpoint, or a statically configured RPC port. `Program.cs`'s unconditional `DistributedComUtil.Initialize()`/`InitializeSecurity()` call (any non-`Disarm` build, regardless of which verb is ultimately invoked — see `01`) means COM security context initialization happens at process startup, before argument parsing even completes.
- **Paired HTTP(S) connections to `<CA-host>/certsrv/`** — `enum-cas`'s ESC8 probe deliberately makes **two** near-simultaneous authenticated requests (with and without NTLM channel binding) against the same web-enrollment endpoint; two closely-timed outbound connections to `/certsrv/` from the same source process, rather than one, is a specific behavioral tell of this exact check running (unless `--skip-web-checks` was passed).

## Memory Forensics

- Unlike Rubeus, Certify's process memory routinely holds **decrypted private key material** during a run — `CX509PrivateKey.Create()` generates the RSA key pair locally, in-process, before the CSR is ever sent to the CA. A live memory capture of the Certify process during or shortly after a `request`/`forge` call can recover that key directly, independent of whatever the operator chose to do with the console output afterward.
- If reflectively loaded (`execute-assembly`, `[Assembly]::Load()`), the Certify CLR module exists in memory only, with no corresponding on-disk PE — the standard "unbacked executable memory region" signature (Moneta, PE-sieve, `Get-InjectedThread`-style EDR heuristics), independent of anything Certify-specific.
- COM/DCOM activation for the ICertRequest/ICertAdminD2 interfaces leaves in-memory RPC/COM runtime state (proxy/stub objects, security contexts) that isn't file-backed and isn't typically captured by disk forensics at all — a live-memory or ETW-based capture is the only way to observe the DCOM security-context initialization described above directly.

## OS-Level Audit Trail

- **Sysmon Event ID 1** (process creation): `CommandLine` carries template/CA/target-identity strings as described above; `OriginalFileName`/`Company`/`Product` PE fields are only useful if the operator didn't clear them at compile time.
- **Sysmon Event ID 3** (network connection): the LDAP/SMB/DCOM/HTTP(S) connections described above, sourced from a process that isn't a normal LDAP/COM client.
- **Sysmon Event ID 7** (image/DLL load) if Certify is compiled and invoked as a library rather than a standalone EXE.
- **Sysmon Event ID 13** (registry value set), if `--out-file` or `--install` activity is later cross-referenced against any registry-based persistence the operator layers on top — not something Certify itself writes to the registry, but relevant if the operator's broader toolkit does.
- **PowerShell 4104/4103**: only relevant for a PowerShell reflection wrapper — captures the *loader* script's content (the base64 blob, `[Assembly]::Load()`/`[Certify.Program]::Main()` lines), not Certify's own C# source.
- **Security 4688** (process creation, if command-line auditing is enabled) — the non-Sysmon equivalent of the Event ID 1 signal.

## Timeline Correlation Value

Source-side evidence here establishes **which identity was targeted, from which host, and whether a walk-away credential now exists somewhere the operator controls** — a materially different question from most tools in this repo, where the source host mostly shows *intent to act* while the *consequence* lives entirely on the target. Here, a recovered `--out-file`, an exportable cert in the `My` store, or a `.pfx` on disk **is** the consequence, sitting locally, independent of whether it was ever redeemed via `Rubeus asktgt /certificate:` or used for a native Windows logon. Build a timeline in this order: (1) source-host LDAP/network activity establishing enumeration occurred, (2) source-host process/network activity establishing a `request`/`request-agent`/`forge` call completed successfully, (3) a local artifact search (cert store, `.pfx` files, `--out-file` targets) confirming whether the resulting credential still exists on this host or was moved elsewhere, then (4) cross-reference against `04 - Target Evidence.md`'s CA-side and DC-side logs (where enabled) and `Rubeus/04 - Target Evidence.md`'s PKINIT authentication evidence for the redemption step.
