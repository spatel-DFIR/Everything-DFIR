# SharpUp — Target Evidence

## Why "Target" Evidence Is Mostly Just "The Same Host" Here

**Be precise about this rather than force-fitting the usual source/target split.** SharpUp has no remote-targeting flag anywhere in `Program.cs`'s argument parser (per `01`/`03`) — 14 of its 15 checks are entirely local, and even `DomainGPPPassword`, the one check that reaches another host, does so as a live authenticated file read *from* this host, not a separate execution on a remote one. There is no second machine running SharpUp's own code to produce independent "target-side" evidence the way `../../Impacket/wmiexec/04 - Target Evidence.md` documents for a genuinely remote technique. What follows is everything this local host's own telemetry captures about a SharpUp run, plus — as its own clearly separated subsection — the one piece of genuine network-layer/target-DC evidence `DomainGPPPassword` produces.

## Process Creation

| Event | Source | What it captures |
|---|---|---|
| Security 4688 (if command-line auditing enabled) | Process creation | `SharpUp.exe` (or its renamed equivalent), full command line including check name(s)/`audit` |
| Sysmon 1 | Process creation | Same, with richer `OriginalFileName`/`Hashes`/`ParentImage` fields — `OriginalFileName` only useful if unmodified `AssemblyInfo.cs` metadata survived the build (per `03`) |

A single `SharpUp.exe` process creation event, with no corresponding child processes spawned afterward, is itself a mild signal: SharpUp never shells out to `sc.exe`/`wmic.exe`/`schtasks.exe`/`icacls.exe` (per `01`), so a genuine SharpUp run looks like one process doing a great deal of API-level work with **zero process-tree fan-out** — a real point of contrast against a manual-enumeration operator who might chain several native LOLBins (`sc query`, `schtasks /query`, `icacls`) to cover the same ground and would leave a much busier process tree in the process.

## The Concurrent-Thread Query Burst — the Distinguishing Timing Signature

This is the headline target-host artifact, and it's a **timing pattern across several telemetry sources at once**, not a single event ID. Per `01`/`03`, `PrivescChecks()` spawns one `Thread` per requested check and starts them all with no throttle — for a full `audit` run, this produces, within the same few-hundred-millisecond-to-low-second window immediately following the `SharpUp.exe` process-creation event:

- Multiple **registry-key-open** operations across unrelated hive paths (`Environment`, `Winlogon`, `Run`/`RunOnce` keys native and `Wow6432Node`, `Services\<name>` for every installed service, `Windows\CurrentVersion\Installer` policy keys) — no native Windows audit event exists for a bare registry read without a SACL configured on the specific key (non-default, the same caveat this repo's DCSync/Kerberoasting/ProcDump pages already establish for their own SACL-gated events), so this activity is normally **invisible to native logging entirely** unless Sysmon's `RegistryEvent` (Event ID 12/13, key open/query) is separately configured — Sysmon's default config does not include registry-read coverage by default in most deployed rulesets, only value-set/delete.
- One **WMI query** against `root\cimv2`'s `Win32_Service` class (`ModifiableServiceBinaries`) — this is normally serviced by a WMI provider-host process (typically `WmiPrvSE.exe`, the same hosting mechanism `../../LOLBins/wmic/05 - Detection and Hunting.md` documents for `wmic.exe`'s own local queries), which can generate a WMI-Activity Operational Event ID 5857 entry — **flagged as a corroborating signal rather than a guaranteed one**: whether a purely local, in-process `System.Management.ManagementObjectSearcher` query is serviced by a distinct `WmiPrvSE.exe` host process or handled within the WinMgmt service itself depends on the CIMWin32 provider's hosting-model configuration on that specific host, and this repo has not independently confirmed which applies without a live ETW capture.
- A **burst of `OpenProcess()` calls against every running process on the host** — `ProcessDLLHijack`'s `Process.GetProcesses()` + `.Modules` walk, requesting `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` (`0x0410`, verified against `dotnet/runtime`'s `ProcessManager.Windows.cs` — see `03`) against **every reachable PID**, not just one sensitive target the way SharpDump/ProcDump/Mimikatz do. This produces dozens to low-hundreds of Sysmon Event ID 10 (Process Access) entries, all sourced from the single SharpUp process, all landing inside the same sub-second window as the registry/WMI activity above.
- Several **filesystem ACL reads** (`Directory.GetAccessControl`/`File.GetAccessControl`) across `%PATH%` directories, service binary paths, scheduled-task XML files, and autorun targets — again, no native audit event without an explicit SACL.

**The distinguishing property, versus Seatbelt's own sequential dispatcher, is density in time, not any single event type.** A Sysmon 10 view filtered to `SourceImage = SharpUp.exe` (or its renamed equivalent) showing dozens of `TargetImage` entries with timestamps landing within roughly the same second is a timing fingerprint that survives which specific checks were requested, survives binary renaming, and survives recompiling from modified source — since the burst is a property of `Program.cs`'s threading model, which an operator editing individual `Checks/*.cs` files to change strings/PE metadata is unlikely to also rewrite. Seatbelt's own equivalent activity, by contrast, is spread out sequentially (optionally further throttled via `-DelayCommands`), producing a comparatively flat, spread-out telemetry curve rather than a burst.

## DomainGPPPassword — The One Network-Touching Check

Verified directly against `Checks/DomainGPPPassword.cs`: the check reads `USERDNSDOMAIN` from the environment, then recursively walks `\\<USERDNSDOMAIN>\SYSVOL\*.xml` under the calling process's own token — a standard authenticated SMB file read, not a distinct network protocol client, DNS lookup, or LDAP query of its own (domain-name-to-DC resolution rides on whatever the OS's own name resolution already does for a UNC path). This is the **only** check in the tool that generates evidence on a second host at all:

| Layer | What it looks like |
|---|---|
| Source host (this one) | Outbound SMB (TCP 445) session to a domain controller serving SYSVOL; Sysmon Event ID 3 (Network Connection) if configured to log SMB traffic; `Get-SmbConnection`/`net use` may show a live session to `\\<domain>\SYSVOL` if captured mid-run |
| Target DC | Security Event 5140 (Network Share Object Was Accessed) / 5145 (Detailed File Share, if Object Access auditing on the SYSVOL share is enabled — **non-default**, same recurring caveat pattern this repo documents for DCSync/Kerberoasting SYSVOL mounts, e.g. `../../Rubeus/05 - Detection and Hunting.md`'s own SYSVOL-mount hunt) — a recursive read of every `*.xml` file under SYSVOL from a single source IP/account in a short window is the DC-side behavioral signature, since SharpUp's own file-open pattern (walking every subdirectory looking for seven specific filenames) is denser and broader than a normal Group Policy client's own targeted, per-GPO-GUID SYSVOL access |
| Authentication | Rides the caller's existing Kerberos/NTLM session — no separate credential material is presented, no distinct logon event beyond the implicit one already backing the SMB session |

Because `DomainGPPPassword` exits immediately with an explicit error string (`"Error: Machine is not a domain member or User is not a member of the domain."`) when `USERDNSDOMAIN` isn't set, its absence from a captured run's console output/error stream is itself informative — either the check wasn't requested, or the host genuinely isn't domain-joined at the time it ran.

## Endpoint-Security Signature Behavior

**No static hash to match — behavioral only, same posture as Rubeus/Seatbelt/SharpDump.** Per `01`, zero official binaries are ever released; every real-world `SharpUp.exe` is a custom compile, so static AV signatures are inherently brittle against this specific tool. EDR products lean on behavior instead, and SharpUp's own behavioral surface is unusually rich for a "read-only" tool:

- The concurrent-thread burst pattern itself (dense, sub-second, cross-artifact-class API activity from one process) — the strongest behavioral signal, developed fully in `05`.
- The `ProcessDLLHijack` check's mass `OpenProcess()` burst against every running process — a legitimate EDR/AV self-protection trigger in its own right, since "a non-security process is opening handles to dozens of other processes including this security product's own" is a pattern several EDR products flag regardless of what tool is doing it.
- The WMI `Win32_Service` query and SCM-handle-via-.NET-reflection pattern (`ModifiableServices`'s use of `BindingFlags.NonPublic` reflection into `ServiceController.GetServiceHandle()`, per `01`) — reflection into another class library's private members is itself a mild anomaly some behavioral engines flag independent of what it's used for.
- AMSI coverage of the assembly itself is conditional on build target and delivery method — see `03`'s note; SharpUp's stated .NET 3.5 default predates AMSI's CLR-integration hook at the assembly-execution layer, so coverage (if any) depends entirely on the loader's own hosted CLR version when delivered reflectively.

## Memory Forensics

SharpUp writes no dump file and holds no long-lived sensitive state (per `03`) — the target-host memory-forensics angle is thin by comparison to SharpDump's. What a live or near-contemporaneous memory capture *can* still recover: the `SharpUp.exe` process's own working set while it's running (harvested `CachedGPPPassword`/`DomainGPPPassword`/`RegistryAutoLogons` plaintext sitting in `_details` string lists before console output), and — if reflectively loaded — the unbacked CLR module in the host process's address space with no corresponding on-disk PE, the same "in-memory-only .NET module" signature documented for every other GhostPack tool in this repo.

## Building a Timeline

1. **Delivery/execution event** — process creation (Sysmon 1/Security 4688) for `SharpUp.exe` or the reflective-load event, with the exact check name(s)/`audit` argument captured in the command line — establishes T0 and states attacker intent directly (per `03`).
2. **The concurrent-thread burst** (T0 + a few hundred milliseconds to a couple of seconds) — registry-key opens (if Sysmon RegistryEvent coverage is deployed, otherwise inferred rather than directly observed), the `Win32_Service` WMI query (WMI-Activity 5857, if the local hosting model produces it), and the `ProcessDLLHijack`-driven burst of Sysmon 10 Process Access events against every reachable PID — all landing in the same tight window, the tool's defining timing signature.
3. **[If `DomainGPPPassword` was among the requested checks]** — the outbound SMB session to the domain's SYSVOL share, correlated against the target DC's own Event 5140/5145 (if Object Access auditing is enabled there) — the one point where this timeline extends beyond the local host.
4. **Console output / process exit** — SharpUp prints total elapsed time via its own `Stopwatch` and exits; no output file is created, so there is no separate "artifact write" event the way `../SharpDump/04 - Target Evidence.md`'s `debug<PID>.out`/`.bin` sequence provides — the process's own lifetime (creation to exit, normally a few seconds) *is* the operation's full on-disk/in-memory footprint.
5. **Correlate forward** — whatever finding SharpUp surfaced (a writable service binary, a modifiable registry key, a harvested GPP password) becomes the input to a follow-on abuse step by a separate tool (`sc`/`reg`, `../../PowerSploit/PowerUp/`) — that tool's own `04` file picks up the timeline from here, per `02`'s chained-workflow use case.
