# SharpUp — Source Evidence

## Where "Source" Evidence Actually Lives For This Technique

Like `../SharpDump/03 - Source Evidence.md` and `../../ProcDump/03 - Source Evidence.md` establish for their own tools, SharpUp is a **local-only** binary (per `01`) — an operator with a foothold runs it directly on the host being enumerated, not against a separate remote target (the single exception, `DomainGPPPassword`'s SYSVOL walk, still executes *from* this same host — see `04` for its network-layer evidence). "Source" and "target" therefore collapse onto the same machine for every realistic invocation. What follows is what a forensic examination of *this* host — the one SharpUp actually ran on — turns up, independent of whatever remote-execution vector (`../../PsExec/`, `../../Impacket/wmiexec/`) delivered the binary here in the first place; that vector's own command history and session state is cross-linked from its own `03` file, not re-derived here.

## Weaponization and Delivery Artifacts

**No official SharpUp binary exists to fingerprint against.** Per `01`, the project releases no compiled binaries, ever — every real-world sample is a custom Visual Studio (.NET 3.5) build.

- **PE metadata is a real lead only if the operator didn't bother scrubbing it.** Unmodified source produces `AssemblyTitle("SharpUp")`/`AssemblyProduct` strings in `Properties/AssemblyInfo.cs` — the same "supplementary, not primary" caveat `../SharpDump/03 - Source Evidence.md` documents for its own `AssemblyInfo.cs` applies identically here: editing this file before a build takes seconds, and there is no canonical hash to match against since source is public and every build is operator-specific.
- **Compiled-to-disk EXE**: standard AV signature scanning applies to whatever specific build landed on disk; per-compile hash only, not per-tool.
- **Download artifact, if staged from the internet directly**: a fetched `SharpUp.exe` or cloned repo carries a `Zone.Identifier` Alternate Data Stream (`ZoneId=3`) if pulled via a browser or `Invoke-WebRequest` without stream suppression — the same MOTW pattern documented repeatedly elsewhere in this repo (`../../LOLBins/certutil/`, `../SharpDump/03 - Source Evidence.md`).
- **Unmanaged/reflective execution (`execute-assembly`, `[Assembly]::Load()`)**: the CLR loads into a process that may not normally host .NET at all — an anomaly signal independent of anything SharpUp-specific, same framing as `../SharpDump/03 - Source Evidence.md`'s equivalent note.
- **AMSI**: applies to the loader script's own content when delivered via PowerShell reflection, and to the assembly itself only if built against .NET 4.8+ — SharpUp's stated default target is .NET 3.5 (per `01`, one generation older even than SharpDump/Rubeus/Seatbelt's 3.5/4.0/4.8 range), which predates AMSI's CLR-level integration at the assembly-execution layer. Whether AMSI actually applies to a given run depends on the **loader's own hosted CLR version**, not SharpUp's declared target framework, identical caveat to `../SharpDump/02 - Hands-On Use Cases.md`'s in-memory-execution use case.

## Process-List Exposure

Every SharpUp invocation is a single, short-lived process (or a single reflectively-loaded CLR module inside a longer-lived host process) — there is no persistent service, no background listener, and (unlike `../SharpDump/`) **no follow-on artifact process** since SharpUp never writes an output file for another tool to consume later. The process's own command line is the one part of this technique with genuine investigative content, because — unlike Rubeus's `/rc4:HASH` or Mimikatz's plaintext-credential arguments — **every one of SharpUp's arguments is a check name or the literal word `audit`**, never a secret. A captured command line is fully self-explanatory to a reader who has this repo's check-name table (`01`) open next to it: `SharpUp.exe audit ModifiableServices` unambiguously states *both* that the gate was overridden *and* exactly which privesc surface the operator was hunting for.

## Shell / Command History

- If invoked interactively, the full command lands in `ConsoleHost_history.txt` (PowerShell) or is visible via Sysmon Event ID 1's `CommandLine` field / Security 4688 (if command-line auditing is enabled).
- Because check names are literal, human-readable class-name strings (`UnquotedServicePath`, `ModifiableServices`, `TokenPrivileges`, etc.), a captured history entry is a direct, high-fidelity statement of attacker intent — a `SharpUp.exe audit ModifiableServiceRegistryKeys` entry tells an analyst the operator was specifically chasing a service-registry-ACL privesc path, not just "ran some enumeration tool." This is a stronger command-line signal than most tools in this repo produce, precisely *because* SharpUp has no flag namespace to hide behind — every argument is drawn from the fixed, 15-name reflected check list (`01`).
- A bare `SharpUp.exe` (no arguments) only ever prints usage and exits — it is not a real invocation of any check and produces no check-related evidence at all; don't mistake a captured bare invocation for evidence of enumeration having actually occurred.

## OS-Level Audit Trail — the Concurrent-Thread Burst as the Real Signature

SharpUp has **no OS-level audit trail of its own** in the way a network protocol or service-installation event would provide — every check reaches its target purely through in-process .NET/Win32 API calls (per `01`'s mechanism table), and Windows does not audit registry reads, file-ACL reads, or local WMI class queries by default. What *is* structurally distinctive, and independent of which specific checks ran, is **the shape of the API-call burst itself**:

- `Program.PrivescChecks()` spawns one `Thread` per requested check and starts all of them in a tight `foreach` loop with no throttle — verified directly against the live `Program.cs` source. For an `audit` (all-15-checks) run, this means registry reads (`AlwaysInstallElevated`, `RegistryAutoLogons`, `RegistryAutoruns`, `HijackablePaths`, `ProcessDLLHijack`'s `KnownDlls` lookup, `UnquotedServicePath`), a WMI `Win32_Service` query (`ModifiableServiceBinaries`), SCM-handle-via-reflection + `QueryServiceObjectSecurity` calls (`ModifiableServices`), filesystem ACL checks across several path classes, and recursive filesystem walks (`CachedGPPPassword`, `McAfeeSitelistFiles`, `UnattendedInstallFiles`) all **launch within the same few milliseconds**, from the same parent process, and typically complete within a couple of seconds (SharpUp itself prints total elapsed time via a `Stopwatch` in `Main()`).
- **This is the mechanical inverse of Seatbelt's dispatcher**, which runs checks sequentially (optionally throttled via `-DelayCommands`). A host-based EDR or memory-forensics view of "one process issuing a dense, sub-second burst of registry/WMI/filesystem-ACL API calls across a dozen-plus unrelated artifact classes" is a timing signature that survives *which* specific checks were requested — it's a property of `PrivescChecks()`'s dispatch loop itself, not of any individual check's logic, and it holds true even if the operator recompiles from modified source, since the threading model lives in `Program.cs`, separate from the per-check `Checks/*.cs` files an operator is more likely to edit to change output strings or PE metadata.
- **`ProcessDLLHijack` is the one check whose API-call burst is itself independently loud.** It calls `Process.GetProcesses()` then reads every returned process's `.Modules` collection — verified directly against `dotnet/runtime`'s own `ProcessManager.Windows.cs` (`NtProcessManager.GetModules()`), this opens **every reachable process on the host** with `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ)` (mask `0x0410`) to enumerate its loaded modules. On a typical host with 80-150 running processes, this is a burst of **dozens to a hundred-plus separate process-open calls landing inside the same sub-second window** as the other checks' registry/WMI activity — see `04` for the resulting Sysmon 10 signature. This mask is narrower than SharpDump's `PROCESS_ALL_ACCESS` (`../SharpDump/03 - Source Evidence.md`) and different in kind from Mimikatz's `sekurlsa` mask (`0x1010`, `PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ` — note the *limited* vs. full `PROCESS_QUERY_INFORMATION` distinction), but it is unique among tools in this repo for the sheer **number of distinct target processes** touched in one run.

## Memory-Forensics Angle

Unlike SharpDump — which produces a separate `.out`/`.bin` dump file that itself becomes the durable memory-forensics artifact (`../SharpDump/03 - Source Evidence.md`) — **SharpUp never writes a memory dump of anything.** Every check's "memory forensics" angle is instead about the SharpUp process's *own* transient in-memory state:

- If loaded reflectively (`execute-assembly`, `[Assembly]::Load()`), the SharpUp CLR module exists in memory only, with no corresponding on-disk PE — the standard unbacked-executable-memory-region signature (Moneta, PE-sieve, EDR memory-scan heuristics) applies, independent of anything SharpUp-specific, same framing already established for `../SharpDump/03 - Source Evidence.md` and `../../Rubeus/`.
- Findings (writable service paths, cached GPP plaintext passwords, registry autologon credentials) are held only in each check's `_details` string list for the duration of the run and printed to the console — a live memory capture of the SharpUp process taken *during* execution could recover harvested `CachedGPPPassword`/`DomainGPPPassword`/`RegistryAutoLogons` plaintext before it's ever written to any output file (SharpUp writes no output file at all — console-only), but that window is normally sub-second given the tool's typical total runtime.
- Because `ProcessDLLHijack` briefly holds open handles to every enumerated process, a memory/handle-table snapshot taken mid-run would show SharpUp (or its reflective-load host) holding a large, transient set of process handles simultaneously — itself a distinctive live-forensics signature, though one that only exists for the few seconds the check is actually running.

## Timeline Correlation Value

The single process-creation event for `SharpUp.exe` (or the reflective-load event, if applicable) is the anchor. Because the command line carries the exact check name(s) requested (or `audit` for all 15), and because the concurrent-thread burst pattern completes in a tight, predictable window immediately after that event, correlating "this process started" against "this burst of registry/WMI/file-ACL/process-access activity occurred in the following 0-5 seconds" is normally sufficient to tie the two together with high confidence — see `04`'s timeline walkthrough for how that burst appears from the target-host telemetry side. Where SharpUp's timeline value is thinner than SharpDump's or ProcDump's: there is no output-file creation timestamp to serve as a second anchor point, since SharpUp produces none — the process-creation event and the API-call burst it triggers are the *entire* evidentiary chain for a given run.
