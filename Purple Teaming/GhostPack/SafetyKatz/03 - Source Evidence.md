# SafetyKatz — Source Evidence

## Where "Source" Evidence Actually Lives For This Technique

Like `../../ProcDump/03 - Source Evidence.md` and `../SharpDump/03 - Source Evidence.md` already establish for their own techniques, SafetyKatz is most often run **directly on the host already being victimized** — an operator with sufficient access has landed on the box and dumps-and-parses LSASS on it in place, not reaching out to a separate target over the network (SafetyKatz has no network client of its own — see `01`). "Source" and "target" evidence therefore collapse onto the same machine in the common case, and the meaningful question shifts to *where did the compiled binary come from, and under what identity did it run* — the mechanical dump/PE-load/parse/delete artifacts themselves are covered fully in `04`.

When SafetyKatz **is** fired remotely (per `02`'s fleet-wide use case), the actual source-side evidence — command history, authenticated session state, tool staging — belongs to whichever delivery vector did the work (`../../PsExec/03 - Source Evidence.md`, `../../Impacket/wmiexec/03 - Source Evidence.md`, `../../LOLBins/wmic/03 - Source Evidence.md`) and is cross-linked rather than re-derived here.

## Weaponization and Delivery Artifacts

**No official SafetyKatz binary exists to fingerprint against.** Per `01`, the project releases no compiled binaries — every real-world sample is a custom Visual Studio build, and because the embedded Mimikatz component ships as a compressed Base64 blob rather than buildable source, even operators who don't modify `Program.cs` at all still produce a binary whose most detectable component (the inner Mimikatz PE) is identical across every unmodified compile — a stronger static-fingerprinting opportunity than tools whose entire payload is freshly compiled per operator.

- **PE metadata on the outer assembly is not a reliable static indicator by default, but is a real lead if unmodified.** Unmodified source produces `AssemblyTitle("SafetyKatz")` and `AssemblyProduct("SafetyKatz")` (verified directly against `Properties/AssemblyInfo.cs`), with `AssemblyVersion`/`AssemblyFileVersion` both hardcoded to `1.0.0.0` — an operator who doesn't bother editing `AssemblyInfo.cs` before compiling leaves these strings intact even after renaming the output `.exe`. Treat as supplementary, not primary, since editing this file before a build takes seconds — the same caveat already documented for `../SharpDump/03 - Source Evidence.md` and `../SharpUp/01 - Overview.md`.
- **The embedded Mimikatz blob is a fixed 2018-era build (`2.1.1`, built `Jul 7 2018`) unless an operator manually re-embeds a newer one.** Because `Constants.cs`'s `compressedMimikatzString` is a static, compressed asset rather than something recompiled from live upstream source each build, its decompressed size (628,736 bytes, verified against the live `Constants.cs`) and internal PE timestamp/version strings are consistent across every operator's compile that hasn't gone out of their way to regenerate that blob — a more stable cross-sample static fingerprint than most GhostPack tools offer.
- **Compiled-to-disk EXE**: standard AV signature scanning applies; a stable file hash only exists per-compile for the outer assembly, since (like Rubeus/Seatbelt/SharpDump) the outer source is public and every build is operator-specific — but see the point above regarding the embedded inner PE.
- **Download artifact, if staged from the internet directly**: a fetched `SafetyKatz.exe` or a cloned/downloaded repo carries a `Zone.Identifier` Alternate Data Stream (`ZoneId=3`) if pulled via a browser or `Invoke-WebRequest` without stream suppression — same MOTW pattern documented repeatedly in this repo (`../../LOLBins/certutil/`, `../SharpDump/03 - Source Evidence.md`).
- **Unmanaged/reflective execution (Cobalt Strike `execute-assembly`, PowerShell `[Assembly]::Load()`)**: the CLR gets loaded into a process that may not normally host .NET at all — an anomaly signal independent of anything SafetyKatz-specific, identical to `../SharpDump/`'s equivalent finding.
- **AMSI**: applies to the outer .NET-assembly loader script's content when delivered via PowerShell reflection (the base64 blob and `[SafetyKatz.Program]::Main()` invocation lines). It does **not** apply to the inner embedded Mimikatz PE-load step at all — that's unmanaged x64 code mapped by hand via `VirtualAlloc`, entirely outside the CLR and outside AMSI's .NET-integration hook, a meaningfully different exposure profile from a pure-.NET GhostPack tool.

## Command-Line / Shell History

- If invoked interactively, the bare command lands in `ConsoleHost_history.txt` (PowerShell) or is visible via Sysmon Event ID 1's `CommandLine` field. SafetyKatz's command line carries **no credential material and no arguments of any kind** — since `Main()` never reads `args` (per `01`), there is nothing for an operator to even pass, and nothing secret to leak via command-line logging.
- A bare `SafetyKatz.exe` invocation is, on its own, minimal-signal text — the useful correlation is pairing this command-line entry with the process-access/file-creation events documented in `04`, not the command line in isolation. Unlike `../SharpDump/`, there is no PID argument variant to distinguish "default LSASS run" from "targeted non-LSASS run" at the command-line level, since no such targeting option exists.

## Process and Handle Artifacts

The single most distinctive source-side technical fact for this tool, shared with `../SharpDump/`: **SafetyKatz's `targetProcess.Handle` call requests `PROCESS_ALL_ACCESS`** (`0x1F0FFF` — `STANDARD_RIGHTS_REQUIRED | SYNCHRONIZE | 0xFFF`, the same .NET `Process.Handle`-property access pattern verified against .NET Framework's own reference source in `../SharpDump/03 - Source Evidence.md`), because it uses the identical generic property rather than a narrow, purpose-built `OpenProcess()` call the way Mimikatz's own `sekurlsa` module or ProcDump's DbgHelp-driven request do:

| Tool | Access requested against target process |
|---|---|
| SafetyKatz (`Process.Handle`) | `PROCESS_ALL_ACCESS` (`0x1F0FFF`) |
| SharpDump (`Process.Handle`) | `PROCESS_ALL_ACCESS` (`0x1F0FFF`) — identical mechanism, see `../SharpDump/03 - Source Evidence.md` |
| Mimikatz `sekurlsa::logonpasswords` | `PROCESS_VM_READ \| PROCESS_QUERY_LIMITED_INFORMATION` (`0x1010`) — see `../../Mimikatz/sekurlsa (Credential Dumping)/01 - Overview.md` |
| Mimikatz `sekurlsa::pth` | Adds `PROCESS_VM_OPERATION \| PROCESS_VM_WRITE` on top of the above — still narrower than SafetyKatz/SharpDump's blanket request |

A process (`SafetyKatz.exe`, or whatever host process it's reflectively loaded into) requesting near-full access rights against `lsass.exe` is a louder, easier-to-flag signal than the deliberately minimal read a standalone `sekurlsa::logonpasswords` makes. Any GrantedAccess-mask-based Sysmon 10 rule tuned narrowly to Mimikatz's `0x1010`/`0x1410` values will **miss** this — see `../SharpDump/03 - Source Evidence.md`'s identical finding and `05 - Detection and Hunting.md` for a broader mask-based rule that catches both.

**A second, distinct process-access event happens after the dump — but it's internal, not a second `OpenProcess()` call.** Unlike a workflow that dumps on one host and parses on another (`../SharpDump/`'s designed use), SafetyKatz's embedded Mimikatz reads the just-written `debug.bin` file directly via `CreateFile`/file I/O, not via a second `OpenProcess()` against LSASS — the process-access event count for a complete SafetyKatz run against LSASS is exactly **one**, identical to a single `../SharpDump/` run, not two.

## Network Connection State

None. SafetyKatz makes no network connections of any kind — the entire operation is a local `OpenProcess()`/`MiniDumpWriteDump()`/PE-load/parse/delete sequence, with credential output printed to the console (or relayed over whatever C2 channel is hosting the process, if reflectively loaded). Any network activity observed alongside a SafetyKatz run belongs to the delivery vector that got it onto the host, or a separate exfil step, if the operator chose to capture and transmit the console output elsewhere — neither is SafetyKatz's own traffic.

## Memory Forensics

- If loaded reflectively (`execute-assembly`, `[Assembly]::Load()`), the outer SafetyKatz CLR module exists **in memory only**, with no corresponding on-disk PE — the standard "unbacked executable memory region" signature tools like Moneta, PE-sieve, or EDR memory-scan heuristics are built to catch, independent of anything SafetyKatz-specific.
- **A second, distinct memory-forensics signal exists that `../SharpDump/` does not have**: the embedded Mimikatz PE is *always* manually mapped into memory via `VirtualAlloc`/section-copy/relocation-patch (per `01`'s How It Works) — regardless of whether the outer SafetyKatz assembly itself was loaded from disk or reflectively. This means a **second unbacked executable region** (the inner Mimikatz image, distinct from the outer SafetyKatz process/module) is present in every single SafetyKatz run, even a plain `SafetyKatz.exe` double-click from disk. A memory scan that only flags the outer process as suspicious because it's unbacked will miss this; a scan that walks all `PAGE_EXECUTE_READWRITE` regions within the SafetyKatz process specifically should catch the manually-mapped inner Mimikatz image regardless of how the outer tool was launched.
- Unlike SharpDump, which never decrypts or displays credential content itself, SafetyKatz's entire point is that decrypted plaintext/hash/ticket material **is** present in the SafetyKatz process's own working memory during the run — it's the embedded Mimikatz thread doing the decryption and printing, executing inside the SafetyKatz process's address space, not a separate process. A live memory capture of a still-running SafetyKatz process is therefore a materially richer source-side lead than the equivalent capture would be for SharpDump.

## Timeline Correlation Value

The strongest source-side timeline anchor is the process-creation event for `SafetyKatz.exe` (or the reflective-load event, if applicable) — since the command line carries no arguments or credential material at all, correlating this single event's timestamp against the (typically very brief) window during which `debug.bin` exists on disk (`04`) is normally sufficient to tie "SafetyKatz ran" to "this specific dump/parse cycle." Because SafetyKatz's entire dump-parse-delete sequence completes within its own single execution (contrast `../SharpDump/`'s dump now, parse-whenever-later split), the timeline here is unusually compressed — process start, `dbghelp.dll` load, `lsass.exe` access, `debug.bin` creation, and `debug.bin` deletion should all cluster within the tool's 30-second internal thread-wait window, a materially tighter correlation signature than a SharpDump run followed by an exfil step and an offline Mimikatz parse potentially hours or days later.
