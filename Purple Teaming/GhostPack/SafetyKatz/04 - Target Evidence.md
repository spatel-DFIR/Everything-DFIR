# SafetyKatz — Target Evidence

What SafetyKatz leaves on the host it actually runs against. The shared `dbghelp.dll!MiniDumpWriteDump()` mechanic, the `RunAsPPL` access-control gate, and the general Sysmon 7/10 image-load/process-access story are already documented in depth in `../../ProcDump/04 - Target Evidence.md` — apply that page's mechanics directly. The `PROCESS_ALL_ACCESS`-via-`Process.Handle` pattern is documented in `../SharpDump/04 - Target Evidence.md`. This page covers what's specific to SafetyKatz's own single-process dump-then-parse design and its embedded credential-extraction step.

## Filesystem — the Headline Artifact, and Its Narrow Window

**SafetyKatz's hardcoded output path is even more fixed than SharpDump's — but it normally exists on disk for only seconds.** Verified directly against `Program.cs`: every run writes to exactly one path:

| File | Path pattern | Notes |
|---|---|---|
| Raw minidump | `%SystemRoot%\Temp\debug.bin` | Written directly by `MiniDumpWriteDump()`, **raw, uncompressed** — no GZip step at the SafetyKatz layer (contrast `../SharpDump/`'s automatic compression). No PID in the filename — every SafetyKatz run on a given host produces a file at this exact same path, overwriting any prior run's leftover |

Unlike `../SharpDump/` (PID-qualified filename, persists as the deliverable) or ProcDump/`comsvcs.dll` (operator-chosen path, persists until manually deleted), **`debug.bin` is meant to be transient** — the embedded Mimikatz thread opens it, parses it, and deletes it (`File.Delete`-equivalent, executed from within the loaded Mimikatz PE's own code) before SafetyKatz's outer 30-second `WaitForSingleObject()` returns. On a completed, uninterrupted run, live-response file-listing will normally find **nothing** at `%SystemRoot%\Temp\debug.bin` — the absence of the file is not evidence the technique didn't run, only that it completed successfully.

**A `debug.bin` file appearing anywhere under `%SystemRoot%\Temp\` — especially with no PID suffix, no `.gz`/`.out` sibling, and (if caught mid-run) valid raw minidump `MDMP` magic bytes rather than SharpDump's gzip `1F 8B` — is close to a direct fingerprint for this specific tool, or an interrupted run of it.** The no-PID naming is itself the discriminator versus `../SharpDump/`'s `debug<PID>.out`/`.bin` convention.

**Recovering the file after deletion is the realistic forensic path, not catching it live.** Because the on-disk window is normally just seconds, live file-listing rarely catches `debug.bin` mid-run — but the delete itself leaves the usual filesystem-forensics trail: `$MFT`/USN Journal entries recording both the create and the delete event in close succession, and the underlying disk clusters remaining recoverable via standard file-carving (`MDMP` header) until overwritten, exactly the same recovery logic `../SharpDump/04 - Target Evidence.md` documents for its own briefly-live raw `.out` file — only here it applies to the *entire* dump, not just an intermediate pre-compression artifact.

## Registry

**None.** Verified directly against `Program.cs`: SafetyKatz makes **zero registry reads or writes** anywhere in its own code — a genuine divergence from `../SharpDump/`, which at least performs one registry read (`ProductName`) on its default path. Do not expect any registry-based signal from this tool at all, including the `EulaAccepted`-style artifact `../../ProcDump/03 - Source Evidence.md` documents for the Sysinternals tool.

## Event Logs

| Event | Source | What it captures |
|---|---|---|
| Security 4688 (if command-line auditing enabled) | Process creation | `SafetyKatz.exe` (or its renamed equivalent) launching — command line will show **no arguments**, since none are ever supplied or consulted |
| Sysmon 1 | Process creation | Same, with richer `OriginalFileName`/`CommandLine` fields — `OriginalFileName` only useful if unmodified `AssemblyInfo.cs` metadata survived the build |
| Sysmon 7 | Image/DLL load | `dbghelp.dll` loading into the SafetyKatz process (or the reflective-load host process) — the shared signal documented in depth in `../../ProcDump/05 - Detection and Hunting.md` |
| Sysmon 10 | Process access | `OpenProcess()` against `lsass.exe`, with a `GrantedAccess` value consistent with a near-maximal request (`PROCESS_ALL_ACCESS`) — identical mask family to `../SharpDump/04 - Target Evidence.md`, and a single event per run (no second access event for the parse step, since that reads the dump file, not LSASS again) |
| Sysmon 11 | File creation | `debug.bin` under `%SystemRoot%\Temp\` — typically the single most useful Sysmon 11 hit for this tool, but frequently missed on a real timeline sweep unless File Delete auditing (Sysmon 23, if configured) is also enabled to catch the matching deletion event |
| Sysmon 23 (if configured) | File delete | The `debug.bin` deletion, generated by the embedded Mimikatz's own cleanup step — pairing Sysmon 11's create and Sysmon 23's delete for the identical path within a tight (typically sub-30-second) window is a strong, tool-agnostic-but-highly-suggestive pattern once both are available |
| WinInit Event 12 | System log | LSA-protection (PPL) state at boot — identical mechanic to `../../ProcDump/04 - Target Evidence.md`'s coverage, not re-derived |

## Sysmon Detail Specific to SafetyKatz

- **Sysmon 10's `GrantedAccess` field matches SharpDump's, not Mimikatz's.** Both SafetyKatz and `../SharpDump/` use .NET's `Process.Handle` property rather than a narrow DbgHelp-driven or Mimikatz-style minimal `OpenProcess()` call — a hunt scoped only to Mimikatz's `0x1010`/`0x1410` values will miss both; a mask-based rule broad enough to catch `PROCESS_ALL_ACCESS` (`0x1F0FFF`) against `lsass.exe` catches all three tools documented in this GhostPack family plus `../../Mimikatz/sekurlsa (Credential Dumping)/`'s own module.
- **Sysmon 11's filename pattern is the narrowest and most stable in this entire tool family — no PID variable to account for at all.** `debug.bin`, no suffix, always the same path — even narrower than `../SharpDump/`'s already-narrow `debug<PID>.*` pattern, and unlike ProcDump/`comsvcs.dll`'s fully operator-chosen filenames. The tradeoff is that Sysmon 11 alone is far more likely to miss the event entirely on a retrospective sweep, since the file is normally gone again (Sysmon 23) within seconds — this pushes real detection weight onto **live** Sysmon 11 alerting (fires the instant the file is created, before the delete) rather than a post-hoc filesystem walk.
- **No second `OpenProcess()` against LSASS for the parse step** — because the embedded Mimikatz reads `debug.bin` as a file (`CreateFile`/`ReadFile`), not a second live memory access, Sysmon 10 shows exactly one `lsass.exe`-targeting event per complete SafetyKatz run, not two. Contrast this against a scenario where an operator dumps with one tool and separately, later, runs a live-memory `sekurlsa::logonpasswords` against the still-running LSASS — that pattern would show two distinct access events.

## Endpoint-Security-Product Signature Behavior

- Because no official binary is ever released (per `01`), static AV signatures on the **outer** SafetyKatz assembly are inherently brittle, the same positioning as `../SharpDump/`, `../../Rubeus/`, and `../../Seatbelt/`. However, the **embedded inner Mimikatz PE** is a fixed, unmodified blob across any operator compile that doesn't bother re-generating `Constants.cs` (per `01`'s History) — EDR/AV products with byte-pattern or entropy-based signatures tuned to that specific 2018-era compiled Mimikatz build have a real, if narrow, static-detection opportunity here that doesn't exist for a tool whose entire payload is freshly compiled every time.
- EDR products otherwise lean on behavioral detections: the `dbghelp.dll` load, the broad `PROCESS_ALL_ACCESS` request against `lsass.exe`, the fixed `debug.bin` file-creation-then-deletion pattern, and — most distinctively for this tool — a **second, internal `VirtualAlloc(PAGE_EXECUTE_READWRITE)` region appearing inside the SafetyKatz process itself**, populated by the hand-rolled PE loader, independent of whether the outer process was itself loaded from disk or reflectively. This is a stronger, more specific in-process anomaly than most GhostPack tools present, since it's present on **every** run, not just reflectively-loaded ones.
- AMSI applies to the PowerShell-reflection delivery path's loader script content for the **outer** assembly only. It does **not** apply at all to the **inner** Mimikatz PE-load — that's unmanaged code mapped via raw `VirtualAlloc`, entirely outside the CLR and AMSI's .NET-integration hook, regardless of which .NET Framework version the outer assembly targets. This is a meaningfully different AMSI exposure profile from a pure-managed-code GhostPack tool.

## Memory Forensics

- The `debug.bin` file, if recovered (live-caught, carved post-deletion, or captured via a Volume Shadow Copy/backup taken during its brief existence), **is** the primary memory-forensics artifact — parseable with the identical `sekurlsa::minidump` workflow documented in `../../Mimikatz/sekurlsa (Credential Dumping)/`, exactly as `../SharpDump/04 - Target Evidence.md` documents for its own output.
- **A live memory capture of a still-running SafetyKatz process is a materially richer artifact than the equivalent capture of a SharpDump process** (per `03`'s cross-reference) — because SafetyKatz's embedded Mimikatz thread actually decrypts and holds plaintext/hash/ticket material in the SafetyKatz process's own address space during the run (SharpDump never decrypts anything itself), a memory image taken while SafetyKatz is executing can expose credential material directly, without needing to separately recover and parse `debug.bin` at all.
- If LSASS is the target and PPL blocks the attempt outright (per `../../ProcDump/01 - Overview.md`'s shared gate), there is no dump file to recover and no inner Mimikatz PE-load ever occurs — the attempt's only trace is the failed `OpenProcess()` call itself (Sysmon 10, if logged) plus SafetyKatz's own console error output, if captured.

## Distinguishing SafetyKatz From SharpDump / ProcDump / comsvcs.dll on a Live or Imaged Host

| Question | Points to SafetyKatz |
|---|---|
| Is there a `debug.bin` file (no PID suffix) at `%SystemRoot%\Temp\`, or Sysmon 11/23 evidence of one having briefly existed? | Yes — this exact filename is unique to unmodified SafetyKatz; `../SharpDump/` always includes a PID, ProcDump/`comsvcs.dll` output can be named/placed anywhere |
| Is the recovered/carved file's content raw (uncompressed) minidump data (`MDMP` magic), rather than gzip? | Yes — `../SharpDump/`'s equivalent output is gzip-compressed; SafetyKatz's is not |
| Did the file exist only briefly, with a matching create-then-delete pair in a tight window (Sysmon 11 + 23, or `$MFT`/USN Journal)? | Yes — `../SharpDump/`'s `.bin` is designed to persist as the exfil deliverable; ProcDump/`comsvcs.dll` output persists until an operator manually deletes it, if ever |
| Is there exactly one Sysmon 10 `lsass.exe`-access event, with no corresponding exfil-tool activity afterward? | Consistent with SafetyKatz — credentials were parsed and printed in-process, with no dump file needing to leave the host at all, unlike a `../SharpDump/` workflow that typically pairs with an exfil step (`../../Rclone/`) |
| Was a second, internal `PAGE_EXECUTE_READWRITE` memory region observed inside the same process that accessed LSASS, distinct from the outer process's own loaded modules? | Points specifically to SafetyKatz's manual inner PE-load step — `../SharpDump/`, ProcDump, and `comsvcs.dll` have no equivalent second in-process PE mapping |
| Is there an `EulaAccepted` registry artifact? | No — that's ProcDump-specific (Sysinternals EULA gate); neither SafetyKatz nor SharpDump has one |

## Building a Timeline

1. **Delivery/execution event** — process creation (Sysmon 1/Security 4688) for `SafetyKatz.exe` or the reflective-load event, with an empty/unused command line (no arguments ever consulted).
2. **`dbghelp.dll` image load** (Sysmon 7) into the SafetyKatz process — shared signal, see `../../ProcDump/04 - Target Evidence.md`.
3. **Process access against `lsass.exe`** (Sysmon 10) — the single `PROCESS_ALL_ACCESS` request; there is no second LSASS-access event for the parse step.
4. **`debug.bin` file creation** (Sysmon 11) — typically the tightest correlation point, since it happens within the same execution as steps 2-3, not a separately-scheduled later run.
5. **Internal PE-load / `VirtualAlloc(PAGE_EXECUTE_READWRITE)` event, if instrumented** — the embedded Mimikatz being manually mapped into the SafetyKatz process; catches the credential-parsing step itself, which produces no file or network artifact of its own.
6. **`debug.bin` file deletion** (Sysmon 23, if configured, or `$MFT`/USN Journal analysis after the fact) — closes the loop and confirms a *successful*, complete run rather than an interrupted one; the gap between steps 4 and 6 should be small (well under the tool's internal 30-second thread-wait ceiling).
7. **[If a leftover `debug.bin` was recovered from an interrupted run]** — correlate its carved/recovered timestamp against whatever standalone Mimikatz or `pypykatz` analysis session later parsed it (`02`'s "Recovering an Interrupted Run" use case), the same downstream-correlation logic `../SharpDump/04 - Target Evidence.md` documents for its own deliverable file.
