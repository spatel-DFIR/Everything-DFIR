# Nmap — Target Evidence

Evidence left on or around the **scanned** network and hosts. This is the inverse of most sub-tools in this module: Nmap's default behavior runs **no code on the target at all** — the target's entire role is responding to crafted packets, so the deep evidence trail lives at the network layer, not in filesystem/registry/process artifacts. That changes only when the operator layers on `-sT`/`-sV` (which complete real connections application-layer services may log) or NSE `auth`/`brute`/`exploit`-category scripts (which authenticate against, or actively exploit, a target service).

## Network-Layer Evidence

This is the primary evidence class for Nmap — everything below survives regardless of what's running on the target host, because it's generated by the packets themselves.

| Source | What It Shows |
|---|---|
| Zeek `conn.log` | The single highest-value network artifact. A `-sS` sweep produces a burst of connections with `conn_state` `S0` (SYN sent, no reply — filtered/dropped) or a SYN followed immediately by a RST with zero bytes transferred either direction — dozens to thousands of near-simultaneous, content-free connection records from one source touching many distinct destination ports |
| Zeek `weird.log` | Out-of-spec TCP flag combinations (Null/FIN/Xmas scans, `--scanflags` custom combos) frequently trip Zeek's protocol-anomaly detector directly, independent of any dedicated scan-detection logic |
| NetFlow / IPFIX | A fan-out pattern — one source IP, many distinct destination ports and/or destination IPs, each flow tiny (often exactly one packet, 40-60 bytes, TCP flags = SYN only) in a short time window. This is frequently the **first** available signal in environments without endpoint or full-packet logging at all |
| IDS/IPS (Suricata/Snort ET rules) | The `ET SCAN` / `ET POLICY` rule families fire on: default Nmap OS-detection probe signatures, the specific SEQ/ECN/T2-T7 flag combinations documented in `01 - Overview.md`, and known default NSE-script traffic patterns — these are mature, well-tuned signatures precisely because Nmap's own probe set has been public and largely stable for years |
| Firewall connection logs (perimeter/segment) | Volume of denied/dropped inbound connections from one source spiking across a short window — the fan-out signal again, one layer further out |

See `Linux/10c - Network and PCAP Forensics.md` for the general Zeek/Suricata workflow this note builds on rather than re-deriving.

## Windows Firewall and Filtering Platform Logging

Two **separate, both off-by-default** Windows logging mechanisms are relevant if the target is Windows:

| Mechanism | What it captures | Requires |
|---|---|---|
| Security event 5156 | Windows Filtering Platform **allowed** a connection — process, user, source/destination IP and port, protocol | Advanced Audit Policy → Object Access → **Filtering Platform Connection**, "Success" — not enabled by default, and extremely high-volume once on (documented cases of 500+ events/sec on busy hosts) |
| Security event 5157 | Windows Filtering Platform **blocked** a connection — same fields as 5156 | Same audit subcategory, "Failure" |
| `%SystemRoot%\System32\LogFiles\Firewall\pfirewall.log` | Windows Defender Firewall's own W3C-format text log — per-packet allow/drop records, independent of the Security event log entirely | "Log dropped packets" / "Log successful connections" enabled per-profile in Windows Defender Firewall advanced settings (`netsh advfirewall` or GPO) — off by default |

A `-sS` scan against a Windows host with WFP auditing enabled produces exactly the same fan-out pattern as the Zeek/NetFlow signal above, just expressed as a burst of 5157 (mostly — closed/filtered ports) and 5156 (open ports where the SYN/ACK path completes far enough for WFP to log) events with a shared source IP.

## Application-Layer Artifacts (`-sT` / `-sV`)

`-sS` never lets a connection reach the application layer, so nothing here applies to the default half-open scan. `-sT` (connect scan) and `-sV` (which needs a completed connection to grab a banner or exchange protocol data) do:

| Service | Artifact |
|---|---|
| Web servers (IIS/Apache/nginx) | Access-log entries from `-sV`'s generic HTTP probes — often malformed, minimal, or missing headers a real browser would send (no `User-Agent`, or a fixed one across every probed vhost), abruptly reset rather than a normal request/response cycle completing |
| SSH (`sshd`) | `/var/log/auth.log` (or `journalctl -u sshd`) frequently logs `Did not receive identification string from <IP>` or a connection reset **before** authentication — the signature of a banner-grab that connects, reads the banner, and disconnects rather than a real client proceeding to auth |
| SMB (with `-sC`/`-sV` or targeted NSE scripts) | Depending on the specific script, a genuine SMB session setup — potentially a null/anonymous session — appears as a normal Security 4624 (Logon Type 3) event; see `Windows/11 - Event Log Analysis.md` and `Windows/12 - Lateral Movement.md` for the general SMB-logon evidence this note doesn't re-derive |

## NSE Script Footprint

- **`default`/`safe`/`discovery`** scripts generally complete legitimate, if unusual-looking, protocol exchanges (e.g. `smb-os-discovery` performs a real, if minimal, SMB negotiation) — these look like a genuine, if oddly-shaped, client session at the protocol level.
- **`auth`/`brute`** scripts generate repeated authentication attempts against the same service in rapid succession — the same signature a credential-spraying tool would leave, and equally capable of triggering account lockout policies and authentication-failure alerting (Security 4625 on Windows targets, service-specific auth-failure logs elsewhere).
- **`vuln`/`exploit`** category scripts can, by design, actually trigger the vulnerable condition they're testing for — up to and including crashing a service or (for `exploit`-category scripts specifically) achieving code execution. Treat these as active exploitation, not passive recon, when scoping and when reviewing evidence.

## Endpoint Security / IDS-IPS Product Behavior

Most modern EDR and network-IPS products ship a **generic, threshold-based port-scan heuristic** (N distinct ports or hosts touched by one source within window T) rather than relying solely on signature matching — this is precisely why `01 - Overview.md`'s timing-template and rate-control flags exist and matter operationally. Layered on top of that, mature products also carry specific signatures for the well-known default OS-detection probe sequence and for widely-used default NSE scripts. A target with a modern security product that shows **no** alert despite an otherwise-visible network-layer fan-out is itself worth investigating — product disabled, threshold misconfigured, or the scan was slow/spread enough (`-T0`/`-T1`, low `--max-rate`) to stay under the detection window.

## Host-Based Artifacts — What's Absent, and Why

Unlike this module's remote-execution sub-tools (e.g. `Impacket/psexec/`), a default Nmap scan leaves **no filesystem artifact, no registry key, no Prefetch entry, no scheduled task, and no new process** on the target — nothing runs there. The target's Prefetch/Amcache/ShimCache/process-creation evidence classes documented elsewhere in this repo simply don't apply unless an `exploit`-category NSE script achieved actual code execution, at which point the target-side evidence trail becomes whatever that specific exploit's payload leaves behind — a separate investigation from the scan itself.

## Building a Timeline

The tightest, highest-confidence anchor for a Nmap-originated event is purely network-layer: **a burst of NetFlow/Zeek `conn.log` single-packet or SYN-only flows from one source IP, fanning out across many destination ports/hosts, all within a tight window** — minutes for a `-T4`/`-T5` scan, potentially hours for a `-T0`/`-T1` scan deliberately spread to defeat exactly this signal. Where Windows Filtering Platform auditing or `pfirewall.log` is enabled, correlate the same window against 5156/5157 or firewall-log entries sharing the source IP; where `-sV`/`-sT`/NSE ran, correlate further against the application-layer artifacts above for the specific services actually touched.
